## 定位

一句话职责：**「中国期货行情 → 带指标的、可步进的历史视图」的数据层。**

下游是回测引擎（消费视图）。本库**不做交易决策，不做仓位核算**。

```
新浪 / 天勤 / 交易所 ──拉取──> futures-tickflow-go ──视图──> 回测引擎
                                    （本库）
```

姊妹项目 [okx-tickflow-go](https://github.com/dream-until-dawn/okx-tickflow-go)
在加密市场做同一件事。**本库不是它的移植**——两者的指标层、Store 层可以共享思路，
但**时间模型是全新的**，而且是本库绝大部分复杂度的来源。

### 与 okx-tickflow-go 的真实差异

不是「换个交易所」那么简单。下面每一条都会**改变架构**，不是改个参数：

| | okx-tickflow-go | 本库 |
|---|---|---|
| 交易时间 | 7×24 连续 | **一天 2–4 个时段，中间休市；且夜盘跨自然日** |
| 周期对齐 | `anchor + k·step` 时钟网格 | **交易时间轴上的等分**，网格随品种、随日变 |
| K 线标注 | 开盘时刻 | **上游按收盘时刻**（两个时刻都得存） |
| 判「已收盘」 | `now >= ts+step` | **必须查交易日历**，否则判不了 |
| 非交易日 | 无 | 周末 + 11 个法定节假日，**日期每年不同** |
| 「日」的定义 | UTC / 港时两条序列 | **交易日 ≠ 自然日**（夜盘归下一交易日） |
| 换月拼接 | 明确不做（永续无到期） | **必做**，且是核心功能 |
| 特有字段 | — | **持仓量、结算价、成交额** |
| 未完结 K 线 | 有 `Confirm` 标志 | **无标志，且标签是未来时刻** |

├── period.go            IntradayPeriod / CalendarPeriod：算 K 线边界
├── source.go            Source 接口
├── store.go             Store / Iterator 接口
├── sync.go              Syncer：按 coverage 只拉缺失区间
├── feed.go              Feed / View：可步进的多周期视图
├── indicator_api.go     Indicator 接口（别名指向 indicator 子包）
│
├── calendar/
│   ├── embedded/        内置：标称时段模板（带生效区间）+ 交易日表
│   └── derived/         从【分钟线】反推逐日实际时段（日线只定交易日）
├── refdata/             合约参考数据接口（乘数/最小变动价/到期日）
│   └── shinnyref/       天勤 openmd symbols 实现
├── source/
│   ├── sinasource/      新浪：日线 17 年 + 分钟线 1023 根
│   ├── shinnysource/    天勤：深度分钟 + 实时（需快期账户）
│   └── cffexsource/     中金所官方：**中金所品种结算价的唯一源**（非可选）
├── store/segfile/       默认实现：定长文件
├── continuous/          主力连续 / 换月 / 复权
├── indicator/           MA EMA MACD KDJ RSI CCI BOLL
└── adapter/             与下游记账内核对接（独立嵌套模块）
```

**主模块依赖**：`github.com/coder/websocket` 一个（实时行情要用）。
`refdata` 的天勤实现只用 `net/http` + `encoding/json`，不引入新依赖。

> **依赖选型是实测定的，不是偏好。** 本文第一版写的是 `gorilla/websocket`
> ——那是 Go 生态的默认选择，姊妹项目也用它。实测发现
> **gorilla 根本连不上天勤的行情网关**：
>
> - 服务端**要求** `permessage-deflate` 扩展，gorilla 默认不发 → `400 Bad Request`；
> - 开了 `EnableCompression` 之后握手过了（101），但服务端回的是
>   `permessage-deflate; server_no_context_takeover`，而 gorilla 对这个响应头做
>   **精确字符串比较**，只认「两个 `no_context_takeover` 参数都在」的那一种，
>   于是报 `invalid compression negotiation`。
>
> `coder/websocket` 配 `CompressionNoContextTakeover` 一次就通。
> 详见 [probe.md 6.3](probe.md)。
>
> 值得记的是**这个错误有多难从表象定位**：400 Bad Request，响应体只有
> 「Bad Request」四个字，加不加 token 都一样——看起来像鉴权问题，
> 实际在压缩协商。是靠抓本地回环上的原始握手、与 Python 客户端逐行对比才找出来的。

需要 `decimal` 的对接层隔离在 `adapter/` 这个**独立嵌套模块**里，
理由与姊妹项目相同——只想拉数据的人不该被迫拉进一个记账内核。

Go 版本取 **1.22**，与姊妹项目对齐，便于两边共享指标层的思路与测试。

## 二、时间模型：本库的核心

**这一节是本库与姊妹项目分道扬镳的地方，也是绝大部分复杂度的来源。**
先说清楚为什么不能沿用时钟网格。

### 为什么「对齐到整点」是错的

[probe.md 坑三之二](probe.md) 实测：沪银 `AG0` 与沪铜 `CU0`
**日盘时段完全相同**（09:00-10:15 / 10:30-11:30 / 13:30-15:00），
但它们的 60 分钟 K 线网格**整体错开 30 分钟**：

| | 夜盘 | 日盘 60m 标签 |
|---|---|---|
| `CU0`（夜盘 21:00–01:00，240 分 = 4×60） | 整除 | `10:00 11:15 14:15 15:00` |
| `AG0`（夜盘 21:00–02:30，330 分 = 5.5×60） | **余 30 分** | `09:30 10:45 13:45 14:45 15:00` |

原因：`AG0` 夜盘余下的 `02:00–02:30`，**跨过 6.5 小时的隔夜缺口**，
与次日 `09:00–09:30` 拼成一根完整的 60m。

**结论**：一根 K 线的边界，取决于**这个品种这个交易日从开盘起累计交易了多少分钟**。
它既不是时钟整点，也不能只看日盘。任何「对齐到整点」的实现在 `AG0` 上
**每一根都错 30 分钟**，而序列看起来完全正常。

### 三个概念

```go
// Session 一段连续交易时间，左闭右开 [Start, End)，毫秒墙钟。
type Session struct{ Start, End int64 }

// TradingDay 是交易日【编号】，形如 20260907。
//
// 具名类型而非 int32 别名——防的正是它与自然日混用。
// 夜盘在【自然日】上早于日盘，但属于【同一个交易日】：
// 交易日 20260907 = 周五 09-04 21:00–23:00 + 周一 09-07 09:00–15:00。
// 周五 15:00 是交易日 20260904 的结束，周五 21:00 是 20260907 的开始。
//
// 下游记账内核 futsim 用同一个表示，见第十二节——两边不必在边界上转。
type TradingDay int32

// Day 是一个交易日：编号，加上它【实际】开了哪些时段。
//
// 「实际」是关键：长假前停夜盘，那天的 Sessions 里就是没有夜盘段。
// 这是逐日事实，区间模式表达不了。相位不看这里，看 SessionTemplate。
type Day struct {
    Num      TradingDay
    Sessions []Session // 升序，第一段可能落在前一个自然日
}

// SessionTemplate 是【标称】时段模板，带生效区间。相位按它算。
type SessionTemplate struct {
    From, To TradingDay // 生效的交易日区间；To 为 0 表示至今
    Day      []Session  // 相对时刻：当日 00:00 起的毫秒偏移
    Night    []Session  // 可能为空；跨日用 >24h 的偏移表示
}

// ProductKey 是时段表的键：交易所 + 品种。
//
// 【不能只用 product】——郑商所的 `CF`(棉花) 与别处的同名品种要分开，
// 而且交易所本身就决定了时段大类（中金所股指 09:30 开收 15:00、国债 09:30 开收 15:15、
// 商品 09:00 开）。probe.md 第五节的 9 种时段模式正是按这个分的。
type ProductKey struct {
    Exchange string // SHFE DCE CZCE CFFEX INE GFEX
    Product  string // rb / TA / IF
}

func (s Symbol) ProductKey() ProductKey

// 日历说不出结果的三种原因，**必须分得开**。
var (
    ErrNotTradingDay = errors.New("tickflow: 该日不是交易日")
    ErrClosed        = errors.New("tickflow: 该时刻不在任何交易时段内")
    ErrUncovered     = errors.New("tickflow: 日历覆盖不到——这是「答不了」，不是「没有交易」")
)

// Calendar 交易日历。
//
// 键是 ProductKey，因为时段随品种不同（商品/股指/国债三套），
// 也随时间变（夜盘时间历史上调整过多次）。
type Calendar interface {
    // DayAt 返回包含 ts 的交易日。休市 → ErrClosed；覆盖不到 → ErrUncovered。
    DayAt(k ProductKey, ts int64) (Day, error)
    // DayOf 按交易日编号取。不交易 → ErrNotTradingDay；覆盖不到 → ErrUncovered。
    DayOf(k ProductKey, num TradingDay) (Day, error)
    // Template 返回该品种在该交易日生效的【标称】时段模板，算相位要用。
    Template(k ProductKey, num TradingDay) (SessionTemplate, error)
    // Covers 报告能回答的交易日闭区间。让边界出现在一行日志里。
    Covers(k ProductKey) (from, to TradingDay, ok bool)
    // Walk 按升序遍历 [from, to]。fn 返回 false 即停止。
    // ⚠️ 区间有一端落在 Covers 之外就【报错】，绝不静默少遍历。
    Walk(k ProductKey, from, to TradingDay, fn func(Day) bool) error
}
```

> **`v0.1.0` 之后这个接口变过一次**（`(X, bool)` → `(X, error)` + `Covers`）。
> 照着 `v0.1.0` 的文档写代码的人会撞墙，所以记在这里。原因：
>
> `v0.1.0` 里那个 `bool` 承载了两件完全不同的事——
>
> ```
> DayOf(rb, 20260905) → false   ← 周六，真的不是交易日
> DayOf(rb, 20160104) → false   ← 2016 年，日历【答不了】（早于生效起点）
> ```
>
> 后者被当成前者的后果很具体：内置模板自 `2020-05-06` 生效，
> 而新浪 `RB0` 日线自 `2009-03-27` 起——**中间十一年日历全答「不知道」**，
> `Syncer` 读成「不是交易日」就会静默跳过日线最值钱的那一段，且不会自愈。
>
> **三者的职责必须分清，别把前两个当护栏：**
>
> | | 挡住「静默少同步十一年」 |
> |---|---|
> | 哨兵错误 | ✗ —— `if err != nil { continue }` 一行全吞，成本和 `if !ok` 一样 |
> | `Covers` | 半 —— 得有人记得调 |
> | **`Walk` 拒绝超界** | **✓ —— 不调它就得自己写循环，那是看得见的选择** |
>
> 哨兵错误负责**说清楚**，`Covers` 负责**让边界可见**，`Walk` 负责**真的拦住**。
>
> ⇒ 一条通则：**给一个返回值之前，先数它要区分几种情况，看类型装不装得下；
> 装得下之后再问——这几种情况在调用点会不会被【一个惯用法】一次吞掉。**
> `bool` 的 `!ok`、`error` 的 `err != nil`、枚举的 `!= Found`，
> 每种类型都自带一个「一把全吞」的惯用法。**装得下是必要条件，分得开才是目的。**
>
> 时机取「现在」而不是「v0.3 一起改」：`Calendar` 当时零个消费者，
> 而 `Syncer` 正是那个会把 bug 写进去的消费者——**现在改，那个 bug 根本没机会被写出来**。
> 依据是 contract.md 第五节已公布的政策：v0.x API 会变，v1.x 才是对外契约。

### Period：在交易时间轴上等分

周期分**两类**，不是一个类型。日内周期在交易日**之内**切分，
日线及以上按交易日**成组**——把两者塞进一个 `Bars(td)` 里，
后者根本表达不出来（周线跨 5 个交易日，给它一个 `TradingDay` 无从下手）。

```go
// IntradayPeriod 日内周期：1m / 5m / 15m / 30m / 60m …
// 在【一个交易日之内】把交易时间等分。
type IntradayPeriod struct{ /* 内部：分钟数 */ }

// CalendarPeriod 日线及以上：1d / 1w / 1M。
// 按【交易日】成组，一组的边界是首个交易日的开盘到末个交易日的收盘。
type CalendarPeriod int
const (
    Daily CalendarPeriod = iota
    Weekly
    Monthly
)

// BarBound 一根 K 线的墙钟边界。
//
// 【Close - Open 通常不等于周期长度】——中间可能跨了休市段甚至隔夜缺口。
// 这不是异常，是中国期货 K 线的常态。
type BarBound struct {
    Open  int64
    Close int64
    // Full 表示这是一个【完整的网格格子】，不是交易日末尾的冲刷残段。
    // 它【不】等于「装了整整一个周期的交易时间」——停夜盘那天沪银的第一根
    // 日盘 K 线是完整格子，却只装了 30 分钟。要问装了多少，用 Minutes。
    // 反过来【绝不成立】：任何一根都不会装【超过】一个周期。
    Full bool
    // Anomalous 表示【这个交易日】的标称模板与实际时段矛盾，即模板过期。
    // 它是交易日一级的事实，所以那天的每一根都带；判据见 Day.TemplateMismatch。
    // 上层（v0.3 的 SyncReport.Misaligned）扫这一位就能报。
    Anomalous bool
}

// TemplateMismatch 报告当日【实际】夜盘与【标称】模板是否矛盾。
//
// 交易日一级、与周期无关。actual == 0 是停夜盘日，不算矛盾。
func (d Day) TemplateMismatch(tmpl SessionTemplate) (nominal, actual int, mismatch bool)

// Bars 给出某个交易日内该周期的全部 K 线边界。
//
// 这是本库最核心的一个函数：判完结、聚合、对齐、补洞全走它。
// tmpl 是品种的【标称】时段模板，用来算相位——见下面为什么少不了它。
func (p IntradayPeriod) Bars(tmpl SessionTemplate, d Day) []BarBound

// Group 把一串交易日按周/月成组。日线就是一天一组。
//
// 组的边界取【首个有时段的日】与【末个有时段的日】，不是首日与末日——
// 后者会让边界日没有时段时整组被静默丢掉，丢的是一整周或一整月。
func (p CalendarPeriod) Group(days []Day) []BarBound
```

> 一开始只有一个 `Period`，注释里写着「内部：分钟数，或 Daily/Weekly/Monthly」，
> 而唯一的方法是 `Bars(td TradingDay)`。**注释承诺的三种日历周期，
> 那个签名一种都实现不了**——评审 B1 指出的。
> 拆成两个类型之后，「哪些操作对哪类周期有意义」由类型系统回答，
> 不再靠使用者记住。

实现**不是**「沿 `td.Sessions` 累计交易毫秒」。这一点被实测推翻过一次，
值得把两个版本都留着。

> **第一版（错的）**：沿当天的 `Sessions` 累计交易毫秒，每满一个周期切一刀，
> 交易日结束时强制冲刷。它能解释当时观察到的全部现象，读起来也很漂亮。
>
> **它有一个可证伪的预言**：长假前交易所停夜盘，那天沪银没有 30 分钟的夜盘余数，
> 日盘就该从 09:00 干净地重开、网格退化成 `CU0` 那样。
>
> **实测把它证伪了**（[probe.md 坑三之三](probe.md)）：**两个**真正的停夜盘日
> （2026-05-06 五一后、2026-06-22 端午后）× 三个品种，日盘网格**与普通日完全相同**。
> 沪银在没有夜盘的那天，第一根 60m 仍然只装 30 分钟、仍然收在 `09:30`。

正确的规则分两半：

```go
// Phase 返回该品种在该周期上的【相位】——日盘开盘时，网格上已经"欠"了多少。
//
// 它等于「标称夜盘长度 mod 周期」，是【品种的固定属性】，
// 不依赖某一天是否真的开了夜盘。
func (p IntradayPeriod) Phase(tmpl SessionTemplate) time.Duration
```

1. **相位按标称模板算**，是品种常量：沪银 `330 mod 60 = 30`，沪铜 `240 mod 60 = 0`；
2. **切分沿当天实际交易的时段累计**，从相位起算，交易日结束时强制冲刷；
3. **夜盘残段的 `Open` 要带进日盘块**——相位管「网格切在哪」，`Open` 管「那段时间归谁」；
4. **但「带进去」有上界**：残段只有不超过相位时才塞得进第一根日盘。
   超了就说明标称与实际矛盾，**单独冲刷成一根短的并标 `Anomalous`**，不摊进网格。

第 3 条是 v0.1 实现时补的，因为漏了它的第一版**能通过全部标签比对**：

> **v0.1 自查发现的静默丢数。** 第一版只把「相位」带进日盘块，`Open` 让日盘
> 自己从 `09:00` 起。于是沪银 60m 的 `02:00–02:30` **不属于任何一根 K 线的
> `[Open, Close)`** ——收盘标签序列一根不差（`22:00 23:00 00:00 01:00 02:00
> 09:30 …`），总根数一根不差，唯独那半小时凭空消失。
>
> 按 `[Open, Close)` 聚合的下游会安静地少掉 30 分钟成交量，**不报错**。
> 而 `BarBound` 的注释当时就已经写着「沪银 60m 的某一根 = 前一日 `02:00–02:30`
> \+ 当日 `09:00–09:30`」——**文档是对的，实现没做到，而测试比的是标签，
> 看不见这个差别**。doccheck 也看不见：它比签名，不比语义。
>
> 补上的是一条不变量而不是一个回归值：`TestBarsCoverEveryTradingMinute`
> 把交易日的每一分钟点一遍，要求**恰好**落在一根 K 线里——不能漏、
> 也不能被两根同时认领。1m/5m/15m/30m/60m × 含停夜盘日全点。

第 4 条是评审 I1 逼出来的，**方向和上面那次正好相反**：

> **超装。** 补完「不漏」之后，`nightCarried > phase` 时第一根日盘会装
> `nightCarried + (周期 − 相位)` 分钟——**一根 60m 的「完整」格子装了 90 分钟**。
> 触发条件是当日实际夜盘比标称长，即交易所延长了夜盘而模板没跟上。
>
> 三道守卫一道都没覆盖：标签序列一根不差；覆盖不变量 `555 = 555` **通过**
> （多装的时间是从别处偷的，总量不变）；doccheck 比签名不比语义。
>
> ⇒ **守恒类不变量是有方向的，必须成对。**
> 「不漏」（下界：每一分钟至少落在一根里）与「不超」（上界：每一根至多装一个周期）
> 是两条独立的断言，只写一条，另一个方向的错误照样全绿。
>
> 而且**成对的两条必须跑在同一片输入上**——原先上界那条测了「实际 > 标称」，
> 下界那条没测，于是「成对」是假的：一条测 A 集合、另一条测 B 集合，
> 两个方向各留了一半没人看。现在两条共用同一个矩阵
> （标称 0/120/240/330 × 实际 0/90/120/150/240/300/330/390 × 周期 1…90m）。

**为什么是「标记」而不是「按某一侧截断」**：把矛盾显式冒到上层，
比安静地摊进网格便宜得多。

> ✅ **`实际 > 标称` 那一侧，2026-09-09 验了 —— 它不但存在，而且是【一整段历史的常态】。**
>
> ```
> KQ.m@SHFE.rb   2016-04-29 之前   夜盘最晚一根 00:00（开到 01:00）
>                2016-05-03 之后   夜盘最晚一根 22:00（开到 23:00）
> 而内置时段表建于 2020-05-06 之后 ⇒ 它记的是【短的那个】
> ```
>
> ⇒ **把内置表套到 2016-04-29 及更早的 `rb` 数据上，每一天都是 `实际 > 标称`。**
> 而本库的目标深度正好盖到那里（天勤 1m 回溯到 2016-01-04）。
>
> ⚠️ 所以原文那句「实测只覆盖 `实际 ≤ 标称`」**不是「那一侧不会发生」，
> 是「我们当时只看了 2020 年以后」** —— 而库要读的数据比那早四年半。
>
> **⇒ 这一格的处置不用改：「标记不截断」正是对的。**
> 而它现在有了证据 —— 换成「按标称截断」会把 2016 年那段的夜盘**整段丢掉**，
> 且丢得悄无声息。**验完之后维持原判，和没验过就维持原判，不是一回事。**

**而「矛盾」这个判据本身也错过一次**（评审 K1）：

> 第一版把它写成 `nightCarried > phase`——**两个取模后的余数相比**。
> 于是同一个「标称 330 / 实际 310」的事实，`15m`/`30m` 报、`5m`/`60m`/`90m` **不报**
> （60m 下是一根装 40 分钟、不带任何标记的 `Full` 格子）。
>
> 「模板与实际矛盾」是**交易日一级、与周期无关**的事实，而标志骑在了周期上。
> 后果：`SyncReport.Misaligned` 只扫这一位，会**按周期漏报**，
> 且漏掉的那些看起来完全正常。而 `Anomalous` 的注释当时自称
> 「这一根是那个矛盾的产物」——**与行为不符**。
>
> 改法：检测提到日级（`Day.TemplateMismatch`，比分钟数不比余数），
> 那天的**每一根**都带标。`actual == 0` 不算矛盾——那是停夜盘日，
> 是实测过的预期内事实；算进去的话这一位会在每个长假前后亮起来，
> 而**一个经常亮的标志和一个不亮的标志一样没用**。
>
> ⇒ 一条可复用的：**先问这个事实活在哪一级**（合约？交易日？某一根？），
> 再决定标志挂在哪。挂低了会随下层维度漏报，而漏报看起来永远像「没问题」。

第二半解释跨休市段（30m 的 `10:45`）与日末短根（30m 的 `15:00` 只有 15 分钟）；
第一半解释跨隔夜缺口（`AG0` 的 `09:30`）**以及停夜盘日为什么不变**。

这就是 `Bars` 为什么要吃 `tmpl SessionTemplate` ——只给 `TradingDay` 不够，
因为停夜盘那天 `TradingDay.Sessions` 里根本没有夜盘段，相位就无从算起。

> 置信度：**「相位与当天实际交易无关」是实测**（2 个停夜盘日 × 3 个品种）。
> **「相位 = 标称夜盘长度 mod 周期」这个公式是推定**——它拟合了目前观察到的
> 全部数据，但只在 330 分与 240 分两种夜盘长度上验过。
> 变了会怎样：`SyncReport.Misaligned` 不为零。
>
> **这次证伪的代价，正是本库存在的理由。** 那个错误一年只在长假前后发作、
> 只影响 `au`/`ag`/`sc` 这类夜盘不整除的品种，不报错、不崩溃，
> 只是把那几天的每一根 K 线都错开 30 分钟。要是等写完 `Source` 才发现，
> 上层全部要返工。

### 但上面那套规则**只描述新浪**——聚合口径是本库要自己选的，不是照抄的

> **2026-09-07 三轮修正。** 上面「相位 + 交易时间轴切分」是从**新浪**的高周期
> K 线反推出来的，原文把它写成了「中国期货的周期规则」。实测天勤之后发现，
> **那是过度概括**。

天勤（本库的深度与实时数据源）同一天同一品种的高周期（[probe.md 坑三之四](probe.md)）：

```
天勤 60m: 09:00 10:00 11:00 13:00 14:00        ← 纯时钟网格，按【开盘时刻】标注
新浪 60m: 09:30 10:45 13:45 14:45 15:00        ← 交易时间轴，按【收盘时刻】标注
```

沪银与螺纹在天勤那边的 60m 标签**完全相同**——**天勤没有「相位」这个概念**。
而且这不只是标注差异：新浪的 `10:45` 那根装 `10:00–10:15`+`10:30–10:45`（30 分钟），
天勤的 `10:00` 那根只装 `10:00–10:15`（15 分钟）。**内容不同。**

**所以架构上多一条决定：**

> **本库自己从 1m 聚合出全部高周期，用一套本库明确选定的规则；
> 两个源的高周期 K 线一律只作【对账】，不作真值。**

1m 是安全的公共基底——一根 1m 就是一根 1m，两个源在这个粒度上没有分歧。

聚合规则做成可选，两套都实现：

```go
type AggRule int
const (
    AggClockGrid   AggRule = iota // 时钟网格，开盘时刻标注（= 天勤）
    AggTradingAxis                // 交易时间轴 + 相位，收盘时刻标注（= 新浪）
)
```

**默认取哪套是【未验】**：要看国内主流软件（文华 / 博易 / 快期）用哪套，
本库还没测。**在验之前不设默认**——与指标口径同一条处置
（第九节：「未验前不设默认，缺省报错」）。

> 姊妹项目在这里的教训直接适用：它一开始把指标默认口径拍成 TV，
> 理由是「国际主流」，后来实测发现 OKX 平台用 CN，**默认值是拍的、不是量的**。
> 这次不重犯：**一个会改变全部高周期 K 线内容的默认值，必须由实测定。**

「相位」那套规则并没有作废——它是 `AggTradingAxis` 的正确实现，
且新浪的数据要按它解释。作废的只是「它是唯一规则」这个说法。

### 交易日历从哪来：从数据反推，而不是维护一张节假日表

节假日表是**每年国务院发文才定**的，而且调休规则复杂（周末上班、节前节后挪）。
维护一张表意味着每年要改一次代码，且改晚了就静默出错。

**本库的做法是反推**：

- **哪天是交易日** —— 从一条高流动性合约的**日线序列**读出来。
  `RB0` 有 2009 年至今 4237 根日线，**有日线的那天就是交易日**。
  这是从数据本身得到的真值，不是一张会过期的表。
- **每个交易日有哪些时段** —— 天勤 openmd 的 `trading_time`（按合约给）
  提供当前时段；历史时段变更从**历史 K 线的实际时间戳**反推
  （某天最早的一根是 21:05 还是 09:05，夜盘最晚一根到几点）。

内置一份导出快照在 `calendar/embedded`，`calendar/derived` 提供从库里已有数据
现场反推的实现。两者都实现 `Calendar` 接口。

**时段表要分成两层，因为「标称」与「实际」是两回事：**

```go
// SessionTemplate 品种的【标称】时段模板，带生效区间。
// 相位按它算（见上）。夜盘时间历史上调整过，所以要带区间。
type SessionTemplate struct {
    From, To TradingDay // 生效的交易日区间
    Day      []Session // 相对时刻
    Night    []Session // 可能为空；跨日用 25:00 / 26:30 表示
}

// 而 Day.Sessions 是【那一天实际开了哪些段】——逐日事实，
// 区间模式表达不了：长假前停夜盘就是单独某一天没有夜盘段。
```

**两层各管一件事，不能合并**：

- **相位**看 `SessionTemplate`（标称），停夜盘也不变；
- **切分**沿 `TradingDay.Sessions`（实际）累计，停夜盘那天就是少一段。

> 评审 A2 要求「`TradingDay` 的构造路径要能逐日给 `Sessions`，不能只给模式」——
> 这条成立，而且**即使相位不受影响也仍然成立**：那天确实少了几根夜盘 K 线，
> 切分要知道。
>
> **`calendar/derived` 从日线反推不出「那天有没有夜盘」**（日线只能给「哪天是交易日」）。
> 一轮时这是个真缺口——新浪 60m 只有 9 个月，更早的长假无从确定。
> **二轮之后不再是**：天勤有 10 年 1m 数据，每个交易日实际开了哪些段可以逐日反推
> （1m K 线存在与否就是交易与否）。所以 `calendar/derived` 的输入应当是
> **分钟线**而不是日线；日线只用来定「哪天是交易日」。

> **未来的交易日历推不出来。** 反推只能覆盖到「已有数据」的最后一天。
> 实盘要判断明天是否开市，得靠 `embedded` 的前瞻表或交易所公告。
> 本库**不猜**：`DayOf` 对未知日期返回 `ok=false`，由调用方决定怎么办。

## 三、数据模型

```go
// Bar 是一根【已完结】的 K 线。
type Bar struct {
    Ts         int64 // 开盘墙钟时刻，毫秒
    TsEnd      int64 // 收盘墙钟时刻，毫秒
    TradingDay TradingDay // 所属交易日，yyyymmdd

    Open, High, Low, Close float64

    Volume       float64 // 成交量（手）
    Turnover     float64 // 成交额（元）
    OpenInterest float64 // 持仓量（手）
    Settle       float64 // 结算价；仅日线有，分钟线为 NaN

    Flags BarFlags // 完整性与来源，见下
}
```

### 为什么 `TsEnd` 与 `TradingDay` 要【存】而不是【算】

两者都可以由 `Ts` 加交易日历推出来。存下来多花 12 字节。仍然选择存，
理由是**它们依赖的那张表会变，而已落库的数据不该跟着变**：

- 夜盘时间历史上调整过多次（实测：同一个 `product_id` 出现在 3 种时段模式里）；
- 交易所改了时段，`calendar/embedded` 跟着更新，于是**同一批旧数据**
  在新版本下会被算出**不同的** `TsEnd` 和 `TradingDay`；
- 那意味着一个跑过的回测，升级一次库就换了结果，而且**不报错**。

存下来，记录就是**自描述**的：2026 年拉的数据，2027 年交易所改了夜盘之后
读出来仍然是它当初的样子。12 字节买一个「历史不会被追溯性改写」的保证，
很划算。

> 姊妹项目不需要这一条，因为 `ts + step` 在 7×24 上永远成立。
> 这是「同一个抽象在两个市场里代价完全不同」的一个具体例子。

### 为什么 float64 而不是 decimal

与姊妹项目同一个理由：指标计算是热路径，decimal 慢一到两个数量级，
而中国期货的价格位数（最多 4 位小数，如国债期货的 0.005）远在 float64
的 15 位有效数字之内。与记账层的 decimal 世界的转换收在 `adapter/` 一处。

**但有一个中国期货特有的注意点**：`Volume` 与 `OpenInterest` 是**手数**，
本该是整数。用 float64 存是为了记录定长对齐，读出来时若要当整数用，
**必须显式取整**而不是直接转换——`float64(x)` 到 `int64` 的截断在
接近整数的浮点值上会错 1。库里提供 `Bar.Lots()` 做这件事。

### 记录布局

一条记录 **88 字节**（小端），无文件头，`offset = i * 88`：

```
ts(8) tsEnd(8) tradingDay(4) flags(4) | open high low close(32) | vol(8) turnover(8) oi(8) settle(8)
```

`Flags` 里放**完整性与来源**：

```go
FlagPartial   // 已知不完整（时段中途熔断/停牌，或聚合时底层缺根）
FlagAggregated// 由更低周期聚合而来，不是上游直接给的
FlagSrcSina / FlagSrcShinny / FlagSrcExchange  // 来源
```

**来源要记进每一根**，因为本库有多个源且它们可能不一致。
「这根是哪来的」在对账时是第一个要问的问题，事后从别处推不出来。

不预留保留字节：格式变更走 `.meta` 里的 `format`，打开时报错并说明怎么迁移。（**这里原来写的是 `version`** —— 而 §6.1 那份正本叫 `format`，代码里也是 `format`。同一个字段两个名字，2026-09-09 统一。）
预留字节是「猜将来要什么」，猜错了照样要迁移，还白占空间。

## 四、合约代码

```go
// Symbol 规范形式：<EXCHANGE>.<product><YYMM>，如 SHFE.rb2701、CZCE.TA2701。
type Symbol struct {
    Exchange string // SHFE DCE CZCE CFFEX INE GFEX
    Product  string // rb / TA / IF
    YearMon  int    // 2701
}
```

三个坑，都是实测撞出来的：

**一、品种代码大小写不统一，且是交易所规定的。**
上期所/大商所用**小写**（`rb` `cu` `m` `i`），郑商所/中金所用**大写**
（`TA` `MA` `IF` `T`）。新浪对大小写不敏感（`rb2701` 与 `RB2701` 返回完全相同），
但**交易所与 CTP 敏感**。本库内部**一律用交易所的原生大小写**，
入口处做规范化。

**二、郑商所原生是 3 位年月码，有歧义。**
郑商所自己写 `TA701`，指 2027 年 1 月。但 `TA701` 也可以读成 2017 年 1 月——
**跨十年就分不清了**，而本库要处理 2009 年至今的历史。
内部**一律 4 位**（`TA2701`）。新浪也要 4 位——实测 `TA701` 不报错，
返回的是 **`var _=(null)`，是 `null` 而不是空数组**。

这个区别要写进解析层：`json.Unmarshal` 到 `[]Bar` 遇到 `null` 得到 `nil` 切片、
`len()` 为 0，与「这个合约这段确实没有数据」**长得一模一样**。
把「代码写错了」和「确实没数据」渲染成同一个结果是一种静默失败，
所以 `sinasource` 的解析层**必须把 `null` 与 `[]` 分开**，前者报错、后者正常返回空。

> 探针脚本自己在这里栽过一次：`sina_json` 一度把 `null` 归一成 `[]`，
> 等于亲手制造了它旁边那段文字正在警告的失败。已改回不归一。

3 位转 4 位需要一个基准年，规则定为「相对**该数据所属的交易日**取最近的将来」，
而不是相对「现在」——否则同一段历史数据在不同年份跑出不同结果。
这条是**推定**（郑商所没有文档说明跨十年怎么办），有测试锁住，
`RegisterCentury` 可覆盖。

**三、主连/指数不是合约。**
`RB0`（新浪）、`KQ.m@SHFE.rb`（天勤）都不是可交易的合约代码。
本库用单独的类型表达，**不混进 `Symbol`**——否则「这个代码能不能下单」
这个问题就没有类型层面的答案了。

## 五、拉取

```go
type Source interface {
    // Bars 返回 [From, To] 内【已完结】的 K 线，按 Ts 升序。
    Bars(ctx context.Context, req BarRequest) ([]Bar, error)
    // Caps 报告这个源【在某个品种上】的能力与边界，见下。
    // 深度必须按品种问，不能只按周期——同为 60m，AG0 与 RB0 的可回溯天数差近两倍。
    Caps(k ProductKey) Capabilities
}

// BarRequest 是一次拉取请求。
type BarRequest struct {
    Symbol Symbol     // 要哪个合约或主连
    Period Period     // 要什么周期
    From   TradingDay // 起（含）
    To     TradingDay // 止（含）
}
```

> **区间按【交易日】给，且是闭区间——两条都是决定，不是省事。**
>
> **为什么是交易日不是墙钟毫秒**：夜盘属于下一个交易日，
> 所以一个交易日的 K 线**从前一个自然日的 21:00 就开始了**。
> 用毫秒区间表达「我要 2026-09-04 这一天」，调用方得先自己把日历算一遍——
> 而算错不会报错，只会少一段夜盘。**交易日是本库唯一不会让调用方算错的单位。**
>
> **为什么是闭区间**：`Span`（§六，已实现）的 `To` 就是闭的。
> `Syncer` 的活是把 coverage 里的 `Span` 翻成 `BarRequest`，
> **两个区间语义不同的话，那一步每次都要 ±1，而 ±1 错了不报错**——
> 它表现为「少拉一天」或「多记一天已拉」，后者会被 coverage 固化成
> 「拉过，确认没有」，正是第七节最在意的第二类缺口。

`Period` 是一个**密封**接口：只有本包里的 `IntradayPeriod` 与 `CalendarPeriod`
实现它，靠一个不可导出的方法封口。

```go
type Period interface {
    String() string
    isPeriod()
}
```

> **为什么要密封**：`Capabilities.Since` 用它做 map 键，
> 而一个只要求 `String()` 的开放接口，任何带 `String()` 的类型都能塞进来——
> 包括 `time.Duration`。密封之后「周期」这个概念在类型层面就是**穷举的两种**，
> 新增一种必须改本包，改本包就会撞上这里的测试。

实现**必须**保证（与姊妹项目同一套，但多了两条）：

- 返回按 `Ts` 升序、无重复；
- **只含已完结的 K 线**——上游没有标志位，实现要自己按交易日历判；
- 只含落在 `[From, To]` 内的（**按 `TradingDay` 判，不按 `Ts`**——夜盘的 `Ts` 在前一个自然日）；
- 真的没数据时返回空切片而非错误（停牌、新合约上市前都会缺）；
- **`TsEnd` 与 `TradingDay` 必须填**，不能留零值让上层猜；
- **不得把上游的收盘时刻标签当成 `Ts`**——新浪给的是收盘时刻，要换算回开盘时刻。

### `Capabilities`：让「这个源能给什么」成为可查询的

```go
// Caps 报告【某个品种上】的能力。
//
// 深度必须按品种问，不能只按周期——见下。
func (s Source) Caps(k ProductKey) Capabilities

type Capabilities struct {
    Periods   []Period // 支持哪些周期
    MaxBars   int      // 单次/总共最多能给多少根（新浪是 1023，且【无法翻页】）
    Since     map[Period]TradingDay // 【该品种】各周期**最早给得出哪个交易日**
    HasSettle bool     // 是否给结算价
    HasOI     bool     // 是否给持仓量
    Realtime  bool
}
```

> **`Depth` 一度以 `Period` 为键，那是错的**——它犯的正是 B2 刚在 `Calendar`
> 上修掉的同一个结构性错误。新浪的 1023 是**根数**上限，而一个交易日出几根
> 取决于品种的时段总长，于是同为 60m：`AG0` 只有 **≈4.8 个月**、
> `CU0` ≈6.1 个月、`RB0` ≈8.5 个月（[probe.md 坑一](probe.md)）。
>
> 不改的话，`Syncer` 会按 `RB0` 的 9 个月去向 `AG0` 要数据，拿回 4.8 个月，
> 然后把差额记成「**拉过，确认没有**」——那正好落进第七节最在意的第二类缺口，
> 而且**静默**：coverage 一旦这么记下，那段就永远不再重拉。
>
> 评审 D1 指出的。

> ⛔ **而它第二次改形状：`Depth map[Period]time.Duration` → `Since map[Period]TradingDay`。**
>
> 第一次改的是【键】（按品种问，不只按周期）；这一次改的是【值】：
>
>	真实约束是一个**绝对日期**（新浪合约级日线约从 2018-05 起）；
>	而「能回溯多久」是一个**随时间增长的量** ⇒ 写成常量它明天就偏一天。
>
> ⚠️ 而换成 `TradingDay` 还多买到一样东西：**零值可辨**。
> `time.Duration(0)` 里「不知道」和「一天都给不了」长得一模一样；
> `TradingDay(0)` 的 `Valid()` 为假 ⇒ **忘了填这件事本身能被 `Validate` 查出来**。
> ⇒ **换形状的理由不是「新的更好听」，是旧的把「没填」藏了起来。**
>
> 这一格是**第一个实现**（`sinasource`）撞出来的 —— 设计稿上它看不出问题。

姊妹项目没有这一层，因为它只有一个源。本库有三个，且**它们的能力差异很大**
（新浪日线 17 年 / 分钟线 3 周；天勤要账户；中金所只有日线）。
把差异做成**数据**而不是散落在文档里，`Syncer` 才能在拉不到时给出
「这个源本来就给不了这么深，换一个」而不是一个干巴巴的空结果。

### `CheckBars`：把上面那六条约定变成一次可执行的检查

六条「实现必须保证」写在文档里，**而文档不会在实现违反它的时候出声**。
`source.go` 里给一个共用的检查器，每个源的测试都拿它过一遍：

```go
func CheckBars(req BarRequest, bars []Bar, now int64) error
```

它一次报出**全部**违反项，不是第一条就返回——写实现的人要的是一张清单，
不是一次只修一个然后重跑六遍。

⚠️ **它比不了的两格，写在这里而不是留给下一个人去发现：**

| 约定 | 为什么机械查不了 |
|---|---|
| 真的没数据时返回**空切片而非错误** | 那是返回路径的形状，不在 `bars` 里 |
| **不得把上游的收盘时刻标签当成 `Ts`** | 整体偏移一个周期的序列，**自身完全自洽**：仍然升序、仍然落在区间内、`TsEnd-Ts` 仍然等于周期长。只有拿它和日历的 `BarBound` 对齐才看得出来 |

⇒ 第二格由各源自己的解析测试盯（新浪那一侧尤其要盯，见下表）。

### 各源的粗糙面

| 源 | 要消化的 |
|---|---|
| **新浪** | JSONP 包裹要剥；GBK（实时接口）；**标签是收盘时刻**；**含未完结的当前根且标签在未来**；1023 根硬顶且**无翻页**；郑商所要 4 位码；`null` ≠ `[]`；**实时接口已冻结两年，不接** |
| **天勤** | OIDC 取 token（**机密客户端**）；**行情地址必须问名称服务**；websocket 要 `permessage-deflate`；DIFF 协议的增量合并；**日期按交易日而非自然日** |
| **中金所** | XML；只有日线；只覆盖中金所。**714 条里 686 条是期权**，按 `instrumentid` 含 `-` 过滤 |

### 天勤源的四个实现约束（都是实测出来的，见 [probe.md 第六节](probe.md)）

**一、`client_secret` 由使用者显式提供，库里【不设默认值】。**
它是从对方开源 SDK 里读出来的（`shinny_tq` + 一个 UUID），**不是发给我们的**。

两个理由，是两类：

**技术上**：对方随时可以轮换，轮换当天本库就连不上。可配置至少让使用者能自己救，
写死成常量就只能等我们发版。鉴权失败时的错误信息要**直接说出这个可能性**，
而不是丢一个 401。探针 `shinny-auth` 盯着这一条。

**合规上**：拿对方 SDK 里的客户端身份去连对方服务，**是否符合天勤的使用条款，
本库未验**。库里若带一个默认值，等于**替使用者做了这个决定，而他们多半不知道
自己在用一个不属于自己的 client 身份发请求**。所以不是「做成可配置」，
而是**必须显式提供，缺失就报错**——让这一步成为使用者明确的一个动作。

> 这一维是评审 D4 补的。原文只写了「会轮换」这个技术脆弱点，
> 把一个**合规**问题记成了纯技术问题。contract.md 的风险表里单列一行，
> 后果一栏写「合规/条款」而不是「数据错」——它和表里其他行不是同一类风险，
> 混在一起会被当成又一个技术坑略过。

**二、行情地址走名称服务，不写死域名。**
`GET https://api.shinnytech.com/ns?stock=false&backtest=false` 返回 `mdurl`。
实测返回 `wss://free-openmd.shinnytech.com/...`——而这个域名**猜不出来**
（试过 `openmd` / `api` / `free-api` / `u` 全错）。对方按账户与负载返回不同地址，
写死等于给自己埋雷。

**三、DIFF 协议的合并要自己实现，且是 merge-patch 语义。**
服务端推 `rtn_data`，`data` 是一串 JSON merge-patch：`null` 表示**删键**，
对象递归合并，其余直接覆盖。客户端维护一份快照。
`set_chart` 用 `focus_datetime`(纳秒) + `focus_position` 定位左端点，
`left_kline_id` 往后翻页，`view_width` 一次 2000 根。

**四、日期口径要在入口处转换。**
天勤的日线按**交易日**标注（周一夜盘 21:00 属于次日那根），
新浪按**自然日**。`Bar.TradingDay` 以**交易日**为准（与天勤一致，
也与交易所结算一致），所以 `sinasource` 要做转换，`shinnysource` 直接用。
**这条不做，两个源的数据接在一起就整体错位一天，且不报错。**

**新浪实时接口不实现。** [probe.md 第三节](probe.md)实测它自 2024-07-17 冻结，
返回 200 与一份看起来完全正常的快照。**接一个会静默给出两年前数据的源，
比没有这个源糟得多。**

> 若日后有人要接任何实时源，**必须带开机自检**：把实时快照与当日日线比对，
> 对不上就报错。这条写进 `Source` 的实现约定里，不是建议。

## 六、持久化

沿用姊妹项目的定长文件方案（理由相同：K 线是定长、追加、按时间有序的负载；
SQLite 要 CGO 或几十 MB 生成代码；bbolt 的 B+ 树页会让文件膨胀且我们不需要事务）。
`Store` 是接口，谁想接别的都行。

```
<root>/
  candles/                 命名空间（ticks/ 等留位）
    SHFE.rb2701/
      1m.dat               纯定长记录数组，offset = i * 88
      1m.meta              JSON，人可读
    _continuous/           主连序列（见第八节），与合约分开放
      SHFE.rb@oi--ratioback-v1/1d.dat
  .lock
```

⛔ **接口按【本仓实现】反推，姊妹项目的名字仅供参考**（改于 2026-09-09，七之零冲突三）。
上一版写的是「与姊妹项目基本一致（`Append` / `Merge` / `Iter` / `Range` /
`Meta` / `AddCoverage` / `Series` / `Close`）」，而 `store/segfile` 实到的是
`Coverage` / `AppendBars` / `CommitSpan` / `Verify` / `HasBars` / `Close` ——
**八个名字只对上一个（`Close`）**。照那一行写 `Syncer`，它会对着一组不存在的方法。

与姊妹项目的两处不同（这两条与名字无关，仍然成立）：

**一、`coverage` 记的是【交易日】区间，不是时间戳区间。**
时间戳区间在这里表达不了「这一段我请求过且确认没有数据」——
休市段本来就没有数据，用时间戳记会让每个夜盘间隙都长得像一个空洞。
按交易日记，语义是清楚的：「20260101 到 20260131 这些交易日我都问过了」。

**二、主连序列单独放 `_continuous/`，且键里带【全部】拼接参数。**
同一个品种按不同换月规则、不同复权方式拼出来的是**不同的序列**，
它们必须能共存。

键的生成规则**必须写死，且必须覆盖每一个参数**：

```
<product>@<rollRule>-<rollParams>-<adjust>-v<keyVersion>
例：SHFE.rb@oi--ratioback-v1
    SHFE.rb@fixeddays-3-ratioback-v1
    SHFE.rb@fixeddays-10-ratioback-v1
```

> **`SHFE.rb@oi-ratioback` 这个第一版的键是错的**：它没编码 `RollRule` 的参数，
> 于是 `FixedDaysBeforeExpiry(3)` 与 `FixedDaysBeforeExpiry(10)` 会落到
> **同一个目录，静默互相覆盖**——而这一段自己写的理由正是「换个参数就是
> 另一条序列，不会互相覆盖」。**一句承诺，配一个兑现不了它的键。**
> 评审 B3 指出的。
>
> 参数多了目录名会长，所以规则定成：**参数少于 4 个直接编进目录名，
> 超过则用 `h<8位哈希>`，并在该目录的 `.meta` 里存全量参数**。
> `keyVersion` 是给「以后改了键的算法」留的——不带它的话，
> 换算法就会让旧目录被当成新参数的序列读出来，那又是一次静默覆盖。
>
> `Open` 时会把 `.meta` 里的全量参数与请求的参数**比对**，
> 不一致直接报错而不是接着写——哈希碰撞与手工改目录名都能被挡住。

> > 不是它们和盘上的文件一致。**

> > 它保证这 20 条**都有人认领**；**它不保证认领的人真的动手了。**
> > `TestInvariantA2_Red` 里有没有真的违反 A2，`go/ast` 读不出来。
>
> **这是「存在 ≠ 一致」在编号上的重演**，和 `guardNames` 那次一模一样：
> 登记的是名字，把函数体掏空照样 PASS。
> ⇒ 真正顶住后一半的**不是**这条收集测试，是那 13 个 `_Red` **各自的对照组**：
> **每个 `_Red` 必须在【不违反该不变量】的输入下变绿**——
> 否则它证明的只是「这个测试会红」，不是「它因为那条不变量而红」。

#### 先划清：四态里只有两态是【存储】能回答的

```
没拉过        ← 存储（coverage）
拉过确认没有  ← 存储（coverage）
不是交易日    ← 日历
日历答不了    ← 日历
```

**存储只需要把前两态分开**，后两态问日历。这一格划不清就会去设计一个
「存储里记这天是不是交易日」的字段——**那是把日历的答案抄进存储，
抄件会过期，而过期的抄件不会报错**（同 §5 那张时段表抄自被截断的目录）。

> ⚠️ **但存储对「拉没拉过」有【三种】回答，不是两种**：
> 除了「没拉过」「拉过（有数据 / 确认没有）」，还有 **「答不了」**——
> 触发条件是 **`format` 缺失且源不可重放**（见下方那一段）。
>
> 这一行是补的：上一版 §1 只说了两种，而 `unverified` 是在下面才引入的，
> **停在 §1 的人会带着一个缺一种回答的模型往下读**。
> ⇒ **一个用来建立模型的段落，不能只在别处被修正。**

#### ① ② 两对，不是一对：**coverage 分「拉没拉过」，计数分「确认没有 vs 丢了」**

```json
{
  "format": 1,
  "coverage": [{"from": 20200506, "to": 20261231, "bars": 1284310, "days": 1497}]
}
```

- `coverage` 是**交易日闭区间**的有序不重叠列表（§6 已定：不是时间戳区间）；
- **相邻性按【交易日】算**，不按自然日：`20200731`（周五）与 `20200803`（周一）
  是相邻的两个交易日，**中间没有洞，必须合成一段**；
- 每段带**两个计数**：`bars`（写这一段时实际落盘了多少根）与
  `days`（这一段里至少有一根的交易日条数）。**两个都要，理由见下面「和什么比」。**

⚠️ **第一版这一格我写错了两处，两处都由评审方 2026-09-08 找出来：**

> **错一（形状）**：我把「拉过确认没有」定义成
> 「在 coverage 内 **而 `.dat` 里没有它的根**」——**一个缺席**。
> 而「没有根」不止一个成因：崩溃留下的半截、后来的截断、索引写坏、一个 bug。
> **它们全都长成「确认没有」**，一个自信的错答案。
>
> **而这正是我在上一层刚拒绝过的形状**：我用 coverage 把「确认为空」和「没写过」
> 分成了两串字节，**然后在下一层把「确认没有」和「数据丢了」合成了同一串字节。**
> ⇒ **「记号」要的是【缺席不再是一个合法状态】，这一点我上一版没做到。**

> **错二（自然日）**：我举的例子是 `[…20200731], [20200803…]`——
> 而这两天是**相邻的交易日**（周五与周一）。**例子把相邻性按自然日算了**，
> 于是照它实现会**每个周末切一刀**，17 年约 900 段，且「只拉缺失区间」
> 会把每个周末当成洞去拉。
> ⚠️ **这个仓库的第二节就叫「交易日 ≠ 自然日」，而它出现在定义格式那一节的第一个例子里。**

**改后的判定表——缺席从此只意味着损坏：**

| `.meta` 说 | `.dat` 里 | 判定 |
|---|---|---|
| 不在任何区间内 | — | **没拉过** |
| 在区间内，该段 `bars` **与** `days` 都相符 | 有根 | 拉过，**有数据** |
| 在区间内，该段 `bars` **与** `days` 都相符 | 没有根（两个计数记的就是 0） | **拉过，确认没有** ← 正面记号：那两个 `0` 是被写下去的 |
| 在区间内，`bars` **或** `days` 对不上 | — | **坏了。报错，不猜** |
| 在区间内，**这一段还没走查过** | — | **答不了**（见下面「走查在哪一刻发生」）|

> **正面记号是那两个被写下去的计数（`bars` 与 `days`），不是「没有根」这件事。**
> `bars == 0` 是一个**写下来的 0**，和「什么都没写」在字节上不同——
> 这与 `format` 用 `*int` 是同一条：**「值为 0」和「没有值」必须分得开。**

##### `bars` / `days` 到底和**什么**比——这一格必须写死，否则上面那个洞没关上

**判据（写死）：和【一次真正的枚举】比，不和一个算出来的期望比。**

```
bars  ← 按【读者会用的那条路径】把这一段的记录逐条走一遍，数出来的条数
days  ← 同一次走查里，【至少出现过一根】的交易日条数
```

⚠️ **不能拿「文件长度 ÷ 记录长」当 `bars`**，评审方 2026-09-08 给的失败场景：

> 区间 `[A,B]`，`bars = N`，`D` 日确有数据。
> `D` 的起点因为日→偏移映射损坏而找不到了，**而 N 条记录一条没少**
> ⇒ 「文件长度 ÷ 记录长」**仍然等于 N** ⇒ `D` 判成「拉过，确认没有」。
> **上一版那个自信的错答案，原样回来。**

**「长度 ÷ 记录长」抓得住少了/多了/残尾，抓不住「记录都在而读不到」。**
而后者恰恰是本节要防的那一类：**读不到的东西和不存在的东西长得一样。**

⇒ 所以两个计数比的都是**读者视角下真的看见了什么**：
**写入方记下「我放进去多少」，读取方数出「我现在能看见多少」，两者对不上就报错。**
拿一个算出来的期望去比，等于**用同一套假设验证它自己**（同 §14.2 那条：
「跑了自己」和「没跑」给出的全绿长得一样）。

`Days` 的边界仍然照旧：**它说得出「这一段坏了」，说不出「坏的是哪一天」**——
定位需要逐日记，那是第二份表示、会和 `.dat` 漂移。**这一格仍然选不定位。**

##### ⛔ 存储侧的「答不了」有**两种**，必须给区分得开的错误值

这一节写到这里，存储侧已经有了两个「答不了」，**而它们的补救动作完全不同**；
再加上日历那个，调用方手上共有**三**种：

| 「答不了」 | 谁给的 | 补救动作 | 性质 |
|---|---|---|---|
| `ErrUncovered`（已有） | 日历 | **换一份覆盖得到的日历** | 永久 |
| `ErrSpanUnverified` | 存储：这一段还没走查过 | **走一遍**（第二档） | 瞬时，**自动可解** |
| `ErrLegacyMeta` | 存储：`format` 缺失且源不可重放 | **一个显式决定**（`Force` 或人工确认） | 要人 |

```go
var (
    // ErrSpanUnverified 这一段的 bars/days 还没走查过，所以现在【答不了】
    // 「这一天是不是确认没有」。补救：走一遍（第二档）。瞬时，自动可解。

    // ErrLegacyMeta .meta 没有 format 字段（v0.3 之前写的），而这个源不可重放，
    // 所以 coverage 既不能当「已拉过」也不能当「没拉过」。补救：一个显式决定。

塞进一个 `error` 或一句「答不了」，调用方最省事的写法又会是 `if err != nil { … }`——
**而那正是 `contract.md` §5 写过的、会把三种一起吞掉的那一行。**

> **答案的取值空间比问题的答案空间小 —— 本仓第三次。**
> 前两次：`Calendar` 的 `bool`（不是交易日 / 答不了）、
> coverage（没拉过 / 拉过确认没有）。这一次是**三种「答不了」共用一个「答不了」**。

⇒ **判据不变**：先数这个返回值要区分几种情况，**再问这几种在调用点会不会被一个惯用法一次吞掉。**

##### 走查**在哪一刻发生**——不写这一格，那两个计数就只是装饰

评审方 2026-09-08 点的，而他把代价的不对称说清楚了：

```
写 bars/days   免费   写入方本来就知道自己放了多少
验 bars/days   O(n)   要真的走一遍；一条序列 128 万根
```

> **便宜的是写，贵的是验 ⇒ 会被跳过的正是验的那一半。**
> 而「每次打开都走一遍」是一个**每次启动 O(n) 的必过项**——
> 本仓自己登记过它的下场：**一个会红的必过项迟早被加 `|| true`。**

**所以分三档，每一档写明代价和它换来什么：**

| 何时 | 代价 | 检什么 | 不做会怎样 |
|---|---|---|---|
| **每次 `Open`** | **O(1)** | 文件长度 % 记录长（约束三的残尾） | 残尾会被后续追加接在后面 |
| **首次要回答「这一天是不是确认没有」时**，按**段**走查一次，进程内缓存 | O(该段) | `bars` / `days` | —— 见下面那条硬规矩 |
| **`Syncer.Sync` 结束时**，只验**本次碰过的段** | O(本次写入) | `bars` / `days` | 那些段的损坏要等到有人读才发现 |
| **显式命令**（`Store.Verify`） | O(全库) | 全部段 | 见下方「发现时间没有上界」 |

⚠️ **第二档的时机是要害**：走查发生在**给出「确认没有」这个答案【之前】**，
不是发现异常之后。**读到一天没有根 ⇒ 先验这一段 ⇒ 再回答。**

> **而没走查过的时候，这两个计数【什么也不意味着】。**
> 那时不许回答「拉过，确认没有」——**只能答「答不了」**（判定表最后一行）。
>
> 这是本节第一原则的又一次应用：**缺少验证不能悄悄变成一个肯定的答案。**
> 「没验过」和「验过了，是空的」如果都回答「确认没有」，
> 那么加这两个计数**只是把原来那个洞挪了个位置**。

##### ⚠️ 而把三档合起来看：**损坏的发现时间没有上界**

```
Syncer 问的是「哪些【区间】缺」——从不问「D 日有没有根」 ⇒ 它不会触发第二档
第二档只在【有人读到那一天】时才触发
Store.Verify 是唯一会【主动】发现损坏的东西，而它靠人跑
   —— 本仓【没有 CI】（查过：无 .github/、无 Makefile）
```

⇒ **一天的根丢了，它仍在 coverage 里 ⇒ Syncer 不会重拉 ⇒
在有人读到那一天之前，没有任何东西会发现。**

我上一版把第三档「不做会怎样」写成「只是没做全量体检，**不影响正确性**」——
**读到的那一刻确实仍然正确**（会报错或答不了），但那句话**把「发现时间无上界」说成了没有代价**。

**能收窄的部分收窄了**（上表新增那一档）：

> **`Syncer.Sync` 结束时，对本次碰过的段各走一次。**
> 代价是 O(本次写入)——**本来就刚写过它们，数据还在页缓存里**；
> 而它把「正在维护的序列」的发现延迟，从**无上界**变成**一个同步周期**。

**收窄不到的部分写明**：**冷序列**（长期不同步、只偶尔读）仍然无上界，
只能靠 `Store.Verify`。⇒ **建议时机写死为「每次全量重建索引 / 每次换机器搬库之后」**——
**不写「每周」**：那是一个靠人记得的东西，而本仓对「靠人记得」有专门的一类。

**缓存的边界也写明**：缓存只在**进程内**、只对**打开期间没被别的写者动过**的段有效；
写者扩了某一段 ⇒ 该段缓存作废。**跨进程不缓存**——那需要把「验过了」也落盘，
而那是第三份表示，会和前两份漂移。

##### 为什么不取评审方建议的「零长度的根」

他的建议是给「确认没有」写一条零长度记录。**方向对，我换了载体，理由是这份文件的形状**：

- `.dat` 是**定长记录数组**（`offset = i * 88`），**没有「零长度记录」这种东西**；
  能做的是塞一条带 `FlagNoData` 的**哨兵根**；
- 而哨兵根会**污染 K 线流**：每一个消费者都得记得过滤它，
  **忘了过滤就会看到一根不存在的 K 线**——那正是本仓一直在拆的
  「看起来像数据而不是数据」。

⇒ 取**每段一个计数**：不进 `.dat`、不污染流，且**顺带盖住残尾**（见约束三）。

**它的边界，写明**：计数只能说「这一段整体对不对」，**说不出是哪一天丢了**；
也挡不住「根数对而内容错」。⇒ 它把「确认没有 vs 丢了」分开了，**没有**把
「丢了哪一天」定位出来。要定位得逐日记，那是第二份表示、会和 `.dat` 漂移——
**这一格我选了不定位，代价写在这里。**

⚠️ 而这带来下面几条**写入顺序**的硬约束，它们才是这一格的要害：

> **一、`coverage` 只能在数据落盘之后扩大。**
> 顺序反了，崩溃就会留下「声称拉过而其实没有」——**正是最危险的那个方向**
> （第七节那张表第一行：静默漏数据且不会自愈）。
> 反过来（先写数据后扩 coverage）崩溃留下的是「拉过却没记」⇒ 重拉一遍，吵而不丢。

> **二、上游出错时【不许】扩 coverage。**
> 「问了但没问成」和「问了，确认没有」在返回值上可以长得很像
> （空数组 vs 错误 vs 超时后的空响应）。**只有完整成功的响应才允许扩区间。**
> 这是「取不到 ≠ 0」在存储层的同一条。

> **三、打开 `.dat` 时必须校验并截断【未完成的尾部记录】，而截断这件事要进 `SyncReport`。**
> （评审方 2026-09-08 提的，我照收。）
>
> 前两条管的是**两个文件之间**的顺序，它们**不管 `.dat` 自身写到一半**：
> 崩在追加中途 ⇒ 半截记录留在文件尾 ⇒ coverage 没扩（这一格顺序守住了），
> **但下一次追加会落在那半截【后面】**，除非开文件时先检测并截断。
>
> 判据是现成的：`.dat` 是定长记录数组，**文件长度不是记录长度的整数倍 ⇒ 有残尾**。
> 而它和上面那个 `bars` 计数**互为兜底**：残尾会同时让计数对不上，
> ⇒ **一条读不出来的根不会伪装成「确认没有」，它会当场报错。**
>
> **截断必须留声**：`SyncReport.TruncatedTails []string`。同 `LegacyMetaDiscarded` 的道理——
> **自愈动作必须留声，否则它和「本来就没事」长得一样。**

#### ③ 旧文件：**`format` 缺失本身就是那个信号，而它必须内生**

评审方给的约束：

> **「年代说不了」的判据，必须能从【文件自身的字节】读出来**，不能靠外部记录。
> 否则它不是第五态，是一条元数据——**而元数据会丢，丢了之后会静默落回某一态。**

我加的一格：**元数据不只会丢，还会【对不上】**——外部记录说「这份文件是 2026 年写的」，
而文件其实是从别处拷来的旧文件。**丢了会退化成「不知道」，错了会给出一个自信的错答案。**
⇒ 判据必须内生，这条是本节的第一原则。

具体机制：

```go
type meta struct {
    // 指针：分得开【缺失】与【值为 0】。0 是一个合法版本号。
    Format   *int    `json:"format"`
    Coverage []Span  `json:"coverage"`
}

// Span 是一段【交易日闭区间】，外加两个【被写下去的计数】。
//
// ⚠️ 这两个计数不是统计信息，是【正面记号】：
// 没有它们，「拉过确认没有」就只能靠「.dat 里没有它的根」来表示——
// 那是一个【缺席】，而缺席也可能是残尾、截断、索引损坏、一个 bug。
type Span struct {
    From TradingDay `json:"from"`
    To   TradingDay `json:"to"` // 闭区间；相邻性按【交易日】算，不按自然日

    // Bars 是写这一段时【实际落盘的记录条数】。
    Bars int `json:"bars"`

    // Days 是这一段里【至少有一根的交易日】条数。
    //
    // 只有 Bars 不够：记录一条没少而【某一天的起点找不到了】（日→偏移的映射
    // 损坏、首条记录时间戳被写坏）时，Bars 仍然相符，于是那一天读成
    // 「拉过，确认没有」—— 上一版那个自信的错答案原样回来。
    // Days 对不上就报错 ⇒ **缺席重新只意味着损坏。**
    Days int `json:"days"`
}
```

> ⚠️ **第一版这里是 `Coverage [][2]TradingDay`**——它**装不下**上面那个 JSON
> （对象解不进 `[2]TradingDay`，连解码都会失败），**更没有 `bars`**。
> 也就是说：上一轮 (a) 那个修正**只活在散文和例子里，类型里根本不存在**，
> 而照类型实现的人会原样重建那个缺陷。
>
> **散文说服人，类型决定代码。一节格式定义里两者不一致时，赢的是类型。**
> （评审方 2026-09-08 指出。）

| `.meta` 的状态 | 判定 | 为什么 |
|---|---|---|
| 读不到 / 不是合法 JSON | **报错，不猜** | 连「它说了什么」都不知道，任何猜测都是编的 |
| `format` **缺失**（`nil`） | **按 D2 判**：可重放 ⇒ coverage 作废、全按「没拉过」；**不可重放 ⇒ coverage 不作废**，整份标 `unverified`、报告并停 | 这是 v0.3 之前写的文件，**它可能有另一种 coverage 语义**；而怎么处置**不是常数**，取决于 `Source.Caps` 的可重放性 |
| `format` > 当前已知 | **报错，不猜** | 未来版本写的，语义未知 |
| `format` == 1 | 按上面读 | |

> ⛔ **第二行原来写的是「整份 coverage 作废，全区间按『没拉过』」——无条件。**
> 而下面「取决于这个源能不能重放」那一格明写：**不可重放的源 coverage 不作废**，
> 整份标 `unverified`、报告并停。**两处相反。**
>
> 这一行停在了**旧判定**上：判定后来被 `Source.Caps` 那一格细化了，而状态机没跟着动。
> ⇒ **这正是本节开头那张「六处」清单预言的漂移，而且是它自己的第 3 处（判定表）。**
> 发现于 2026-09-08 推导不变量表时 —— **不是读出来的，是把两处判定并排列出来才看见的。**
> **一份清单最先照出来的，往往是清单自己覆盖的那块地方。**


##### `format` 缺失时怎么办：**取决于这个源能不能重放，而那不是我的判断，是 `Source.Caps` 的字段**

⚠️ **我第一版的理由是错的，而错在一个没写出来的前提上**（评审方 2026-09-08）：

> 我写：「『答不了』会让 `Syncer` 停下来；『没拉过』会让它重拉。重拉只是**吵**，
> 停下来要人工介入。**代价不对称，选便宜的**。」
>
> **隐含前提：上游还能把那段重新给你。** 而本仓自己的 `probe.md` 说它不能：
> **新浪分钟线硬顶 1023 根、没有翻页参数**（[坑一](probe.md)），实时接口**已冻结两年**。
>
> ⇒ 一份新浪分钟序列的旧 `.meta` 被作废 ⇒ Syncer 认为十年都「没拉过」⇒
> 而它**永远只能取回 1023 根**；按约束二（上游出错不许扩 coverage），
> 剩下那段**永远停在「没拉过」，每次同步重试一遍，永不收敛**。
> **这不是「吵」，是不收敛。** 而那十年数据一直躺在 `.dat` 里、读得出来。

**所以判定不能是一个常数，它取决于一个可测的性质：**

| 源 | 判定 | 为什么 |
|---|---|---|
| **可重放**（天勤：给定合约与区间可重取） | coverage 作废，全按「没拉过」，重拉 | 吵，但**会收敛**；而重拉能把语义未知的旧记录换成语义已知的新记录 |
| **不可重放**（新浪分钟：1023 根硬顶） | coverage **不作废**，整份标 `unverified`，**报告并停** | 作废在这里换不来任何东西：重拉取不回那段，只会永远重试。而**丢掉那些区间是不可逆的** |

> **「可不可重放」正是 `Source.Caps` / `Capabilities` 要表达的东西**
> （`pending.txt` 里 v0.3 那批已经登记了这两个标识符）。
> ⇒ 这一格**不靠我猜代价，靠源自己声明能力**。

⚠️ 而 `unverified` 的语义要写死，否则它就是第二个 `bool`：

```
unverified 的 coverage：
  【不】当作「已拉过」——否则语义未知的旧记录会让 Syncer 静默跳过（最危险的方向）
  【也不】当作「没拉过」——否则不可重放的源会永远重试
  ⇒ 它是「答不了」：Syncer 报告并停，等一个【显式决定】（`Force` 或人工确认）
```

**「停下来」在这里是对的，而第一版说它错，是因为第一版以为自愈可用。**
**源不可重放时，自愈从来就不在选项里**——那时候「停下来问」不是代价，是唯一诚实的动作。

**两种情况都必须进 `SyncReport`**：
`LegacyMetaDiscarded []string`（作废了哪些）与 `LegacyMetaUnverified []string`（标了哪些）。
否则「重拉了十年」和「本来就该拉十年」长得一样——**不报，它就是一次静默的全量重拉。**

⚠️ **`format` 用指针不用零值**，因为 `int` 的零值是 `0`，而 `0` 是一个合法的版本号——
**「字段没写」和「字段写了 0」在 `int` 上长得一样**。这是 v0.1 那个
`Calendar` 的 `bool` 承载两件事的同一个形状，只是发生在 JSON 解码上。

#### 这一节自己的已知洞

| 洞 | 后果 | 有没有守 |
|---|---|---|
| `.dat` 与 `.meta` 不是原子写的 | 崩在两者之间 ⇒ coverage 与数据不一致 | ⚠️ 靠**顺序**（先数据后 coverage）把不一致压到安全方向，**不是靠原子性** |
| `.dat` 自身写到一半 | 半截记录留在文件尾，下次追加落在它后面 | ✅ 约束三：开文件时按「长度 % 记录长」检出并截断，且 `bars` 计数同时对不上 |
| **某一天的起点读不到，而记录一条没少** | 那一天会读成「拉过，确认没有」 | ✅ `Days`（有根的交易日条数）对不上即报错——**前提是两个计数都和【一次真正的枚举】比**，不和「文件长度 ÷ 记录长」比 |
| **损坏的发现时间没有上界**（冷序列） | 坏了但没人读 ⇒ 没有任何东西会发现 | ⚠️ 只收窄了一半：`Syncer.Sync` 后验本次碰过的段 ⇒ 热序列延迟 = 一个同步周期；**冷序列仍无上界**，只能靠 `Store.Verify`，**而本仓没有 CI** |
| 计数对得上、**内容却是错的** | 「确认没有」与「拉过有数据」仍分得开，但数据本身错 | ❌ 没有。计数说的是「这一段整体对不对」，不是「每一根对不对」 |
| 计数对不上时**说不出是哪一天丢了** | 只能报「这一段坏了」 | ❌ 有意如此：逐日记会是第二份表示，会和 `.dat` 漂移（代价已写在上面） |
| `coverage` 区间可以人手改 | 编一个区间 ⇒ 「确认没有」凭空出现 | ❌ 没有。同 §5「只能靠人」那一类 |
| `format` 只挡版本，不挡**同版本内的语义漂移** | 同是 `format:1` 而含义变了 | ❌ 没有。改语义就必须升 `format`，**而这条只能靠人记得** |

**这一节最该被后来的人读到的是「`format` 挡不住同版本内的语义漂移」那一条**：

> **版本号挡得住「格式变了」，挡不住「格式没变而含义变了」。**
> 所以改这一节的语义时，**升 `format` 是必须动作，不是可选动作**。

#### ⛔ 冲突七单独说：缺口表**漏的不是一格，是一整个维度**

§七 三那张表说得很重：「缺口要区分【四种】，而不是两种、也不是三种」。
**而 `store/segfile` 完工之后，四种也不够。**

`HasBars` 的返回空间**实测有四种**（`store/segfile/store.go`）：

```
(false, nil)  不在任何 coverage 里     ⇒ 第一类「没拉过」              ✅ 表里有
(true,  nil)  走查过，那天有根          ⇒ 不是缺口                     ✅
(false, nil)  走查过，那天没根          ⇒ 第二类「拉过，确认没有」      ✅ 表里有
(false, ErrSpanUnverified)            ⇒ **这一段还没走查过，答不了**   ⛔ 表里【没有】
```

再加上 `.meta` 那一侧的 `ErrLegacyMeta`（D2a：版本未知且源不可重放 ⇒ 需要一个显式决定），
**存储侧一共有两个「答不了」，而缺口表一格都没给它们。**

⚠️ §6.1 有一整节叫「**存储侧的「答不了」有两种，必须给区分得开的错误值**」——
**两张表，一张知道，另一张不知道。** 而它们描述的是同一次判定。

> ⇒ **这不是「漏了一格」，是「漏了一整个维度」。**
> 前四类都在回答同一个问题：**这一天该不该拉**。
> 而这两类说的是另一件事：**我答不了这个问题。**
> **「答不了」不是那个答案里的一个取值，它是【答案缺席】本身。**
>
> ⇒ 本仓记过的那条在这里第三次应验：
> **「我列了 N 格」该问的是「我是不是漏了一整个维度」，而不是「N 对不对」。**
> 前两次是 `Capabilities.Depth`（问的是密度，毛病在维度）
> 与 `Capabilities.Since`（一个数不是关于那个品种的）。

⇒ **缺口是【六】类，不是四类。** 而新增的两类必须分开，因为**处置不同**（同⑱）：

```
存储答不了·未走查   ErrSpanUnverified  瞬时、自动可解 ⇒ **走一遍就行，不必问人**
存储答不了·旧格式   ErrLegacyMeta      需要一个【显式决定】 ⇒ **必须问人，机器不许替他答**
```

⚠️ 而「六」这个数**同样没有证据说它就是全部**。§七之六那一格已经写过：
**「一共就这些」这句话，至今每被审一次就掉一次**。
⇒ 所以这里只写**已验的那一句**：**六类各自站得住（每一类都有一条能单独触发它的输入）；
「一共就这六类」未验。**

## ⛔ 而这四个空间里，**第四个不封闭** —— 这一刀决定了它只能兜底

```

> ⇒ 判据：**说「一共就这几类」之前，逐维问「这一维封不封闭」** ——
> **封闭的可以枚举，不封闭的只能兜底；混在一起数，数出来那个 N 一定是错的。**

⇒ 所以「六类是完全的」这句话要**拆成两句**，不能合成一句：

```

一维兜底   写明它【为什么】不能被枚举（OS 错误空间）    ⇒ 这一半只能声明射程
```

⚠️ 顺带一个实测，它让「开集」这句话更准：**「解码坏了」这一支今天一行代码都到不了。**
`dayHasRecords` 里 `buf := make([]byte, RecordSize)`，而 `DecodeBar` 唯一的错误是
「记录不足 `RecordSize` 字节」⇒ **恒不触发**。

⛔ **而这句话的射程比事实【窄一格】**（评审方 2026-09-09 指出，我复核一致）：
`DecodeBar` 的生产侧调用方**是 2 个**（`store.go` 的 `Verify` 与 `dayHasRecords`），
**两个的 `buf` 都是 `make([]byte, RecordSize)`** ⇒ 那条错误**全仓不可达**，
不只是「在 `dayHasRecords` 里」不可达。
⇒ 判据：**写「在 X 里不可达」之前，数一遍 X 有几个兄弟** ——
`grep` 一次调用方比读一个函数贵不了多少，**而它决定这句话是【局部】还是【全仓】。**
⇒ 而收窄之后这一维的理由更干净：

⇒ 今天活着的「坏了」**只有 `Stat` 与 `ReadAt` 两个 OS 错误** ——
**而 OS 错误空间恰恰是这四维里最不可枚举的那一种。**

```go
func (s *Syncer) Sync(ctx context.Context, req SyncRequest) (SyncReport, error)

```go
type SyncRequest struct {
    Symbol Symbol
    Period Period         // 封口接口，见 source.go；IntradayPeriod 与 CalendarPeriod 都装得下
                          // ⛔ 原来写的是 `IntradayPeriod`——那个类型【装不下 Daily】
                          //    （Daily 是 CalendarPeriod），而 Daily 是今天唯一同步得了的周期。
                          //    见七之零冲突一。
    From   TradingDay     // 起始交易日，必填
    To     TradingDay     // 0 表示到最后一个已收盘的
    Force  bool           // 忽略 coverage 强制重拉该段
}
```

读 `Meta.Coverage`（交易日区间）→ 求缺失 → 只拉这些 → 落库 → 合并 coverage。

`Force` 有两个正当用途：**交易所修正了历史结算价**，以及
**上游抖动被固化成「确认无数据」**——后者不重拉就会永久留一个不该存在的空洞。

三条本库特有的规则：

**一、区间末端截到「最后一个已收盘的 K 线」，而这需要交易日历。**
姊妹项目里这是 `now - step`，一行算术。这里必须问日历：
当前时刻属于哪个交易日、那个交易日的这个周期有哪些边界、哪一根的
`Close` 已经过去。**新浪会把还在累积的那根一并返回并标上未来时刻**
（[probe.md 坑四](probe.md)），不主动挡就会存进去，而且此后再不会去补。

**二、`Report` 要报「对不上网格的根数」，并且【扫 `BarBound.Anomalous`】。**

上游给的每一根，其 `Ts`/`TsEnd` 都应当落在 `Period.Bars(tmpl, d)` 算出的边界上。
不为零就说明**时段表与实际对不上**——多半是交易所改了夜盘而内置表没跟上。

⚠️ **必须扫 `Anomalous`，而不是自己再判一遍**：v0.1 里那个标志一度
挂在周期上（`nightCarried > phase`，两个取模后的余数相比），于是同一个
「标称 330 / 实际 310」的事实在 15m/30m 报、5m/60m/90m 不报。
现在它由 `Day.TemplateMismatch` 按**交易日**判、那天每一根都带——
**上层只要扫这一位就不会按周期漏**。自己另写一套判定，就是把那个坑重挖一遍。

**三、缺口要区分【六种】。**

⚠️ 这一句原来写的是「**四种**，而不是两种、也不是三种」。
`store/segfile` 完工后逐条对了一遍：**四种也不够** —— 存储侧还有两个「答不了」
（`ErrSpanUnverified` / `ErrLegacyMeta`），而它们**不是这四类里的取值，是【答案缺席】本身**。
见七之零冲突七。下表前四行是原表（每一行的方向都是量出来的，不动），后两行是补的。

| 情形 | 真值来自 | 姊妹项目 | 本库 | **最危险的错认**（方向要写明） |
|---|---|---|---|---|
| 没拉过 | coverage | ✓ | ✓ | 当成「拉过确认没有」⇒ **静默漏数据，且不会自愈** |
| 拉过，确认没有 | coverage | ✓ | ✓ | 当成「没拉过」⇒ 每次都重拉一段确实没有的区间（吵，但不丢数据） |
| 不是交易日 / 不在交易时段 | **日历** | 不存在 | ✓ | 当成「没拉过」⇒ 永远重拉一段**不存在**的区间 |
| **日历答不了**（`ErrUncovered`） | **日历的覆盖边界** | 不存在 | **✓ 第四类** | 当成「不是交易日」⇒ **静默跳过整段历史** |
| **存储答不了·未走查**（`ErrSpanUnverified`） | **存储**（B3） | 不存在 | **✓ 第五类** | 当成「拉过确认没有」⇒ **把「没验过」升级成一个肯定的答案** |
| **存储答不了·旧格式**（`ErrLegacyMeta`） | **存储**（D2a） | 不存在 | **✓ 第六类** | 与第五类合并 ⇒ 「重跑一下就好」被用在一个**需要人拍板**的格子上 |

> ⚠️ **这一列必须逐行写明方向**。上一版的表头是「错认成『不是交易日』的后果」，
> 而第二行填的是「永远重拉」——那是把**「不是交易日」错认成「没拉过」**的后果，
> **方向反了**。把「拉过确认没有」当成「不是交易日」其实无害（本来就该跳过）。
>
> 这一格要紧，因为**这张表是 v0.3 分类逻辑的规格书**：
> 照着它实现的人会去防一个方向，而表里那一格指的是另一个方向。
> ⇒ **一个统一的列头，会把每行各不相同的方向抹平成一个。**
> 这和「一个数字盖住三件事」是同一个形状，只是发生在表头上。

第三类在加密市场根本不存在。混进第二类的话，`Gaps` 会把每个周末、
每个午休、每个春节都列成「数据缺失」——**一份全是噪声的告警等于没有告警**。

**第四类是 v0.1 之后加的**，因为它在 `Calendar` 那个 `bool` 里和第三类塌缩过：
内置模板自 `2020-05-06` 生效，而新浪 `RB0` 日线自 `2009-03-27` 起——
**中间十一年日历全答「不知道」**，读成「不是交易日」就会静默跳过日线
最值钱的那一段。

> 两条同构的话，放在一起记：
>
> - **「没拉过」和「拉过确认没有」在存储层长得一样** ⇒ coverage 必须记**区间**，不能只记「有哪些根」；
> - **「不是交易日」和「日历答不了」在 `bool` 上长得一样** ⇒ `Calendar` 返回**区分得开的错误**。
>
> 两条都是**答案的取值空间比问题的答案空间小**。

**四、`SyncReport` 必须带「请求区间 vs 日历覆盖区间」两行。**

```go
type SyncReport struct {
    Requested [2]TradingDay // 请求的闭区间
    // Covered 是日历【能回答】的闭区间（Calendar.Covers）。
    // CoversOK 为 false 表示【整个品种】日历都答不了——那时 Covered 无意义，
    // 不能填 [0,0]：一个零值区间读起来仍然像一个区间。
    Covered   [2]TradingDay
    CoversOK  bool
    Synced    [2]TradingDay // 实际同步到的

    Bars       int
    Misaligned int // 边界对不上网格的根数

    // AnomalousDays 是【模板与实际矛盾】的交易日，**不是根数**。
    //
    // 写成根数是错的，而且错法有名字——那就是 K1 在报告层复发：
    // 那个标志由 Day.TemplateMismatch 按【交易日】判、那天每一根都带，
    // 于是按根数计就是「天数 × 每天根数」，**同一个事实在 60m 给约 30、
    // 在 1m 给约 1650**。标志本身修到了交易日一级，计数又把它挂回周期上。
    //
    // 而且报告是给人看的：人问的是「哪几天的数据可疑」，
    // 不是「有多少根带了这一位」。给日期，直接可行动。

**五、序列级的「永久取消夜盘」检测。**

```

#### ⛔ 量了（2026-09-09）：**长假的答案是 1，而没有任何 `N` 是对的**

### 七之七、限流、分块与失败预算

#### ⛔ 先纠一句话：「限流属于调用方」是对的，但它把闸门装在了看不见请求的那一层

`cffexsource` 写着「本层不自己限流，因为限流策略属于调用方」。
调用方就是 `Syncer`。**而 `Syncer` 看不见 HTTP 请求**：

```
Source.Bars(ctx, req) 是【一次调用】，而它内部发几次请求，随源而变——
  sinasource   一个合约的全部历史 = **1 次**
  cffexsource  要 N 个交易日      = **N 次**
⇒ 站在 Syncer 上，这两者【长得一模一样】
```

> **一个词（「限流」）盖住了两件事：谁定【多快】，和谁按【那个闸门】。**
> 策略确实属于调用方；**而闸门只能装在发请求的那一层。**
> ⇒ 分开说，两句都成立：**策略在 `Syncer`，闸门在 `http.RoundTripper`。**

⇒ 落地：本仓给一个现成的限流 `RoundTripper`（新包 `source/pacing/`），
由 `Syncer` 造好、经 `WithHTTPClient` 交给源 —— 这正是 `cffexsource`
注释里已经指的那条路。**不给现成的，每个调用方会各写一个，而那是四份会各自漂的实现。**

⚠️ **本层【不】设「不限流」这个默认。** 零值可用的话，一个忘了配的调用方
会用满速打中金所官网 **2671 次**，而**没有任何东西会拦**。
⇒ 构造时必须显式给，库里同时提供 `NoPacing()` ——
**一个具名的「我不限流」是一个看得见的选择；一个零值不是。**
（同 `segfile.Outcome` 零值不合法、`cffexsource.New` 缺日历即报错、SRC-11 无默认 secret。）

#### 分块：一次 `Bars` 调用就是一次 coverage 提交单位

`cffexsource.Bars` 中途失败即中止、不返回半截（理由见那边：半截会被 coverage
记成「拉过、确认没有」）。⇒ **把 2671 天一次性交给它，第 2670 天失败 = 全白干。**

⇒ 所以 `Syncer` 必须切块，而**块大小是【源的性质】，不是调用方的偏好**：

```
sinasource   切成一天一块 ⇒ 2671 次「拉全部历史」——不是浪费，是不可用
cffexsource  不切         ⇒ 一次失败丢 2671 天
⇒ 同一个默认值，对两个源一个不可用、一个很贵。**跨源的默认值不存在。**
```

⇒ **`Capabilities` 缺一格**（我们自己的类型，加一格比让 `Syncer` 猜便宜）。
⚠️ 它**落在丙那一片**，不落在本片：甲乙一个字都用不到它，而加这一格要动两个源。
本片只把它写进规格 —— 而「写进规格」在本仓的意思是**它同时进 `pending.txt`**，
否则 doccheck 连「尚未实现」都不会报它（冲突四那一格的教训）：

```go
// BatchDays 是这个源【一次请求最好覆盖多少个交易日】。
//
//	sinasource   一次请求 = 一个合约的全部历史 ⇒ BatchDaysUnbounded
//	cffexsource  一次请求 = 一天的全部合约     ⇒ 1
//
// ⛔ 零值【不合法】。登记⑫ 那一格的教训：`MaxBars: 0` 同时是
// 「没有硬顶」和「一根都给不了」，两者不可分辨 —— 于是**忘了填查不出来**。
// 这里把「不必切」写成一个【具名常量】，就是为了让它和「忘了填」分得开：
// **一个具名常量说「我想好了」，一个 0 说不清是「想好了」还是「忘了」。**
BatchDays int
```

```go
// BatchDaysUnbounded 表示「区间对这个源不构成代价，整段一次拿」。
const BatchDaysUnbounded = -1
```

#### 失败预算：单次失败跳过，**连续** K 次才停

分块提交让「跳过一块继续走」变成**安全**的：留下的洞就是第一类缺口（没拉过），
**而第一类缺口会被重拉**。⇒ 所以判据不是「丢多少」，是「留下的状态安不安全」。

那为什么还要停？**因为吵。** 上游宕机时不停，一次宕机会变成 2671 次请求。

⇒ 判据取**连续失败**，而这一条的形状本仓已经量过一次：

> **一次抖动和一次宕机，在【第一次失败的时候】是同一件事 —— 区别只在【后来会不会恢复】。**
> 而「连续 K 次」这个判据**等到了「后来」**，所以它成立；
> 「累计 K 次」不成立，因为它把整段历史里散落的抖动加起来当成一次宕机。
>
> ⚠️ 这与 §七 五那条**结论相反而形状相同**：那里「持续 N 天」不成立，
> 因为判据在下判断的那一刻拿不到「后来」；这里拿得到（K 次就在眼前）。
> ⇒ **同一个形状，答案取决于「后来」到没到。** 那才是判据，不是「用不用持续量」。

⇒ **K 不设默认，由调用方给**，而理由与 `BatchDays` 恰好相反，两者的分界写死：

```
源的性质    ⇒ 进 Capabilities   （BatchDays：这个源一次请求覆盖多少天）
环境的性质  ⇒ 进 SyncRequest    （K：网络多差、能容忍多久 —— 那确实是调用方的事）
```

⚠️ **K 的取值本仓没有实测分布**（对比：§七 五那个阈值 2 是十年 2595 个交易日量出来的）。
⇒ 所以这里**不给推荐值**。给一个没有量过的推荐值，
下一个人会把它读成「量过的」——**本仓已经在 `maxFetchFails = 2` 上栽过一次同族**。

### 七之九、甲：`PlanGaps` —— 六类缺口的分类器，**纯函数**

```go
// SpanStatus 是【存储对一段 coverage 的答复】：这一段在哪，以及它答不答得了。
//
// ⛔ 把 Span 与它的可答性放在一起，是因为**分开传就一定会错位**：
// 两个切片、两套下标，而错位之后每一天的类别都变了，且没有任何东西会响。
type SpanStatus struct {
	Span Span

	// Err 是这一段的可答性。nil / ErrSpanUnverified / ErrLegacyMeta。
	//
	// ⚠️ **别的错误值一律当成「坏了」** —— 见 PlanGaps 的兜底那一段。
	Err error
}
```

```go
// PlanGaps 把请求区间按【六类缺口】分好。
//
// ⛔ **纯函数**：日历、coverage、以及「这一天有没有根」全部由参数给，
// 内部不取时钟、不碰网络、不开文件。
// ⇒ 这是甲能排在 `Store` 接口【之前】的全部理由（见七之八）。
//
// hasBars 回答「这一天在 .dat 里有没有记录」。它是一个参数而不是一个接口，
// 理由是**测试要能一行造出六类里的任何一类**；实现方把 `Store.HasBars` 包一层即可。

⛔ **这个签名在文档里写成【一行】，而那不是排版偏好** ——
`doccheck` 的 `parseFunc` 只认单行签名：写成折行的形式，**它一处都收不到**
（2026-09-09 实测：折行版 `-list` 里 `PlanGaps` 命中 **0**，`SpanStatus` 三项照常收到）。
⇒ 于是那个声明会**既不在守卫视野里、也不在白名单里** —— 与 `Gap` 那次同族：
**声明真的存在，而登记看不见它。**
⇒ 处置取「让它被守住」而不是「让它好看」（同 `docs_guards_test.go` 那条守卫的选址）；
**而 `doccheck` 认不认折行签名，是它自己的一个洞，记在这里，不在本片修。**

#### 它按七之零那棵划分树走，而**顺序是判据的一部分**

```
一  先与 Covers() 求交
     交集之外 ⇒ GapCalendarUnknown（冲突五的处置：不让 Walk 炸，而是把它列出来）
     ⛔ 求交必须在最前面：放后面的话，越界那几天会先被 coverage 判成「没拉过」
二  交集内逐日走 Walk
     Walk 只遍历交易日 ⇒ **第三类是「被跳过的那些天」，不是它报出来的东西**
     ⇒ 所以要拿【自然日区间】与【Walk 走过的天】相减才得到 GapNotTrading
三  每个交易日，按 coverage 定位
     不在任何 Span 内           ⇒ GapNeverFetched
     在某 Span 内且 Err != nil  ⇒ 按哨兵分：ErrSpanUnverified / ErrLegacyMeta
     在某 Span 内且 Err == nil  ⇒ 问 hasBars
                                    有 ⇒ 不是缺口
                                    没有 ⇒ GapConfirmedEmpty
四  hasBars 返回的错误【不是缺口】⇒ **整段中止并返回它**（兜底，见冲突八）
```

⛔ **第二步那句「相减」是这一层最容易写错的地方，写死在这里：**

> `Calendar.Walk` **只把交易日交给回调**。于是「不是交易日」在它的输出里是一个**缺席**，
> 而本层要报的是一个**区间**。
> ⇒ 必须拿区间与「走过的天」相减 —— **而这正是⑨ 那一格的形状**：
> **「日历说有、数据没给」与「日历本来就没说有」，在一个只看回调的循环里长得一样。**

#### 六类各一条能单独触发它的输入（这是甲的验收标准，不是测试清单）

```
GapNeverFetched     日历覆盖内的交易日 · cov 为空                      ⇒ 第一类
GapConfirmedEmpty   同上 · cov 覆盖该日且 Err==nil · hasBars 给 false  ⇒ 第二类
GapNotTrading       区间里夹一个非交易日（Walk 跳过它）                 ⇒ 第三类
GapCalendarUnknown  请求区间的一端落在 Covers() 之外                    ⇒ 第四类
GapStoreUnverified  cov 覆盖该日 · Err = ErrSpanUnverified             ⇒ 第五类
GapStoreLegacy      cov 覆盖该日 · Err = ErrLegacyMeta                 ⇒ 第六类
兜底                hasBars 返回一个不是上述哨兵的错误                  ⇒ **返回 error，不返回缺口**
```

> ⚠️ **「各一条能单独触发」是【必要】不是【充分】**：它保证六类各自可达，
> **不保证分类器把边界划对**。边界要另外造 —— 相邻两类的**交界样本**，
> 例如「Span 恰好覆盖到 to 的前一天」「区间恰好等于 Covers()」。
> ⇒ 这一句写在这里，是因为「六类各一条、全绿」读起来非常像「分类器对了」。

#### 甲**不做**的三件事，写下来让「没做」和「做漏了」分得开

```
一  不判「这一天要不要重试」—— 那是 ㉒ 的减法（未上市/已到期由上市日、到期日减掉），
     而上市日在 refdata（v0.4）。甲只报「它属于哪一类」。
二  不跨类别合并。相邻且【同类】要合（见下一格），**不同类绝不合**。
三  不碰限流、不碰分块、不发任何请求。那些在丙。
```

#### ⛔ 改一条：`PlanGaps` 的输出是请求区间的一个【划分】

上一版这一节写着「**不合并相邻的同类缺口** …… 合并会把『连续 N 天』这个 ⑨ 要用的形状抹掉」。
**写实现时它站不住，两处都站不住：**

```
一  不合并 ⇒ 每个 Gap 都是一天 ⇒ **Gap 是个区间类型就没有意义了**
    而同一节上面刚写过「用区间而不是逐日列表：一段十一年的『日历答不了』
    列成逐日是约 2700 行噪声」—— **两句话互相打架，同一节里**
二  那个理由是反的：**合成【段】正是「连续 N 天」那个形状本身**，
    不合并才是把它拆碎（⑨ 要的是「连续多少天」，而那就是段的长度）
```

⇒ 改成一句能被断言的话：

> **`PlanGaps` 返回的，是请求区间在【自然日】上的一个划分 ——
> 不重叠、不留白、按类别分段。相邻且同类 ⇒ 合成一段；不同类 ⇒ 绝不合并。**

⇒ 而这句的价值不在措辞，在**它可以被机器验**：
```
断言一  把返回的段按 From 排序，逐段首尾相接 ⇒ **不重叠、不留白**
断言二  相邻两段的 Kind **必不相同**（相同就该已经合了）
断言三  首段 From == 请求 from，末段 To == 请求 to
⇒ 这三条比「六类各一条」强得多：**它们对【任何】输入都成立，而不只是六条样例**
```

⚠️ **「按自然日相邻」而不是「按交易日相邻」，这一格是有代价的选择：**
```
按交易日相邻  周末两侧的 GapNeverFetched 会合成一段 ⇒ 段更少
              ⛔ 但那一段会【盖住】中间那个 GapNotTrading ⇒ **两类重叠，划分性质没了**
按自然日相邻  周末自己成一段 ⇒ 段更多（一年约 52 个周末段）
              ✅ 而划分性质成立 ⇒ **调用方筛 GapNeverFetched 就是「我该拉哪几天」，一行**
```
> ⇒ 取后者。**噪声可以靠筛，重叠不能靠筛** ——
> 而「相邻性按交易日算」那条（`Span` 的 A2）管的是 **coverage**，不是缺口：
> **coverage 说的是「拉过什么」，缺口说的是「这一段是什么」，两者的相邻性口径本来就不该相同。**

⚠️ **第四类的端点是【自然日】，不是交易日** —— 这一条必须写明：
> 日历答不了那一段 ⇒ **「哪天是交易日」在那一段里没有答案**
> ⇒ 它的端点只能取自然日（请求端点，或覆盖边界的自然日前/后一天）。
> **其余五类的端点都是交易日**（它们都在 `Walk` 走过的范围里）。
> ⇒ 而这条非对称**不是瑕疵，是那一类的定义带来的** —— 写下来，免得下一个人去「统一」它。

## 八、主力连续与换月拼接：本库相对姊妹项目最大的增量

姊妹项目明确写了「交割合约换月拼接——**不做**」，理由是永续合约没有到期日。
**中国期货每个合约都有交割月，这里不做就等于没做。**

### 为什么两个免费源的主连都不能直接用

**新浪 `RB0`**（[probe.md 第四节](probe.md)）：未复权。2026-08-28 → 08-31 换月那天，
`RB0` 显示 **+2.73%**，而实际持有 `RB2610` 是 **+1.00%**、`RB2701` 是 **+1.23%**——
凭空多出 **1.5–1.7 个百分点**（是个区间，取决于你持的是哪一个合约；
只报上界就是把区间悄悄收成最好看的那一头）。

**天勤 `KQ.m@SHFE.rb`**（[probe.md 6.5](probe.md)）：**同样未复权，而且更坏**。
它在 **09-02** 换月（**比新浪晚两天，换月规则不同**），那天：

| | 09-01 → 09-02 |
|---|---|
| `KQ.m@SHFE.rb` 显示 | **+0.61%** |
| 真实 `rb2610` | **−1.02%** |
| 真实 `rb2701` | **−1.01%** |

**两个真实合约都跌约 1%，主连却显示涨 0.61%——连符号都反了。**
新浪那次是把涨幅放大，这次是把一根阴线变成阳线。

两条推论：

1. **两个免费源的主连都未复权**，所以复权必须自己做，这不是「可选的增强」；
2. **它们连换哪天都不一致**，所以**不能互相当对照**。要对账只能与
   **合约级序列**对，那才是唯一的真值。

序列看上去连续平滑、毫无标记。螺纹钢一年换月 3–6 次，17 年上有上百个这样的接缝。

### 设计

```go
type ContinuousSpec struct {
    Product string       // "SHFE.rb"
    Roll    RollRule     // 怎么换月
    Adjust  AdjustMethod // 怎么复权
}

type RollRule interface {
    // Pick 在给定交易日，从候选合约里选出主力。
    Pick(day TradingDay, cands []ContractDay) (symbol string, ok bool)
}
// 内置：ByOpenInterest / ByVolume / ByOIAndVolume（两者都最大才换）/
//       FixedDaysBeforeExpiry(n)

type AdjustMethod int
const (
    NoAdjust   AdjustMethod = iota // 不复权（= 新浪 RB0 的口径）
    RatioBack                       // 后复权·比例
    RatioFwd                        // 前复权·比例
    DiffBack                        // 后复权·价差
    DiffFwd                         // 前复权·价差
)
```

产出**不只是拼好的序列，还有接缝**：

```go
type Continuous struct {
    Bars  []Bar
    Rolls []Roll
}

type Roll struct {
    Day       TradingDay // 换月发生在哪个交易日
    From, To  string  // 旧合约 → 新合约
    Basis     float64 // 换月当日两个合约的价差（基差）
    Factor    float64 // 复权因子
}
```

**接缝必须交出去。** 回测引擎需要知道哪几天的收益来自换月而不是行情，
以及换月本身是要付成本的（平旧开新，两笔手续费加两次冲击成本）。
不给接缝，下游就只能假装换月不存在。

### 三条容易踩的

**一、默认用后复权，前复权要显式选，且会警告。**
前复权以最新价为基准，于是**每换一次月，全部历史价格都会变**。
同一段历史、同一个策略，今天跑和下个月跑**结果不同**——而且不报错。
这对「回测可复现」是致命的。后复权以最早为基准，历史一经生成就不再变。

**二、复权只动价格，不动成交量与持仓量。**
量是手数，没有复权的含义。库里有测试锁住这一条。

**三、复权后的价格【不是可成交价格】。**
后复权序列的绝对价位是虚构的（螺纹钢后复权到 2009 年基准可能是几万点），
**用它算手续费、保证金、涨跌停一律是错的**。
所以 `View` 同时给两套：

```go
v.Close()      // 复权后的价格 —— 拿去算指标、发信号
v.RawClose()   // 真实合约的真实价格 —— 拿去下单、算钱
v.Contract()   // 这一根实际是哪个合约
v.IsRollDay()  // 今天是不是换月日
```

**这是本库对下游最重要的一条约定**：**信号用复权价，成交用真实价。**
只给一套的库，会逼使用者在两种错误里挑一个。

## 九、指标

接口与实现直接沿用姊妹项目的设计（`Name` / `Fields` / `Warmup` / `Update` /
`Reset`，加可选的 `Settler`），因为那一套已经被两套口径、三层测试、
真实行情 golden 验过，没有理由重来。

三处需要改：

**一、口径默认值要重新实测。** 姊妹项目实测 OKX 平台用 CN 口径，
默认改成了 CN。**国内期货软件（文华、博易、快期）用哪套，本库尚未实测**，
在验之前**不设默认**——构造指标时必须显式给口径，缺省报错。
这比拍一个默认值然后写进文档要诚实。

**二、指标要能吃持仓量。** 中国期货有一类以持仓量为输入的指标
（增仓/减仓、持仓量变化率），而姊妹项目的 `Update(c Candle)` 里没有这个字段。
接口改成 `Update(b Bar)` 即可，`Bar` 里什么都有。

**三、「有定义」不等于「已收敛」这条照搬。** 姊妹项目实测
MACD(12,26,9)/CN 的 `Warmup()` 报 1 而实际要 428 根才逐位收敛，
只预读 4 根时值错一倍。**这是递推本身的性质，与市场无关**，直接适用。
`Feed` 的自动预热按 `Settle` 算，`View.Ready()` 按「已收敛」判。

## 十、Feed 与视图

形态与姊妹项目一致（主周期步进、辅周期只给最后一根已收盘的、列式环形缓冲、
`View` 是值类型句柄、无效视图给 NaN 不给 0）。

本库特有的三条：

**一、辅周期的「最后一根已收盘」要问日历。**
姊妹项目是 `extra.LastClosed(base.Next(t))`，一行算术。
这里 `LastClosed` 必须遍历交易日的时段表。语义不变，代价变了。

**二、日线的可见性有个专属的坑。**
主周期是 15m、辅周期是 1d 时，**当天的日线要到 15:00 收盘才可见**。
但夜盘属于**下一个**交易日——21:00 的那根 15m 已经属于 T+1，
此时 `TF("1d")` 应当给 **T 日**那根（刚收盘的），而不是 T-1。
这个跳变发生在 15:00 而不是午夜，很容易写错，**双向测试必须覆盖它**
（不能超前：给的那根必须已收盘；不能落后：下一根必须还没收盘）。

**三、主连模式下 `View` 多四个方法**（见第八节）：
`RawClose` / `Contract` / `IsRollDay` / `Basis`。

## 十一、实时

```go
f, _ := tickflow.NewFeed(nil, cfg)   // store 传 nil 即纯实盘形态
f.Push("5m", bar)
```

与姊妹项目相同的理由：实盘与回测共用同一套指标/视图代码，
省掉「回测跑通了实盘对不上」这类最难查的问题。

本库特有的约束：

- 推入的 `Ts`/`TsEnd` **必须落在 `Period.Bars(td)` 算出的边界上**，否则报错。
  实盘里重复推送与乱序推送都真实存在，静默接受会让指标悄悄算错。
- **实时源必须实现冻结自检**（见第五节）。新浪的教训在前。
- 交易日切换（15:00 之后、21:00 夜盘开盘）时 `TradingDay` 要跟着跳，
  这一步不能靠墙钟推，要问日历。

v1 的实时源是 `source/shinnysource`（天勤，需免费快期账户）。
**2026-09-07 已实测打通**：鉴权、名称服务、websocket、K 线拉取全部跑通，
深度 890,231 根 1m（回溯到 2016-01-04），盘中能拿到当前正在走的那根。

**仍未验的一条最要紧**：未完结的那一根在 DIFF 协议里**有没有标志位**。
天勤若像 OKX 那样给一个 `Confirm`，判完结就能省掉查日历这一步；
没有的话仍然只能靠日历。这一条在写 `shinnysource` 之前必须先问清楚，
否则会写出一个「盘中把半根 K 线当成完整根」的实现——而它不报错。

## 十二、与下游对接：futures-position-simulator-go

姊妹仓 [futures-position-simulator-go](https://github.com/dream-until-dawn/futures-position-simulator-go)
（根包 `futsim`）是中国期货的**持仓与结算内核**。回测引擎的形状是：

```
futures-tickflow-go ──视图──> 回测引擎 ──成交/结算──> futures-position-simulator-go
      （本库）                                              （记账）
```

两个上游各自独立，但**口径必须在设计阶段就对齐**——否则回测引擎夹在中间，
每一步都要translate 一层，而那一层是纯粹的浪费，还是个出错点。

以下是 2026-09-07 直接读它的仓库（`README` / `design.md` / `cn-futures-rules.md`
与 `testdata/probes/*.json`）之后，对出来的结果。**标「待定」的是已经发过去、
等它回复的**。

### 12.1 合约代码：这是唯一一处真冲突

实测两边的年月位数：

| | CZCE | SHFE / DCE / INE / CFFEX |
|---|---|---|
| 天勤 openmd（它的 oracle 那一侧） | **3 位** `CZCE.CF609`（671 个合约无一例外） | 4 位 |
| 新浪（本库的历史数据源） | **必须 4 位** `TA2701`；`TA701` 返回 `null` | 4 位 |

它的 `cn-futures-rules.md` 记的是 CTP 口径的三位，并且自己点出了那个歧义
（`AP610` 既可以是 2026-10 也可以是 2036-10）。

**本库必须用 4 位**：要覆盖 2009 年至今 17 年，三位码跨十年分不清；
且上游只认四位。所以规范形式是 `CZCE.TA2701`。

**解决放在本库这边**，`Symbol` 同时给出两种形式：

```go
sym.String()     // "CZCE.TA2701"  规范形式：无歧义，内部与落盘用
sym.Native()     // "CZCE.TA701"   交易所 / CTP 线格式，给下游
sym.Exchange()   // "CZCE"
sym.Instrument() // "TA701"        与 futsim 的 instrument_id 同构

// 三位 → 四位，以【该数据所属交易日】为锚，不以「现在」为锚
func ParseNative(exch, instID string, asOf TradingDay) (Symbol, error)
```

> **锚点必须是数据自身的交易日。** 以「现在」为锚的话，同一段历史数据
> 在不同年份跑出不同结果——那是个跑一年才会发现的静默错误。

### 12.2 本库能直接供给它、而它当成负担的两样

**一、当日结算价。** 它的 `design.md` 写着「结算价……**无法从 K 线推出**，
必须由调用方在结算时显式给出」。前半句对，但**新浪日线白给**：字段 `s`，
`RB0` 自 2009-03-27 起 4237 根全有，六个交易所都覆盖。所以 `Bar.Settle`
可以直接喂它的 `Settle()`，回测引擎不必另找一个源。

**边界**：这是**当日结算价**，不是**交割结算价**（各所规则不同，股指是最后
两小时算术平均）。交割结算价本库不提供。

**二、交易日历与交易时段表。** 它明写「**本库不推算交易日，它由日历数据给出**」，
而本库正好在造这个（第二节）。**这块两边在重复建设。**

因为依赖约束（见 12.4）两边不能互相 import，所以提案是**本库生成 JSON，
它 `go:embed`**——零代码耦合：

```json
{"exchange":"SHFE","product":"ag",
 "templates":[{"from":20160104,"to":20200324,
               "day":[["09:00","10:15"],["10:30","11:30"],["13:30","15:00"]],
               "night":[["21:00","02:30"]]}],
 "days":{"20260506":{"sessions":[["09:00","10:15"],...]}}}
```

`templates` 是**标称**模板（带生效区间，算相位用），`days` 是**逐日实际**
（停夜盘那天就是少一段）。**两层不能合并**——这是第二节被实测逼出来的结论，
而它那边目前只有「区间模式」这一层。

### 12.3 `Settle` 的触发时机：用 `TradingDay` 变化

它的 `Advance(bar)` / `Settle(settlement)` 是两个动词，且
「一个交易日可能横跨三个自然日（周五夜盘 → 周六凌晨 → 周一日盘），中间没有结算」。

本库每根 `Bar` 都带 `TradingDay`，所以契约可以简单到一行：

```go
if bar.TradingDay != prev.TradingDay {
    sim.Settle(...)   // 先结上一日
}
sim.Advance(bar)
```

**回测引擎因此不需要自己判交易日边界**——那正是它担心「漏掉或重复执行，
后续每一天的平今/平昨、手续费、保证金基线全部错位，而且不会报错」的地方。

本库对此的保证：`TradingDay` 是**落盘存下来的字段，不是读取时现算的**
（第三节说明了为什么），所以它不会因为本库升级、时段表更新而追溯性改变。

### 12.4 float64 / decimal 的边界：实测定的

两边的依赖是互斥的：它的主模块硬约束**只依赖 `shopspring/decimal`**，
本库为了实时行情要 `coder/websocket`。**所以两边都不能 import 对方。**

本库用 float64（指标是热路径），它用 decimal（钱不能有误差）。
边界画在哪，实测说了算（[probe.md 第十节](probe.md)）：

```
float64 → decimal 往返：29/29 逐位无损
  含 国债 T tick=0.005、沪金 0.02、股指 0.2、原油 0.1、碳酸锂 50

但【金额乘法】不同：
  沪金 512.34 × 1000 克/手 × 8 手
    float64 = 4098720.0000000005
    decimal = 4098720                差 5e-10
```

于是边界很明确：

- **价格与量用 float64 跨库传是安全的**——转成 decimal 逐位无损；
- **金额运算在 float64 里做不安全**——必须在 `futsim` 内部用 decimal 做。

**所以本库绝不预先算任何金额**，`价格 × 乘数 × 手数` 这类乘法一律发生在对面。
转换收在 `adapter/` 这个**独立嵌套模块**里（照搬 okx 那一对的 `adapter/simbar`），
主模块的依赖树不受污染。

| 待定 | 为什么要紧 |
|---|---|
| `Advance` 的入参**逐字段**长什么样 | 本库会把 `Bar` 做成**超集且同名**，让 adapter 里只有平铺赋值、没有语义转换 |
| `TradingDay` 用 `int32` 还是 `string` | 它的 testdata 是字符串（天勤 DIFF 线格式），本库用 `int32`。**统一一个，别在边界上来回转** |
| 合约键取 `String()` 还是 `Native()` | 按它「取值与 CTP 线格式一致」推测是 `Native()`，但要它确认 |
| **涨跌停价谁供** | 它撮合要校验涨跌停。新浪日线**不给**；天勤 quote 有 `upper_limit`/`lower_limit` 但那是**实时字段，历史回测取不到**。**这是本库当前的一个缺口**，见 contract.md 未验表 |
| 要不要「按交易日打包」的视图 | 取决于回测引擎的循环怎么写，可能要三方一起定 |

> **在这些定下来之前，`adapter/` 不动手写。** 现在写就是照着猜的接口写，
> 猜错了返工的是 adapter 加上两边的字段名——比等一轮贵得多。

## 十三、明确不做

不是没来得及，是**决定不做**，各有理由。

| 不做 | 理由 |
|---|---|
| **期权** | 期权链、隐含波动率、希腊字母是另一个数据模型，塞进来会把 `Bar` 撑变形。天勤的 5347 个期权合约留着，接口上不挡 |
| **组合 / 套利合约** | 同上。`FUTURE_COMBINE` 有 3529 个，但它们的价格是价差，不是价格 |
| 逐笔成交 / 盘口深度 | 中国期货的「tick」是 500ms 快照不是逐笔，形态不同。命名空间已留位 |
| 涨跌停 / 保证金的**模拟** | `refdata` 给参数，怎么用是回测引擎的事 |
| 交易决策 / 仓位核算 | 下游的事 |
| 上期/大商/郑商的官方直连 | 被 WAF 挡（实测 412），绕过要无头浏览器，不该进一个库的依赖树 |
| **新浪实时行情** | 已冻结两年，接了就是静默错误 |
| 多进程并发**写** | 一个命名空间同一时刻一个写者，第二个拿 `ErrLocked`。并发**读**支持 |

`Feed` **不是并发安全的**——一个回测循环就是一条时间线。并发跑多组参数各建各的。

## 十四、测试策略

姊妹项目的三层（手算基线 / 朴素批量参考 / 真实行情 golden）照搬到指标层。
本库另外要盯的，都在**时间模型**上——因为那是全新的、且错了不报错：

| 要锁住的 | 怎么锁 |
|---|---|
| `Period.Bars` 与新浪实际返回的标签**逐根一致** | 拿实测下来的 5m/15m/30m/60m × 商品/金属/贵金属，逐根对 |
| **`AG0` 与 `CU0` 的 60m 网格必须不同** | 反向测试。两者一样就说明退化成了时钟网格 |
| **停夜盘日的网格必须与普通日相同** | 反向测试。不同就说明相位按当天实际时段算了（见第二节被推翻的第一版） |
| **`null` 与 `[]` 必须走不同分支** | 喂 `var _=(null)` 应当报错，喂 `[]` 应当正常返回空 |
| 天勤与新浪的**同一根 K 线** `TradingDay` 一致 | 两个源日期口径相反，转换错了这里就炸 |
| 未完结的 K 线不进入任何一层 | 用「墙钟卡在时段中间」的构造用例 |
| 夜盘归属下一个交易日 | 周五夜盘的 `TradingDay` 必须是下周一 |
| 换月接缝处 `RawClose` 连续、`Close` 复权 | 用实测的 08-28→08-31 那组数 |
| 前复权会改写历史（**这是要证明的行为，不是 bug**） | 两次不同基准点跑出不同历史，断言差异存在 |
| 后复权不改写历史 | 加一段新数据后，旧区间逐位不变 |

> **「测试全绿」不等于对。** 姊妹项目里有一条教训直接适用：
> 只测 15m 的话，「按时段对齐」的错误实现**也能全绿**——因为 15m 上
> 两种规则结果相同。**分辨规则必须用 30m/60m。**
> 一个只在特定参数下才暴露的差异，测试用例挑错了参数就永远照不出来。
> 四条已知的「挑错参数就照不出来」列在 `contract.md` 第四节。

### 14.1 写一条断言的时候

**顺序有讲究，而且顺序不是权限：**

> **写自己的断言【之前】别看实现**——否则断言只覆盖你刚读到的那条路。
> **写完【之后】必须读实现**——常量写错、顺序写反、边界写偏，只有读得到才找得着。

两句话各管一类错：

| 从哪儿出发 | 找得到 | 找不到 |
|---|---|---|
| 从**失败场景**倒着写 | 逻辑写反 | **常量写错** |
| **读实现** | 常量写错 | 只覆盖实现走过的那条路 |

（后者**没有逻辑形状**，不违反任何模型，只是和世界不符——**只有和世界对一次才找得着**。
`dayBond` 那个 09:15 是**已随 `v0.1.0` 发布**的真 bug，
没有任何失败模型能推出「国债 09:15」这个具体数字。）

**然后逐条问：**

1. **有没有第二条路能让这条断言成立？**
   （去数**原因**，不是去数**现象**。这一问防的是「一条断言其实什么都没守」。）
2. **这条断言能区分三件事吗：对了 / 错了 / 什么都没发生？**
   - `notWant` 分不出「对了」与「什么都没发生」；
   - 子串式的 `want` 分不出「对了」与「错了」
     ——`"一致。"` 是 `"不一致。"` 的**子串**，会在失败报告上通过。
   ⇒ 每条用例都要有一件**必须发生的事**，且**其措辞不能是它反面的子串**。
3. **期望值是从哪儿来的？** 三种手敲都出过事：
   **手写输入 / 手写期望 / 从实现读出期望**。
   第三支最隐蔽——那个数是**算出来的**，看起来比手敲常量可靠，
   而它守的是**实现**，不是**事实**。
4. **失败时看得出这条测试当时在测什么吗？**
   不能只看出它不满意。**参数写错的测试会安静地测另一件事**——
   把**前提**也打印出来（`mkTmpl(26)` 被当成 330 分钟其实是 300，
   案例根本没测到想测的东西，救场的就是这一行）。

**守恒类不变量：有方向，必须成对，且跑在同一片输入上。**

| 方向 | 断言 | 只写这一条会漏掉 |
|---|---|---|
| 下界（不漏） | 每一分钟**至少**落在一根里 | **超装**：某根 60m 装了 90 分钟 |
| 上界（不超） | 每根**至多**装一个周期 | **漏装**：02:00–02:30 不属于任何一根 |

⇒ 两次都是「收盘标签序列一根不差、总根数一根不差」，
**比「输出等于基线」的测试，测不出「输入有没有被全部消费」。**
第三层：**成对的两条必须跑在同一片输入上**——一条测 A 集合、一条测 B 集合，
那叫「有两条不变量」，**不叫成对**。

**断言错误行为是允许的**，三个条件：

1. 名字自带限定（前缀 `TestKnownDefect_`）；
2. **失败信息要告诉未来的人「变红可能意味着你修好了」**；
3. 与文档里的限定绑定。

外加**可枚举**——`go test -list 'TestKnownDefect_.*' ./...`。
否则它会和白名单走同一条路：**欠条必须能被一条命令列出来。**

### 14.2 做破坏性验证的时候

写完测试，怎么知道它在承重？**改坏一处，看它红不红。** 但这件事有五个坑。

**① 编译不过不算变红。**
Go 的「未使用即错误」让最自然的变异写法**直接变成编译错误**——
`build failed` 不是 `--- FAIL`。本仓踩过**五**次（P4/P5、W2、M1，
以及 2026-09-08 对照组里的两次：拆掉守卫后 import 变「未使用」）。
**只看退出码非零，会把「变异根本没发生」记成「守住了」。**

##### 而「非零」的成因不止两种——这是一张**会长的表**

```
编译不过      实验根本没做成
被超时杀      我自己的 timeout 打断了它（退 124）——一次没做成的测量，不是一个结论
真失败        被测的东西确实红了
被信号中断    外部把它停了
```

⚠️ **遇到第五种时，先把它加进这张表，再解释结果。** 不要把它塞进已有的某一格——

> **凡是把「非零退出码」当成一种结论的判据，先数一遍非零有几种成因；
> 而「已知四种」是一个 as-of，不是一个穷尽。**

⚠️ **而这张表只管【退出码怎么解释】。** 另有一个轴：**这次测量所处的环境**——
退出码可以解释得完全正确，而那次测量仍然无效（见 ②'' 那一格）。
**两个轴不要合并**：合并之后那张表会变成「所有让结论不可信的原因」，而那不是一张能收敛的表。

**② 每处变异必须由【点名它的】那条测试捕获。**
「有测试红了」不够。两道刹车同时拆才红，说明**没有一道单独承重**。

**②'' 而「还原对了」这件事本身要验，不能靠仔细。**

评审方在同一件事上栽过**三次，三次的失效方式各不相同**：

```
.replace() 打偏                      → 变异【没发生】
CRLF 写回没生效                       → 还原【没发生】
git checkout <rev> -- f 更新了 index  → 还原【做了另一件事】：
                                        后面那条 git checkout -- f 忠实地
                                        还原到了刚被污染的那个 index
```

**第三个最难看：命令成功、退出码 0、文件确实被写了，只是写成了错的内容。**

⇒ 他的处置比修它值钱，照抄——**而射程要写全**：

> **任何一次要拿来下结论的测量，之前和之后各断言一次 `git status --porcelain` 为空；
> 两次都必须为空，否则这次测量作废。**

**覆盖哪些场合**（2026-09-08 扩写，最后一条是新增的）：

```
破坏性验证      原来只写了这一条
合并前重跑全套
送审自检
对照组
跑审计脚本      ← 新增
```

⚠️ **为什么原来那句会失效**：它写的是「每次实验前」，而 2026-09-08 那两次失效
**一次是「合并前的例行验证」、一次是「跑一个审计脚本」——两次都不是「做实验」**。

> **一条规矩挂错了范围，和挂在别人身上，效果一样——它在需要它的那一刻不在射程内。**
> 而现场看起来像「没照做」，于是没人会去改那条规矩。

⚠️ **为什么是「前后各一次」而不是只查前面**：只查前面挡得住「开跑时就已经脏了」，
**挡不住「跑的过程中被别的东西弄脏」**——而后者正是 2026-09-08 实例一的形态
（一个会变异载体的后台作业和这次测量并发）。

⚠️ **为什么写「两次都为空」而不写「两次相同」**：两次都空 ⇒ 必然相同，
「相同」在通过的那一侧是**废话**；而只写「相同」的话，
**「一直脏着，但脏得一样」会被读成通过。**（这条措辞被否掉的理由写在这里，
是为了下一个人不必重新提议它一次。）

⚠️ **看起来有一个例外，其实没有**：有些测量本来就会产出文件（日志、临时产物），
跑完 `status` 必然非空。**那不是例外——那种测量属于下面「会变异工作区的测量」那一条，
它本来就该在扔掉的克隆里跑。**

> **两条规矩正好互相消掉对方的例外**：
> 主树里的测量「前后都必须为空」没有例外，因为**会产出东西的不在这里跑**；
> 「去扔掉的克隆里跑」也没有例外，因为**主树里的规矩不给它留位置**。

> **别信还原，验还原。**

**②' 变异的【还原】也可能没生效
（出处：**评审方 2026-09-08**，实例、归因与修法都是他的。）

他做「插入一段再删回去」的实验时，脚本是
`插入 → 跑 → 用 .replace() 删回去 → 跑`，结果第二次跑**还是红**，
差点被当成「删除也被抓到」的证据。

实际是**还原那一步根本没生效**：文件是 CRLF，插的是 `\n`，`replace` 匹配不上——
**他的「删掉」什么也没删。**

> **一个失效的还原步骤，不会报错，它返回一个【看起来像证据的输出】。**

修法：**别用 `replace` 还原，把原始字节写回去**——

```python
raw = open(f, "rb").read()      # 动手之前存原始字节
...                             # 变异、跑
open(f, "wb").write(raw)        # 还原：写回去，不是「反向替换」
```

这是「读回别手敲」的同一条，只不过对象是**还原**而不是**校验**。

⇒ 这三条凑齐了同一条缝的三面，**表现完全一样**：

```
① 编译不过不算变红   → 变异【没发生】
② 打偏的变异         → 变异发生了，但【打在别处】
②' 还原没生效        → 变异【没被撤销】
```

**测试给出一个结果，而那个结果不属于你以为的那次变异。**

**③ 变异锚点也要在输出里露出来。**
`replace(..., 1)` 命中了另一行——探针照样 FAIL，**看起来「抓到了」**，
靠输出里那行 `13:00-15:00` 才发现打错了地方。

**③' 断言分两类，而你多半只补了第一类。**（评审方 2026-09-08 命名）

```
第一类：实验【做了没】     变异是否真的改了文件 / 写盘是否生效 / 还原是否逐字节
第二类：实验的【结论成不成立】 对照组是不是红 / 收尾时世界是不是绿 /
                              这些结论要不要影响【退出码】
```

**两类混在一起都叫「断言」，分开看才看得见缺口。**

真事：本仓的三个边界脚本，第一类断言写得很厚（4~7 条），
**第二类一处都没有**——对照组只 `print`，收尾自检只 `print`，退出码恒 `0`。
于是「守卫全坏掉」会打印三个 🟢 然后**成功退出**。

⚠️ **为什么会偏成这样**，值得单记：

> 第一类我踩过四次（`replace` 打偏 / CRLF 还原没生效 / 找不到目标行 /
> `sed` 只换了续行的第一行），所以补得很厚；
> **第二类一次都没踩过，就一处都没补。**

⇒ 而这**正是本仓已经登记过的那条**，第二次发生：

> **烧到你的那一半，和最承重的那一半，不是同一半。
> 别按「哪里出过事」分配检查，按「哪里塌了最贵」分配。**

**规矩在仓库里，而我仍然按出过事的地方分配了加固。**
所以这一条的用法要写成一个动作，不是一句提醒：
**写完一个实验脚本，先把断言按上面两类分个组，看哪一栏是空的。**

**④ 布尔信号的破坏性验证【必须是一对】。**
「恒为 true」和「从不为 true」都要变红。
**一位总亮着的标志，和没有这一位，是一回事。**

**⑤ 最贵的一条：层级是变异测试的盲区。**

> **变异测试在【已有的建模】里换值，它换不掉建模本身。**
> 它的射程 = 「你想到要变异什么」，而你想到的基本就是**被声称过的行为**
> ⇒ 它证明的是「声称的行为成立」，**不是「覆盖面够」**。

（为 `Anomalous` 写「恒 true / 从不 true」两个变异时，**已经默认了它是逐根的**，
两个变异都在那个前提里打转——而**错的正是那个前提**：
「模板与实际矛盾」是**交易日一级**的事实。）

⇒ **问「这个信号该在哪一级成立」的时机，就是你为它写第一个变异的时候。**

**测覆盖面要换一个动作：拿一个刚做完的真实改动去撞它，看它响不响。**

#### 而看到【全绿】时，该问的不是「对不对」

一个干净的全绿至少有两个来源，**而它们在输出上长得一模一样**：

```
没跑        —— 条件存在就下了结论（评审方 2026-09-08：推断「行号已经在偏了」，
               去测了，没有偏）
跑了自己    —— 我写的「真值」和被测代码共用同一个 `+2`，两边当然一致；
               那不是复现，是同义反复
```

> **⇒ 看到全绿时该问的不是「对不对」，是【这次绿，是什么东西有机会让它变红？】**

答不上来，那个绿就不是证据。（这也是对照组存在的全部理由：
**它就是那个「有机会让它变红」的东西**。）
（`doccheck` 的字段级空洞就是这么撞出来的：
「我改了文档没改代码，它会不会红」——**不会**，因为类型只登记名字。
补上之后当场抓到**四处真实分歧**。）

**顺带三条：**

- **守卫也要被验，不然它只是让人放心。** 加完一个字段就问一次：
  「我只改一边，它红不红？」
- **假警报比没有警报更糟**——**一条假警报教人忽略整个工具。**
- **修完之后再问一句：那个洞是被堵上了，还是被搬走了？**
  搬走的那种表面更好看，因为它从 SKIP 变成了 PASS。
  > **用一个错的理由换一个错的结论，不是改进。**

**为可测性做的重构，和它的第一批测试，不能互相担保**——两者共用同一个新形状。
要证明行为没变，只能拿新形状**之外**的东西比；最便宜的一条是
**新旧两版在同一输入上的输出逐字节 diff**。

**v0.1 先做时间模型，不是先做拉取。** 因为「一根 K 线是否已完结」这个问题
在本库里**必须先有日历才能回答**（[probe.md 坑四](probe.md)），
而 `Source` 的实现约定里就有「只返回已完结的」。顺序反过来的话，
第一个 `Source` 就得先塞一个临时的判完结逻辑，然后再拆掉。

> **v0.1 必须交付一个【可用的】日历实现，不能只交接口。**
> 排期第一版把 `Calendar` 接口放在一档、把唯一的实现 `calendar/derived` 放在【两档之后】，
> 于是【紧接着那一档】的 `Source` 拿不到任何能判完结的东西——**它的实现约定依赖一个
> 两个版本之后才交付的组件**。
>
> 改法是把 `calendar/embedded`（从天勤导出的时段表快照 + 交易日列表，
> 带生效区间）提到 v0.1。`calendar/derived` 留在 v0.4，它的价值是
> **覆盖内置表的历史盲区**（现在可行了——天勤有 10 年 1m 数据，
> 每日实际时段可以逐日反推），而不是「第一个能用的实现」。
>
> 这条是评审提出来的。**排期上的依赖倒置很难自己看出来**，因为每一行
> 单独看都合理，只有把「【那一档】的验收标准」和「【再下一档】才有的东西」摆在一起才现形。

**v0.5 的深度分钟提前到 `continuous` 之前**：换月规则要按持仓量判主力，
而持仓量的日频数据新浪就有——但复权后的序列要拿分钟级去验证接缝，
所以先把深度数据落库更顺。
