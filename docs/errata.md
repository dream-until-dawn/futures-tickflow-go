# 发布注解的勘误

> ⛔ **这份文件存在的理由只有一条：tag 注解改不了。**
>
> 文档写错了可以改，`README` 写错了可以改，而一条已经推到远端的 tag 注解 **改不了** ——
> 它是不可修的载体。⇒ 当后续版本让某一句注解变假时，**唯一的通道就是在这里写一条勘误**。
>
> ⚠️ **它不放在 `docs/release/` 下**，理由是那个目录有一条正在干活的不变量：
> **每一份都必须是可机械裁出的 tag 正文**（`release_notes_test.go` 钉着它）。
> 勘误不是 tag 正文 ⇒ 放进去只能靠给那条守卫开一个例外，而**会误报／被开例外的守卫最终被关掉**。
>
> 📌 **只增不改**：一条勘误写下之后不再改写、不再删除。
> 读它的人多半是拿着一份旧 tag 在照着做，而**他手上那份永远是旧的**。

## v0.4.1 · 「自查」方法二 —— 自 v0.5 起失效

**注解里那一句（逐字）：**

```
二、或跑一次 `Sync`，看 `rep.Gaps` 里有没有 `GapStoreUnverified`。
    ⚠️ 而它只在 `.meta` 还在时有效：删掉 `.meta` 之后那一段会报成「没拉过」（实测）。
```

⛔ **v0.5 起它不再管用，而失效的方式是【为真而有害】：照着做的人会得出「这个库没问题」。**

它在 v0.4.1 上管用，靠的恰恰是当时的一个缺陷：

```
v0.4.1  损坏库 ＋ 再同步 ⇒ 落盘先失败 ⇒ 本次一段都没走查
        ⇒ 每一段报 GapStoreUnverified ⇒ 照方法二做的人【找得到】它 ⇒ 结论「库坏了」 ✅
v0.5    走查不再看「本次碰过什么」，而是按 coverage 的每一段走一遍
        ⇒ 坏库的每一段都走查过了、而且没通过
        ⇒ 它们报的是 GapStoreVerifyFailed，【不再是】GapStoreUnverified
        ⇒ 照方法二做的人【找不到】它 ⇒ 结论「库没问题」 ⛔ 而库是坏的
```

**改看这一类：**

```
GapStoreVerifyFailed   这一段走查过了，而它没通过 —— 真因在 rep.TruncatedTails 里
```

⚠️ **而 `GapStoreUnverified` 这个名字没有消失**，它在 v0.5 之后的身份变了：
**我们自己的 `segfile` 实现不会再产出它**（只有「这一遍走查跑不起来」那一种会）。
⇒ 在 `rep.Gaps` 里找不到它 **不再是**「库没问题」的证据。

✅ **方法一不受影响，它是仍然可用的那条路：**

```
一、对 `store.Coverage()` 的每一段跑 `store.Verify(span)`：
    坏掉的段返回「记录的交易日不是非降序」。
```

`Verify(span)` 在 v0.5 里**特意保留**（从 `Store` 接口降级成 `*segfile.Store` 的具体方法），
两条理由都不是兼容：**这条注解逐字点名了它**，以及它是新读法的参照实现。
⇒ `tag_selfcheck_meta_test.go` 钉着方法一今天照着做得通。

---

📎 **这条勘误是怎么被逼出来的**：v0.5 那一片计划里有一步「把
`whole_library_error_unattributed_test.go` 翻面」——
而**翻面的那一刻，就是方法二失效的那一刻**。
🔴 那条守卫在 main 上的绿，本身就是「方法二今天找得到」的读数；
它变红时如果没有人接着问一句「那条注解怎么办」，这份勘误就不会存在。
⇒ **一颗钉在现状上的钉子，它响的那一刻要连着问「有没有哪份不可修的东西引用了这个现状」。**
