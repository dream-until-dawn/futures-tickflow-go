# 探针记录：中国期货数据源实测

> **这份文档是全部设计的事实底座。** 下面每一条都是 2026-09-07 在本机打真实接口
> 问出来的，不是从文档或记忆里抄的。设计里任何一处「因为上游是这样，所以我们
> 那样做」，都应该能在这里找到对应的那一行。
>
> 每条都标了**怎么重跑**。数据源会变，变了就该由重跑来发现，而不是由某个
> 回测结果不对劲来发现。
>
> 探测环境：Windows 11 / Go 1.26.1 / 直连（无代理）/ 2026-09-07（周一）13:15–13:30。

## 一、新浪：日线（能用，而且很深）

**端点**

```
https://stock2.finance.sina.com.cn/futures/api/jsonp.php/var%20_=/InnerFuturesNewService.getDailyKLine?symbol=RB0
```

需要 `Referer: https://finance.sina.com.cn`。返回是 JSONP 包着的 JSON 数组，
前面带一行 `/*<script>location.href='//sina.com';</script>*/` 需要剥掉。

**实测（2026-09-07）**

| symbol | 根数 | 区间 |
|---|---|---|
| `RB0`（螺纹主连） | 4237 | 2009-03-27 → 2026-09-04 |
| `IF0`（沪深300主连） | 2339 | 2017-01-17 → 2026-09-04 |
| `RB2701` | 155 | 2026-01-16 → 2026-09-04 |
| `RB2610` | 219 | 2025-10-16 → 2026-09-04 |
| `M2701`（大商所） | 154 | 2026-01-19 → 2026-09-04 |
| `TA2701`（郑商所） | 154 | 2026-01-19 → 2026-09-04 |
| `T2612`（中金所国债） | 120 | 2026-03-16 → 2026-09-04 |

**字段**：`d` 日期、`o/h/l/c`、`v` 成交量、`p` **持仓量**、`s` **结算价**。

持仓量与结算价是加密货币没有的两个字段，而它们在中国期货里是必需的——
主力判定靠持仓量，每日结算与保证金靠结算价。**新浪日线免费给了这两个**，
这是它比大多数免费源更值钱的地方。

**合约代码的坑**：郑商所原生是 **3 位**合约码（`TA701`），新浪要 **4 位**
（`TA2701`）。3 位码跨十年有歧义（`TA701` 既可以是 2017-01 也可以是 2027-01），
本库内部**一律用 4 位**。大小写不敏感（`rb2701` 与 `RB2701` 返回完全相同）。

`TA701` 不报错，返回的是：

```
var _=(null);
```

**是 `null`，不是空数组。** 差别要紧：`json.Unmarshal` 到 `[]Bar` 会得到一个
`nil` 切片而非报错，`len()` 为 0，看起来和「这个合约当天确实没有数据」
一模一样。**把「代码写错了」和「这段确实没数据」渲染成同一个结果，
是本轮遇到的第三种静默失败。** 解析层必须把 `null` 与 `[]` 分开处理。

**重跑**

```bash
curl -s -H "Referer: https://finance.sina.com.cn" "https://stock2.finance.sina.com.cn/futures/api/jsonp.php/var%20_=/InnerFuturesNewService.getDailyKLine?symbol=RB0" | head -c 300
```

## 二、新浪：分钟线（能用，但有四个坑）

**端点**（`type` = 5 / 15 / 30 / 60）

```
.../InnerFuturesNewService.getFewMinLine?symbol=RB0&type=5
```

字段比日线少一个：`d o h l c v p`——**没有结算价**（分钟线本就没有），有持仓量。

### 坑一：硬顶 1023 根，且没有翻页参数

四个周期实测**全部恰好 1023 根**：

| type | 根数 | 覆盖区间 | 折合 |
|---|---|---|---|
| 5 | 1023 | 2026-08-17 → 2026-09-07 | 约 3 周 |
| 15 | 1023 | 2026-07-06 → 2026-09-07 | 约 2 个月 |
| 30 | 1023 | 2026-05-07 → 2026-09-07 | 约 4 个月 |
| 60 | 1023 | 2025-12-22 → 2026-09-07 | 约 9 个月 |

**没有发现任何分页 / 起止时间参数。** 这意味着分钟级回测的历史深度上限就是这个数，
**且过去的分钟数据一旦滑出窗口就永远取不回来**。这是本项目当前唯一的硬缺口，
也是要接第二个数据源的唯一理由。

### 坑二：K 线按【收盘时刻】标注，且休市段直接消失

2026-09-04（周五）RB0 的全部 5m 时间戳：

```
09:05 09:10 ... 10:10 10:15 | 10:35 10:40 ... 11:25 11:30 |
13:35 13:40 ... 14:55 15:00 | 21:05 21:10 ... 22:55 23:00
```

三件事同时被这一行确定下来：

1. **首根是 `09:05` 而不是 `09:00`** → 标注的是**收盘时刻**，与 OKX 等加密源
   （标注开盘时刻）**相反**。
2. `10:15` 之后直接跳到 `10:35`，**没有 10:20 / 10:25 / 10:30**
   → 休市段不占位，不是空洞，是根本不存在。
3. 夜盘 `21:05`–`23:00` 挂在 **2026-09-04** 名下 → 新浪按**自然日**标注。
   但按中国期货的规则，周五夜盘属于**下周一（09-07）的交易日**。
   **两套日期口径在这里分叉**，见第六节。

### 坑三：高周期是「交易时间轴计数聚合」，会跨休市段

同一天的 15m / 30m / 60m：

```
15m: 09:15 09:30 09:45 10:00 10:15 | 10:45 11:00 11:15 11:30 | 13:45 ... 15:00 | 21:15 ... 23:00
30m: 09:30 10:00 10:45 11:15 | 13:45 14:15 14:45 15:00 | 21:30 22:00 22:30 23:00
60m: 10:00 11:15 14:15 15:00 | 22:00 23:00
```

规则是**按「实际交易了多少分钟」累计**，而不是按时钟网格对齐：

- 30m 的 `10:45` 那根 = `10:00–10:15` + `10:30–10:45`，**跨了上午的休市段**；
- 30m 的 `13:45` 那根 = `11:15–11:30` + `13:30–13:45`，**跨了午休，且横跨上下午**；
- 30m 的 `15:00` 那根只有 15 分钟（`14:45–15:00`），收盘强制截断。

**15m 是个例外**：三个日盘时段的长度（75 / 60 / 90 分钟）都是 15 的整数倍，
所以「计数聚合」与「按时段对齐」在 15m 上**恰好给出相同结果**。
只在 30m / 60m 上才分得出来。

> 这一点值得单说：**如果只测 15m，会得出「新浪是按时段对齐的」这个错结论**，
> 而且测试全绿。分辨两种规则必须用 30m 或 60m。

### 坑三之二：网格在【交易日】边界重启，并跨越隔夜缺口——两个品种可以有不同的 60m 网格

上面只证明了「会跨休市段」，没证明网格从哪里起算、在哪里断。
用**夜盘长度不是周期整数倍**的品种可以一次问清楚。

沪银 `AG0` 夜盘 21:00–02:30 = **330 分钟**，330 / 60 = **5.5**，不是整数倍；
沪铜 `CU0` 夜盘 21:00–01:00 = 240 分钟 = 4×60，是整数倍。同一天的 60m：

| | 夜盘部分 | 日盘部分 |
|---|---|---|
| `CU0` 60m | `22:00 23:00 00:00 01:00`（4 根，整除） | `10:00 11:15 14:15 15:00` |
| `AG0` 60m | `22:00 23:00 00:00 01:00 02:00`（5 根 + 30 分钟余数） | **`09:30` 10:45 13:45 14:45 15:00** |

**两个品种的日盘时段完全相同（09:00-10:15 / 10:30-11:30 / 13:30-15:00），
60m 网格却整体错开 30 分钟。** 原因只有一个：`AG0` 夜盘余下的
`02:00–02:30` 那 30 分钟，**跨过了 02:30 到次日 09:00 这个 6.5 小时的隔夜缺口**，
与 `09:00–09:30` 拼成了一根完整的 60m，标注为 `09:30`。

30m 上则两者都整除（330/30 = 11，240/30 = 8），网格因此一致——
`AG0` 30m 夜盘正好 11 根：`21:30 22:00 22:30 23:00 23:30 00:00 00:30 01:00 01:30 02:00 02:30`。

**三条规则由此确定：**

1. 网格在**交易日开始**处重启（有夜盘的品种是 21:00，没有的是 09:00）；
2. 网格**跨越隔夜缺口**（02:30 → 次日 09:00）——因为夜盘与其后的日盘
   属于**同一个交易日**；
3. 网格在**交易日结束**处强制冲刷（15:00），最后一根可以是短的。

**代价**：`60m` 的网格**无法只从日盘时段推出来**，必须知道整个交易日
（含夜盘长度）。任何「对齐到整点」的实现，在 `AG0` 上会**每一根都错 30 分钟**，
而且序列看起来完全正常。

这条把「交易时间轴」从一个漂亮的抽象变成了**必需品**，见 design.md 第二节。

**重跑**

```bash
for s in AG0 CU0; do curl -s -H "Referer: https://finance.sina.com.cn" ".../getFewMinLine?symbol=$s&type=60"; done
```

比较两者日盘部分的标签是否错开。

### 坑四：会返回一根【未完结】的当前 K 线，且标注的是【未来时刻】

探测时的墙钟是 **2026-09-07 13:19:54**，下午盘 13:30 才开。而此刻：

- 5m 序列最后一根 = `11:30`（正常，上午收盘那根）
- 30m 序列最后一根 = **`13:45`** ← 比墙钟晚 25 分钟
- 60m 序列最后一根 = **`14:15`** ← 比墙钟晚 55 分钟

那根 `13:45` 的内容 `o=3150 h=3152 l=3147 c=3150 v=932`，实际只装了
`11:15–11:30` 这 15 分钟的上午残段。也就是说：

**新浪把还在累积的那根 K 线一并返回，并给它打上「它将来会收盘的那个时刻」
作为标签，而且没有任何 confirm 标志。**

这比 OKX 的 `Confirm == false` 更难防——OKX 至少有个标志位。
这里要判断一根 K 线是否已完结，**必须先有交易时段表**：得知道 `13:45` 对这个
品种今天是不是一个合法的收盘时刻，以及那一刻是否已经过去。

**这直接决定了架构**：交易日历与时段表不是配套设施，是**判断数据是否可信的前置条件**，
必须做成一等公民。

**重跑**

```bash
date '+%Y-%m-%d %H:%M:%S'
curl -s -H "Referer: https://finance.sina.com.cn" ".../InnerFuturesNewService.getFewMinLine?symbol=RB0&type=30" | tail -c 200
```

盘中跑，对比墙钟与最后一根的时间戳。

## 三、新浪：实时行情【已冻结两年】

这是本轮探测里最要紧的一条，因为它**不报错**。

**端点**：`https://hq.sinajs.cn/list=RB0`（需 `Referer`，返回 GBK）

**返回**（2026-09-07 探测）：

```
var hq_str_RB0="螺纹钢连续,145957,3538.00,3556.00,3484.00,3544.00,3486.00,3487.00,
3487.00,0.00,3541.00,3,138,2186809,1578526,沪,螺纹钢,2024-07-17,0,...";
```

HTTP 200，字段齐全，数值合理，看不出任何毛病。但把它和日线序列对一下：

| | 实时接口 | 日线 2024-07-17 | 日线 2026-09-04（最新） |
|---|---|---|---|
| 开 | 3538.00 | **3538.000** | 3145.000 |
| 高 | 3556.00 | **3556.000** | 3180.000 |
| 低 | 3484.00 | **3484.000** | 3137.000 |
| 最新/收 | 3487.00 | **3487.000** | 3166.000 |
| 持仓量 | 2186809 | **2186809** | 1497791 |
| 成交量 | 1578526 | **1578526** | 877156 |

**六个字段逐位相同**，且它自己的日期字段就写着 `2024-07-17`。

结论：**`hq.sinajs.cn` 的期货实时行情自 2024-07-17 起冻结，至今两年零两个月。**
它仍然返回 200 和一份结构完整、数值合理的快照——这正是最坏的一种坏：
**不报错、不为空、看起来完全正常。**

新浪的 **K 线**接口是活的（更新到当天），**只有实时接口死了**。
两者同域名、同风格，很容易被当成一套东西一起信。

> 网上大量教程与开源库仍在用 `hq.sinajs.cn` 取期货实时价。任何直接照抄的人，
> 拿到的都是 2024 年 7 月 17 日下午 2 点 59 分 57 秒的那一帧。

**本库的处置**：不提供基于 `hq.sinajs.cn` 的实时源。若日后要接，
必须带一条**开机自检**——把实时快照与当日日线比对，冻结就直接报错，
而不是让它悄悄流进回测。

**重跑**

```bash
curl -s -H "Referer: https://finance.sina.com.cn" "https://hq.sinajs.cn/list=RB0" | iconv -f GBK -t UTF-8
```

看第 18 个字段（日期）。不是今天 = 已冻结。

## 四、主力连续 `RB0` 是【未复权】拼接——实测虚增 1.7 个百分点

`RB0` 是什么，不能猜，得对出来。拿它和具体合约逐日比：

**最近 40 个交易日**：`RB0` 与 `RB2610` 逐位相同的有 **35 天**，
与 `RB2701` 相同的有 **5 天**——它是**主力连续**，会在合约间切换。
比对同时包含收盘价与持仓量，两个字段都相同才算命中，避免撞价。

**换月点实测**：

| | 2026-08-28 | 2026-08-31 | 涨跌 |
|---|---|---|---|
| `RB0`（主连） | 3112.0（跟 RB2610） | 3197.0（跟 RB2701） | **+2.73%** |
| `RB2610` 真实 | 3112.0 | 3143.0 | +1.00% |
| `RB2701` 真实 | 3158.0 | 3197.0 | +1.23% |

**主连在这一天显示 +2.73%，而无论持有哪一个合约，真实收益都只有 1.0%–1.2%。
凭空多出约 1.5–1.7 个百分点，而且是在一天之内。**

这不是新浪的 bug，是「未复权主力连续」的定义使然：切换那天前后两根来自
不同合约，中间的**基差**被当成了涨跌。螺纹钢一年换月 3–6 次，17 年的 `RB0`
上有上百个这样的接缝，**每一个都是凭空的收益或亏损**。

而它**完全静默**：`RB0` 的序列看上去连续、平滑、没有任何缺口标记。

**这条直接决定本库必须自己做换月拼接**：
以合约级序列为准，自己按明确的规则换月、按明确的方式复权，并把接缝位置
（`RollSchedule`）交出去，让回测能知道哪几天的收益不该算。
新浪的 `RB0` 只作**对账参照**，不作真值。

> 对比：okx-tickflow-go 明确写了「交割合约换月拼接——**不做**」。
> 加密市场的永续合约没有到期日，那个决定是对的。
> 中国期货每个合约都有交割月，**这里不做就等于没做**。

## 五、天勤 openmd：合约参考数据（免费、无鉴权、含**交易时段表**）

**端点**：`https://openmd.shinnytech.com/t/md/symbols/latest.json`

约 **12.5 MB** JSON，实测下载很慢（约 1.3 MB / 3 分钟，需 `-C -` 断点续传），
解析出 **11845** 个 symbol：

| class | 数量 | 含义 |
|---|---|---|
| `FUTURE_OPTION` | 5347 | 期货期权 |
| `FUTURE_COMBINE` | 3529 | 组合（跨期套利等） |
| `FUTURE` | 2628 | **期货合约** |
| `OPTION` | 204 | 期权 |
| `FUTURE_INDEX` | 64 | 指数（`KQ.i@SHFE.rb`） |
| `FUTURE_CONT` | 64 | **主力连续**（`KQ.m@SHFE.rb`） |
| `SPOT` / `INDEX` | 9 | 现货 / 指数 |

交易所分布：CZCE 4829、DCE 2658、SHFE 2118、CFFEX 193、INE 44。

**每个合约带的字段**（这是关键）：

```
instrument_id  exchange_id  product_id  ins_name
volume_multiple      合约乘数（每手多少吨/股）
price_tick           最小变动价位
price_decs           价格小数位
expire_datetime      到期时刻（Unix 秒）
trading_time         【交易时段表】
margin  commission  position_limit
max/min_limit_order_volume  等报单约束
```

`trading_time` 长这样：

```json
"trading_time": {
  "day":   [["09:00:00","10:15:00"], ["10:30:00","11:30:00"], ["13:30:00","15:00:00"]],
  "night": [["21:00:00","23:00:00"]]
}
```

**这正是判断「一根 K 线是否已收盘」所必需的那张表**，免费、机器可读、按合约给。

### 实测出的 9 种时段模式

| 日盘 | 夜盘 | 品种数 | 代表品种 |
|---|---|---|---|
| 09:00-10:15 / 10:30-11:30 / 13:30-15:00 | 无 (`null`) | 50 | 已退市或无夜盘品种 |
| 同上 | 无 (`[]`) | 42 | AP CJ JR LR PM RI RS SF SM UR WH 等 |
| 同上 | 21:00–**23:00** | 32 | rb hc i j jm m y p a c cs eb eg fu l pp TA MA FG SR CF OI RM ZC |
| 同上 | 21:00–**23:30** | 17 | 部分农产品 / 黑色（历史时段） |
| 同上 | 21:00–**25:00**（次日 01:00） | 7 | cu al zn pb ni sn ss |
| 同上 | 21:00–**26:30**（次日 02:30） | 3 | **au ag sc** |
| 09:15-11:30 / 13:00-15:15 | 无 | 3 | **T TF TS**（国债期货） |
| 09:30-11:30 / 13:00-15:00 | 无 | 3 | **IC IF IH**（股指期货） |
| 同上（商品日盘） | 22:30–23:00 | 1 | eg（历史片段） |

三件事从这张表里直接读出来：

1. **夜盘跨日用「25:00 / 26:30」表示**，不是负数也不是次日日期。解析时要按
   `hh >= 24 → 次日 (hh-24)` 处理。
2. **中金所的股指与国债时段互不相同，且都与商品不同。** 任何「中国期货的交易时间是
   9:00–15:00」的硬编码都是错的。
3. **同一个 `product_id` 会出现在多种模式里**（`CF` 同时出现在三种）——因为
   时段表是**按合约**给的，而**夜盘时间在历史上被调整过多次**。
   于是：**一张静态时段表不足以支撑历史回测**，见 contract.md 的风险表。

### 主力连续 / 指数符号

天勤自己有 `KQ.m@SHFE.rb`（主力连续）与 `KQ.i@SHFE.rb`（指数）。
它们的复权口径**未经本轮实测**，不能假定与新浪 `RB0` 一致，也不能假定已复权。

**重跑**

```bash
curl -C - -o tq.json "https://openmd.shinnytech.com/t/md/symbols/latest.json"
```

## 六、天勤 openmd 实时 / 深度历史：路径存在，但需账户

**websocket 端点探测**（Go + gorilla/websocket）：

| URL | 结果 |
|---|---|
| `wss://openmd.shinnytech.com/t/md/front/mobile` | **400 Bad Request** |
| `wss://openmd.shinnytech.com/t/md/front/pc` | 404 Not Found |
| `wss://api.shinnytech.com/t/md/front/mobile` | 404 Not Found |
| `wss://free-api.shinnytech.com/t/md/front/mobile` | 404 Not Found |
| `wss://u.shinnytech.com/t/md/front/mobile` | 400 Bad Request |

**400 与 404 的差别就是结论**：返回 400 的那两个路径**存在**，只是握手被拒；
其余是路径不存在。所以缺的是鉴权，不是找错了地址。

**鉴权方式已确认**（不带凭证探的）：

```
POST https://auth.shinnytech.com/auth/realms/shinnytech/protocol/openid-connect/token
     grant_type=password & client_id=shinny_tq & username=... & password=...
```

空密码时返回 **422** 并明确指出是 `password` 字段不符合格式——
说明端点接受了这个请求形状（`grant_type` / `client_id` 都对），只差真实凭证。
换成 `/realms/...`（不带 `/auth` 前缀）则是 404，所以路径也已确定。

**待办**：拿到免费快期账户后验证 ①能否取到深度分钟历史 ②实时推送是否可用。
注册入口 `https://account.shinnytech.com/`（实测 200）。

**凭证不进版本库**：走 `.env`（`.gitignore` 已覆盖）或环境变量
`SHINNY_USER` / `SHINNY_PASS`，测试从环境读，缺失时跳过而不是失败。

## 七、交易所官方：只有中金所能直连

| 交易所 | 端点 | 结果 |

| **中金所 CFFEX** | `http://www.cffex.com.cn/sj/hqsj/rtj/202609/04/index.xml` | ✅ **200**，489 KB XML |

中金所 XML 字段：`instrumentid` `tradingday` `openprice` `highestprice`
`lowestprice` `closeprice` `preopeninterest` `openinterest` 等，含期权。

**412 Precondition Failed 是 WAF 的典型响应**（需要 JS 挑战 / Cookie）。
绕过它要么上无头浏览器，要么模拟挑战——两者都**不适合放进一个库的依赖树**，
且随时会被改。

**处置**：官方源只做**可选的对账通道**（中金所可直连，其余留接口不实现），
不作为主数据源。主线仍是新浪 + 天勤。

## 八、这轮探测改变了哪些原本的设想

诚实记一下：动手探之前脑子里的几条，被实测推翻了。

| 原本以为 | 实测 | 影响 |
|---|---|---|
| 新浪实时行情能用（教程都这么写） | **冻结两年** | 实时源必须另找；且任何实时源都要加冻结自检 |
| K 线按开盘时刻标注（照搬 crypto 的直觉） | **按收盘时刻** | 内部要同时存开 / 收两个时刻，见 design.md |
| 高周期按时段对齐 | **按交易时间轴计数聚合，会跨休市段** | 聚合器不能用「时钟网格」实现 |
| 15m 能验证聚合规则 | **15m 上两种规则结果相同，验不出来** | 测试必须用 30m / 60m |
| 同交易所同日盘的品种，网格一样 | **AG0 与 CU0 的 60m 网格错开 30 分钟**（夜盘长度不同所致） | 网格必须按整个交易日算，不能只看日盘 |
| 未完结 K 线像 OKX 一样有标志位 | **没有标志，且标签是未来时刻** | 判完结必须先有时段表 → 日历成为一等公民 |
| 交易所官网能直接拉 | **四家里三家被 WAF 挡** | 官方源降级为可选对账 |
| 主力连续可以直接拿来回测 | **未复权，单日虚增 1.7pp** | 换月拼接必须自己做，且是核心功能 |
| 一张交易时段表够用 | **同品种不同合约时段不同（历史调整过）** | 时段表必须带生效区间 |

> 八条里有七条会**静默地**把回测结果变好看或变难看，没有一条会报错。
> 这也是为什么先探针、后设计——反过来做的话，上面每一条都会变成
> 「跑了半年才发现结果不对」。

## 九、重跑：`tools/probe/probe.py`

上面每一条的重跑命令都列在各节末尾，但零散地敲 curl 不会有人真去做。
所以做成了一个脚本，把**全部 9 条结论**一次跑完并与本文档记录的基线比对：

```bash
python tools/probe/probe.py                      # 全部
python tools/probe/probe.py --only sina-frozen   # 单条
```

2026-09-07 实测 **9/9 与记录一致**。

**它是探针，不是测试。** 断言的是「外部世界现在是什么样」，不是本库的行为。
因此：

- 它**会**因为上游变化而失败，那正是它存在的理由；
- 失败**不代表本库有 bug**，代表本文档该更新了；
- 所以它**不进 CI 的必过项**——一个会因为别人改接口而红的必过项，
  迟早会被加上 `|| true`，然后就再也没人看了。

退出码：`0` 全部一致 / `1` 有偏离 / `2` 网络或解析失败（无法判断）。
**后两者分开**，因为「连不上」和「结论变了」是完全不同的两件事。

### 写这个脚本时自己踩了一次坑，值得记下来

第一版挑「倒数第二个自然日」来验证网格，结果 `CU0` 那条返回了**空列表**。
原因是：**周五夜盘 21:00 跑到周六 02:30，所以周六也有 K 线**——
按自然日倒数，取到的是一个只有夜盘残段、没有日盘的周六。

改成「最后一个含 `15:00` 标签的自然日」（只有走完整个日盘才有那一根）后正常。

> 这正是本库要解决的问题本身：**自然日与交易日不是一回事。**
> 一个刚把这件事写进设计文档的人，转头在自己的探针脚本里又踩了一遍——
> 说明它不是「知道就能避免」的那类坑，而是**必须由类型和 API 挡住**的那类。
> `TradingDay` 因此是一个独立的类型，而不是一个 `int32` 别名。
