### 「17 年」是【主连】口径；合约级只有约 7.5 年

上表把主连（`RB0` 4237 根 / 2009 起）与合约级（`RB2701` 155 根）并排放，
两行都对，**但合起来读会得出一个错的结论**。合约级逐个打下来：

| 合约 | 结果 | | 合约 | 结果 |
|---|---|---|---|---|
| `RB2509`（已到期） | 239 根，2024-09-19 起 | | `RB1905` | 242 根，**2018-05-16 起** |
| `RB2101` | 243 根 | | `RB1903` | **只剩 1 根**（2019-03-15） |
| `RB2001` | 243 根 | | `RB1901` | **null** |
| `RB1910` | 242 根 | | `RB1801` / `RB1701` / `RB1605` | **null** |

**不是「到期即消失」**——2025 年到期的 `RB2509` 还在。墙落在 **`1903`/`1905` 之间**，
`RB1903` 只剩一根是那道墙的毛边。AG / CU 交叉验证一致，不是单品种现象。

所以**新浪合约级日线的可用深度约 7.5 年**（≈2018-05 起），不是 17 年。

**这一条与 6.4.1 是同一个形状**：design 第八节的真值是**合约级**序列，
而合约级在**两个源上都止于 2016–2019**：

| 口径 | 新浪 | 天勤 |
|---|---|---|
| 主连 | **2009-03-27**（17 年） | 2016-01-04 |
| **合约级** | **≈2018-05**（7.5 年） | **2016-01-04** |

**「17 年历史回测」在合约级口径上做不到**，只有主连口径能到 2009——
而主连未复权（第四节），本库又要求真值必须是合约级。两条合起来的实际结论是：

> **可信的合约级回测区间，起点是 2016-01-04**（天勤地板线）。

评审 E4 指出的。原文没量过这道墙，README 的标题行直接写了「17 年（2009 至今）」。

**字段**：`d` 日期、`o/h/l/c`、`v` 成交量、`p` **持仓量**、`s` **结算价**。

持仓量与结算价是加密货币没有的两个字段，而它们在中国期货里是必需的——
主力判定靠持仓量，每日结算与保证金靠结算价。

### ⚠️ 结算价字段永远存在，但值有大量是 **0**，比例按品种从 0.2% 到 98.6%

> **2026-09-07 三轮加测。** 这条是下游记账内核报回来的——**我把结算价推荐给了它，
> 却没检查过值的质量**。它查了 `RB0`（7.7% 为零），我按品种复查后发现**远不止**。

| 主连 | 总根数 | `s == 0` | 占比 | 2020 年后仍为零 |
|---|---|---|---|---|
| `AG0` | 3487 | 6 | 0.2% | — |
| `RB0` | 4237 | 326 | 7.7% | 3 根（2009–2010 占 317） |
| `TA0` | 4791 | 922 | 19.2% | — |
| `CU0` | 5273 | 1364 | 25.9% | 3 根 |
| `M0` | 5276 | 1589 | 30.1% | 108 根（2020 年 106） |
| **`T0`（国债）** | 2339 | 2060 | **88.1%** | **逐年 242 根，到 2026** |
| **`IF0` / `IH0`（股指）** | 2339 | 2307 | **98.6%** | **逐年 242 根，到 2026** |

### 这一个百分比其实盖住了**三件不同的事**

按日期展开之后才看得出来，三种形态的后果完全不同：

| 形态 | 表现 | 性质 | 后果 |
|---|---|---|---|
| **① 中金所系统性缺失** | `IF0`/`IH0` 98.6%、`IC0` 99.8%、`T0` 88.1%，**持续到 2026-09-04 最新一根** | **能力缺失**，不是数据质量问题 | 这个源上**根本做不了**中金所品种基于结算价的逐日盯市。这条该进**能力边界**，不只是风险表 |
| **② 按【交易所基础设施族】发生的坏日** | 见下表——**不是「全市场」，也不是每次四家** | 上游那几天的**故障**，且有结构 | 对账时要认得出；补数要**按族分别验**，CZCE 根本不需要补 |
| **③ 早期历史缺失** | `M0` 集中在 2020-01~07；`TA0` 19.2% 全在 2014 之前 | 历史遗留 | 2020 年起基本可用 |

`s == 0 → NaN` 对三者都对，**但合成一行会让人以为「中金所也是早期缺失」——
实际上第 ① 类是永久的**。这正是本仓反复强调的那种「一个数字盖住了三件事」，
只不过这次盖住它的是我自己写的那个百分比。

#### ② 的真实形态：按交易所族，不是「全市场」

每个交易所取一个代表品种重打（CZCE 作阴性对照）：

| 日期 | 为零的交易所 | 正常 |
|---|---|---|
| 2021-12-30 | `SHFE` `INE` `DCE`（**3 家**） | `CZCE` |
| 2023-08-28 | `SHFE` `INE`（**2 家**） | `CZCE` `DCE` `GFEX` |
| 2024-09-25 | `SHFE` `INE` `DCE` `GFEX`（4 家） | `CZCE` |

**不是随机的，有结构**：

- **INE 每次都跟着 SHFE**（上期能源是上期所旗下，同一套系统）——3/3；
- **GFEX 只在 DCE 也坏的那天坏**（广期所由大商所牵头组建）——2023-08-28 两家都正常；
- **CZCE 三次全部正常**，从未受影响。

所以这是**按交易所基础设施族**发生的：`{SHFE, INE}`、`{DCE, GFEX}`，CZCE 独立。

> **本文原先写的是「四个交易所同时为零」，那是错的**——只有 2024-09-25 是四家。
> 错的来源是评审上一轮给的样本，而我照收了：`AG0`/`RB0`/`CU0` **全是上期所**、
> `M0` 是大商所，**只有两家**。
>
> 更糟的是**我的探针复现了那个错**：它按「≥3 个品种同日为零」判，
> 而样本是上期所×3 + 大商所×1——**三个上期所品种就能触发**。
> 它检测的其实是「上期所那天为零」，**看不见交易所这一维**，
> 却因为跑出了同一组日期而被当成了独立验证。
>
> **两条路径得到同一个答案，不等于两条独立的路径**——它们共用了同一个有偏的样本。
> 评审 G1 把样本扩到五家才照出来。探针已改为每个交易所取一个品种、
> 按【交易所】数坏日，并把 CZCE 作为**阴性对照**（它若也进坏日名单，
> 说明故障模式变了）。

**重跑**

```bash
python tools/probe/probe.py --only settle-zero-shapes
```

探针对三种形态各有判据：中金所**必须仍然**系统性缺失（有值了要报，那是记录该更新）、
商品近期零值**不得**变多、并把「多品种同日为零」的日期单独列出来。

**为什么这条危险**：字段**永远在那儿**，`json` 解出来是 `0.0`，
拿去做逐日盯市会用结算价 0 算出一整天的灾难性盈亏，**全程不报错**。
这与第三节的「实时接口冻结」同族：**结构完整、数值合法、内容是错的**。

**处置（已成为接口约定）**：

- `sinasource` 把 `s == 0` **映射成 `NaN`**，绝不映射成 `0.0`；
- 记账内核那侧收到 `NaN` 或 `0` 都报错（**没有任何品种的结算价会是零，
  0 只可能是缺失的伪装**）。两侧各一道，原理不同，不会一起失效。
- **本库不再笼统承诺「结算价我有」**：可用性按 (品种, 区间) 报。

#### 中金所品种：别从新浪拿，从中金所官网拿

第一版这里写的是「**中金所品种要另找源**」，语气上接近「股指/国债没有结算价」。
下游记账内核顺着这条查下去，指出**中金所官网自己就有**。我复验，成立：

```
http://www.cffex.com.cn/sj/hqsj/rtj/202609/04/index.xml

IC2609  收=7608  结算=7604.8  昨结=7720.4
纯期货 28/28 全部有非零 settlementprice
```

字段还比新浪多：`presettlementprice`（**昨结算**，下游正是拿它推涨跌停）、
`openinterest` / `preopeninterest`、`expiredate`、`productid`。

**一个过滤坑**：这份 XML 里**期货与期权混在一起**——714 条里纯期货只有 **28** 条，
其余 686 条是期权。按 `instrumentid` 含不含 `-` 过滤（`HO2609-C-2500` 是期权）。

**所以正确的说法是分流，不是缺口**：

| 品种 | 结算价来源 |
|---|---|
| 商品（SHFE / DCE / CZCE / INE / GFEX） | 新浪日线 `s` 字段（2020 年起基本可用） |
| **中金所（IF / IH / IC / T / TF / TS）** | **CFFEX 官网日行情 XML** |

第七节把 CFFEX 记成了「可选的对账通道」——**它其实是中金所品种结算价的唯一可用源**，
定位要提。这条改变了 `cffexsource` 的排期地位：从「可选」变成 v0.2 必需。

> 这条值得记的地方在于**它是从一个措辞不严的结论里查出来的**。
> 我写的是「另找源」，读起来像「没有」；下游据此本来会去做降级设计。
> **一个不完整的结论和一个错的结论一样能传染**——这已经是本仓第三次撞到同一形态了
> （前两次：边界表少一列 `bar`、1023 根少一列品种）。

**重跑**

```bash
python tools/probe/probe.py --only cffex-settlement
```

日期**不写死**（会随时间前滚）：探针从今天往回最多找 12 天，取第一个能拿到 XML
的交易日，断言期货条数 > 0 且 `settlementprice` / `presettlementprice` 全部非零。

> 这条必须有探针，因为第七节自己记着：**四家交易所官网里三家被 WAF 挡**。
> 中金所今天开着不代表明天开着，而它现在是中金所品种结算价的**唯一来源**。
> 评审 G2 指出的——一条把 `cffexsource` 从「可选」升成「唯一」的结论，
> 却没有任何东西盯着那个端点。

顺带一条复核：非零结算价里 **97.7% 与收盘价不同**——再次印证「结算价推不出来」。

**合约代码的坑**：郑商所原生是 **3 位**合约码（`TA701`），新浪要 **4 位**
（`TA2701`）。3 位码跨十年有歧义（`TA701` 既可以是 2017-01 也可以是 2027-01），
本库内部**一律用 4 位**。大小写不敏感（`rb2701` 与 `RB2701` 返回完全相同）。

`TA701` 不报错，返回的是：

```
var _=(null);
```

**是 `null`，不是空数组。** 差别要紧：`json.Unmarshal` 到 `[]Bar` 会得到一个
`nil` 切片而非报错，`len()` 为 0，看起来和「这个合约当天确实没有数据」
一模一样。**把「代码写错了」和「这段确实没数据」渲染成同一个结果，
是本轮遇到的第三种静默失败。** 解析层必须把 `null` 与 `[]` 分开处理。

**重跑**

```bash
curl -s -H "Referer: https://finance.sina.com.cn" "https://stock2.finance.sina.com.cn/futures/api/jsonp.php/var%20_=/InnerFuturesNewService.getDailyKLine?symbol=RB0" | head -c 300
```

## 二、新浪：分钟线（能用，但有四个坑）

**端点**（`type` = 5 / 15 / 30 / 60）

```
.../InnerFuturesNewService.getFewMinLine?symbol=RB0&type=5
```

字段比日线少一个：`d o h l c v p`——**没有结算价**（分钟线本就没有），有持仓量。

### 坑一：硬顶 1023 根，且没有翻页参数

四个周期实测**全部恰好 1023 根**（以下是 **`RB0`** 的数）：

| type | 根数 | `RB0` 的覆盖区间 | 折合 |
|---|---|---|---|
| 5 | 1023 | 2026-08-17 → 2026-09-07 | 约 3 周 |
| 15 | 1023 | 2026-07-06 → 2026-09-07 | 约 2 个月 |
| 30 | 1023 | 2026-05-07 → 2026-09-07 | 约 4 个月 |
| 60 | 1023 | 2025-12-22 → 2026-09-07 | 约 9 个月 |

**上表的「折合」是 `RB0` 专属的，不是周期的属性。**
1023 是**根数**上限，而一个交易日出几根取决于该品种的时段总长，
于是**同样 1023 根，日历跨度按品种差近两倍**（同为 60m）：

| 品种 | 一个交易日的 60m 根数 | 窗口 | 折合 |
|---|---|---|---|
| `AG0` / `AU0` / `SC0`（夜盘 330 分） | 10（5 夜 + 5 日） | 2026-04-13 → 2026-09-07 | **≈4.8 个月** |
| `CU0`（夜盘 240 分） | 8 | 2026-03-04 → 2026-09-07 | ≈6.1 个月 |
| `RB0`（夜盘 120 分） | 6 | 2025-12-22 → 2026-09-07 | ≈8.5 个月 |

**夜盘越长的品种，窗口越短**——这和直觉相反（「数据多的品种能看得更远」）。

> 这条是评审 D1 指出的：上面那张按 `type` 分行的表，读起来像是
> 「60m 周期的深度是 9 个月」，而那只是 `RB0`。**一个不带前提的结论，
> 和一个错的结论一样能传染**——姊妹项目在「历史边界随周期而变」那条上
> 吃过完全一样的亏（表里少了一列 `bar`，被两个下游仓照抄）。
> 这次是少了一列**品种**。
>
> 对设计的影响是具体的：`Capabilities.Depth` **不能以 `Period` 为键**，
> 深度是 `(ProductKey, Period)` 的属性。见 design.md 第五节。
>
> 另外值得记一句：窗口最短的正好是 `au`/`ag`/`sc`，也就是
> `grid-phase-constant` 依赖的那三个品种。今天窗口里有 2 个停夜盘日不算紧张，
> 但那是全仓最短的窗口——所以那条探针取不到对照日时报 **SKIP** 而不是 FAIL。

**没有发现任何分页 / 起止时间参数。** 这意味着从新浪拿到的分钟级历史深度上限
就是这个数，**且过去的分钟数据一旦滑出窗口就永远取不回来**。

> **已解决（见第六节）**：天勤的 `KQ.m@SHFE.rb` 1m 有 **890,231 根**，回溯到
> 2016-01-04。所以新浪的分钟线降级为**对账通道**，不作主数据源。
> 这一条曾是本项目「唯一的硬缺口」，也是去接第二个数据源的唯一理由——
> 现在理由兑现了。

### 坑二：K 线按【收盘时刻】标注，且休市段直接消失

2026-09-04（周五）RB0 的全部 5m 时间戳：

```
09:05 09:10 ... 10:10 10:15 | 10:35 10:40 ... 11:25 11:30 |
13:35 13:40 ... 14:55 15:00 | 21:05 21:10 ... 22:55 23:00
```

三件事同时被这一行确定下来：

1. **首根是 `09:05` 而不是 `09:00`** → 标注的是**收盘时刻**，与 OKX 等加密源
   （标注开盘时刻）**相反**。
2. `10:15` 之后直接跳到 `10:35`，**没有 10:20 / 10:25 / 10:30**
   → 休市段不占位，不是空洞，是根本不存在。
3. 夜盘 `21:05`–`23:00` 挂在 **2026-09-04** 名下 → 新浪按**自然日**标注。
   但按中国期货的规则，周五夜盘属于**下周一（09-07）的交易日**。
   **两套日期口径在这里分叉**，见第六节。

### 坑三：高周期是「交易时间轴计数聚合」，会跨休市段

同一天的 15m / 30m / 60m：

```
15m: 09:15 09:30 09:45 10:00 10:15 | 10:45 11:00 11:15 11:30 | 13:45 ... 15:00 | 21:15 ... 23:00
30m: 09:30 10:00 10:45 11:15 | 13:45 14:15 14:45 15:00 | 21:30 22:00 22:30 23:00
60m: 10:00 11:15 14:15 15:00 | 22:00 23:00
```

规则是**按「实际交易了多少分钟」累计**，而不是按时钟网格对齐：

- 30m 的 `10:45` 那根 = `10:00–10:15` + `10:30–10:45`，**跨了上午的休市段**；
- 30m 的 `13:45` 那根 = `11:15–11:30` + `13:30–13:45`，**跨了午休，且横跨上下午**；
- 30m 的 `15:00` 那根只有 15 分钟（`14:45–15:00`），收盘强制截断。

**15m 是个例外**：三个日盘时段的长度（75 / 60 / 90 分钟）都是 15 的整数倍，
所以「计数聚合」与「按时段对齐」在 15m 上**恰好给出相同结果**。
只在 30m / 60m 上才分得出来。

> 这一点值得单说：**如果只测 15m，会得出「新浪是按时段对齐的」这个错结论**，
> 而且测试全绿。分辨两种规则必须用 30m 或 60m。

### 坑三之二：网格在【交易日】边界重启，并跨越隔夜缺口——两个品种可以有不同的 60m 网格

上面只证明了「会跨休市段」，没证明网格从哪里起算、在哪里断。
用**夜盘长度不是周期整数倍**的品种可以一次问清楚。

沪银 `AG0` 夜盘 21:00–02:30 = **330 分钟**，330 / 60 = **5.5**，不是整数倍；
沪铜 `CU0` 夜盘 21:00–01:00 = 240 分钟 = 4×60，是整数倍。同一天的 60m：

| | 夜盘部分 | 日盘部分 |
|---|---|---|
| `CU0` 60m | `22:00 23:00 00:00 01:00`（4 根，整除） | `10:00 11:15 14:15 15:00` |
| `AG0` 60m | `22:00 23:00 00:00 01:00 02:00`（5 根 + 30 分钟余数） | **`09:30` 10:45 13:45 14:45 15:00** |

**两个品种的日盘时段完全相同（09:00-10:15 / 10:30-11:30 / 13:30-15:00），
60m 网格却整体错开 30 分钟。** 原因只有一个：`AG0` 夜盘余下的
`02:00–02:30` 那 30 分钟，**跨过了 02:30 到次日 09:00 这个 6.5 小时的隔夜缺口**，
与 `09:00–09:30` 拼成了一根完整的 60m，标注为 `09:30`。

30m 上则两者都整除（330/30 = 11，240/30 = 8），网格因此一致——
`AG0` 30m 夜盘正好 11 根：`21:30 22:00 22:30 23:00 23:30 00:00 00:30 01:00 01:30 02:00 02:30`。

**三条规则由此确定：**

1. 网格在**交易日开始**处重启（有夜盘的品种是 21:00，没有的是 09:00）；
2. 网格**跨越隔夜缺口**（02:30 → 次日 09:00）——因为夜盘与其后的日盘
   属于**同一个交易日**；
3. 网格在**交易日结束**处强制冲刷（15:00），最后一根可以是短的。

**代价**：`60m` 的网格**无法只从日盘时段推出来**，必须知道整个交易日
（含夜盘长度）。任何「对齐到整点」的实现，在 `AG0` 上会**每一根都错 30 分钟**，
而且序列看起来完全正常。

这条把「交易时间轴」从一个漂亮的抽象变成了**必需品**，见 design.md 第二节。

**重跑**

```bash
for s in AG0 CU0; do curl -s -H "Referer: https://finance.sina.com.cn" ".../getFewMinLine?symbol=$s&type=60"; done
```

比较两者日盘部分的标签是否错开。

### 坑三之三：相位是【品种常量】，不是当天算出来的——这条推翻了上面的模型

> **2026-09-07 修正。** 上一小节把规则写成「沿当天的 `Sessions` 累计交易毫秒」。
> 那个写法能解释全部已观察到的现象，但它有一个**可证伪的预言**，而实测把它证伪了。

长假前交易所**停夜盘**。按「沿当天实际时段累计」，停夜盘那天沪银没有 30 分钟的
夜盘余数，日盘就该从 09:00 干净地重开，网格退化成 `CU0` 那样。

实测两个停夜盘日（探针自动找出来的）：**2026-05-06**（五一后第一个交易日）与
**2026-06-22**（端午后第一个交易日）。

| 品种 | 标称夜盘 | 普通日的日盘网格 | **停夜盘日** |
|---|---|---|---|
| `AG0` / `AU0` / `SC0` | 330 分（对 60 余 30） | `09:30 10:45 13:45 14:45 15:00` | **一模一样** |
| `CU0` | 240 分（整除） | `10:00 11:15 14:15 15:00` | 一模一样 |

**沪银在没有夜盘的那天，日盘网格仍然是带 30 分钟余数的那一套。** 预言错了。

正确的规则是：

> **网格相位是品种的固定属性，等于「标称夜盘长度 mod 周期」，
> 与当天是否真的开了夜盘无关。**

沪银标称夜盘 330 分，`330 mod 60 = 30`，所以日盘第一根永远只装 30 分钟、
收在 `09:30`——哪怕这一天根本没有夜盘。

**为什么这条要紧**：照上一小节那个写法实现，会在**每个长假前后错一整天**，
而且只错 `au`/`ag`/`sc` 这类夜盘不整除的品种。一年有 7 个法定假期，
每个前后各若干天——**这是个一年错几十天、且只错部分品种的静默错误**。

置信度：「与当天实际交易无关」是**实测**（2 个停夜盘日 × 3 个品种）；
「相位 = 标称夜盘长度 mod 周期」这个公式是**推定**——它拟合了目前观察到的
全部数据，但只在 330 分与 240 分两种夜盘上验过。

探针 `grid-phase-constant` 钉住这一条，且它**自己去窗口里找停夜盘日**，
不写死日期（日期会随 1023 根的窗口滑出去）。

#### 判「有没有夜盘」的判据，第一版是错的

第一版判据是「**这个自然日有没有凌晨根**」——没有凌晨根就当成停夜盘。
它多报了两天，而且多报的**全是周一**。

原因：**周一的夜盘在上周五晚上开**（21:00），跨过午夜的那部分落在**周六**
那个自然日上。于是周一自己永远没有凌晨根——但它的夜盘明明开了。

正确的判据是看**上一个交易日的当晚**有没有 21:00 之后的根：

| 日期 | 上一交易日 | 上一交易日当晚 | 判定 |
|---|---|---|---|
| 2026-09-07（周一） | 09-04（周五） | 有 `22:00 23:00` | 夜盘正常 ✓ |
| 2026-05-06（周三） | 04-30（周四） | **无** | 停夜盘 ✓ |
| 2026-06-22（周一） | 06-18（周四） | **无** | 停夜盘 ✓ |

改判据后从 3 天收敛到 2 天，**结论不变**（那 2 天的网格仍与普通日相同），
但原来那个判据是在拿「周一」冒充「停夜盘日」，属于**证据不成立而结论碰巧对**。

> 这个 bug 是评审追问 A2 时查出来的。值得记的是它的形态：
> **一个错误的判据，恰好在这个数据集上给出了正确的结论。**
> 如果当初停夜盘日的网格真的变了，这个判据会因为混进周一而给出自相矛盾的结果，
> 那时才会发现——但那要等到下一次长假。

**重跑**

```bash
python tools/probe/probe.py --only grid-phase-constant
```

### 坑三之四：**以上三条只描述新浪。天勤用的是完全不同的另一套规则**

> **2026-09-07 三轮加测。** 评审 E1 提出「历史时段变更会翻转 60m 相位」，
> 我拿天勤 1m 去验，结果发现的是一件更基本的事：
> **两个数据源的聚合规则根本不是同一套。**

天勤同一天、同一品种的高周期：

```
天勤 60m: 09:00 10:00 11:00 13:00 14:00
新浪 60m: 09:30 10:45 13:45 14:45 15:00

天勤 30m: 09:00 09:30 10:00 10:30 11:00 13:30 14:00 14:30
新浪 30m: 09:30 10:00 10:45 11:15 13:45 14:15 14:45 15:00

天勤 15m: 09:00 09:15 09:30 09:45 10:00 | 10:30 10:45 11:00 11:15 | 13:30 ... 14:45
新浪 15m: 09:15 09:30 09:45 10:00 10:15 | 10:45 11:00 11:15 11:30 | 13:45 ... 15:00
```

**天勤 = 纯时钟网格，按【开盘时刻】标注，空桶省略、残桶保留。**

- 沪银 `ag2612` 与螺纹的 60m 标签**完全相同**（都是 `09:00 10:00 11:00 13:00 14:00`）
  ——**天勤这边没有「相位」这个概念**，330 分钟的夜盘不产生任何偏移；
- 30m 的 `10:00` 那根只装 `10:00–10:15`（**15 分钟**），因为 10:15–10:30 休市；
- 15m 在 `10:00` 之后直接跳 `10:30`。

**这不只是标注差异，是内容差异。** 同一段行情：

| | 新浪的 `10:45` 那根 | 天勤对应的两根 |
|---|---|---|
| 装什么 | `10:00–10:15` + `10:30–10:45`（30 分钟） | `10:00` 装 15 分钟，`10:30` 装 30 分钟 |

**后果（改了 design 第二节的地位）：**

1. 「坑三 / 坑三之二 / 坑三之三」那一整套——交易时间轴、跨隔夜、相位是品种常量
   ——**只描述新浪**，不是中国期货的普遍规律。原文把它写成了后者，那是**过度概括**。
2. **1m 不受影响**：一根 1m 就是一根 1m，两个源在这个粒度上没有分歧。
3. 所以正确的做法是：**本库自己从 1m 聚合，用【一套本库明确选定并写下来的】规则**，
   两个源的高周期 K 线一律只作**对账**，不作真值。

**「用哪一套」现在是一个必须显式做出的设计决定**，而不是「照上游抄」。
两套都得实现（`AggClockGrid` / `AggTradingAxis`），默认取哪个**未验**——
要看国内主流软件（文华 / 博易 / 快期）用哪套，本库还没测。见 design.md 第二节。

> 这条也顺带回答了评审 E1：**「历史时段变更翻转相位」的风险对天勤数据不存在**
> （时钟网格没有相位可翻），对新浪数据仍然成立。而本库的深度数据源是天勤，
> 所以这条风险的影响面比评审估计的小——但**「本库自己选哪套聚合规则」这个新问题
> 比它大**。

**重跑**

```bash

（改成交易时间轴的话它们会错开 30 分钟）**且等于时钟网格 `09:00 10:00 11:00 13:00 14:00`**。

### 坑四：会返回一根【未完结】的当前 K 线，且标注的是【未来时刻】

探测时的墙钟是 **2026-09-07 13:19:54**，下午盘 13:30 才开。而此刻：

- 5m 序列最后一根 = `11:30`（正常，上午收盘那根）
- 30m 序列最后一根 = **`13:45`** ← 比墙钟晚 25 分钟
- 60m 序列最后一根 = **`14:15`** ← 比墙钟晚 55 分钟

那根 `13:45` 的内容 `o=3150 h=3152 l=3147 c=3150 v=932`，实际只装了
`11:15–11:30` 这 15 分钟的上午残段。也就是说：

**新浪把还在累积的那根 K 线一并返回，并给它打上「它将来会收盘的那个时刻」
作为标签，而且没有任何 confirm 标志。**

这比 OKX 的 `Confirm == false` 更难防——OKX 至少有个标志位。
这里要判断一根 K 线是否已完结，**必须先有交易时段表**：得知道 `13:45` 对这个
品种今天是不是一个合法的收盘时刻，以及那一刻是否已经过去。

**这直接决定了架构**：交易日历与时段表不是配套设施，是**判断数据是否可信的前置条件**，
必须做成一等公民。

**重跑**

```bash

curl -s -H "Referer: https://finance.sina.com.cn" ".../InnerFuturesNewService.getFewMinLine?symbol=RB0&type=30" | tail -c 200
```

盘中跑，对比墙钟与最后一根的时间戳。

## 三、新浪：实时行情【已冻结两年】

这是本轮探测里最要紧的一条，因为它**不报错**。

**端点**：`https://hq.sinajs.cn/list=RB0`（需 `Referer`，返回 GBK）

**返回**（2026-09-07 探测）：

```
var hq_str_RB0="螺纹钢连续,145957,3538.00,3556.00,3484.00,3544.00,3486.00,3487.00,
3487.00,0.00,3541.00,3,138,2186809,1578526,沪,螺纹钢,2024-07-17,0,...";
```

HTTP 200，字段齐全，数值合理，看不出任何毛病。但把它和日线序列对一下：

| | 实时接口 | 日线 2024-07-17 | 日线 2026-09-04（最新） |
|---|---|---|---|
| 开 | 3538.00 | **3538.000** | 3145.000 |
| 高 | 3556.00 | **3556.000** | 3180.000 |
| 低 | 3484.00 | **3484.000** | 3137.000 |
| 最新/收 | 3487.00 | **3487.000** | 3166.000 |
| 持仓量 | 2186809 | **2186809** | 1497791 |
| 成交量 | 1578526 | **1578526** | 877156 |

**六个字段逐位相同**，且它自己的日期字段就写着 `2024-07-17`。

结论：**`hq.sinajs.cn` 的期货实时行情自 2024-07-17 起冻结，至今两年零两个月。**
它仍然返回 200 和一份结构完整、数值合理的快照——这正是最坏的一种坏：
**不报错、不为空、看起来完全正常。**

新浪的 **K 线**接口是活的（更新到当天），**只有实时接口死了**。
两者同域名、同风格，很容易被当成一套东西一起信。

> 网上大量教程与开源库仍在用 `hq.sinajs.cn` 取期货实时价。任何直接照抄的人，
> 拿到的都是 2024 年 7 月 17 日下午 2 点 59 分 57 秒的那一帧。

**本库的处置**：不提供基于 `hq.sinajs.cn` 的实时源。若日后要接，
必须带一条**开机自检**——把实时快照与当日日线比对，冻结就直接报错，
而不是让它悄悄流进回测。

## 四、主力连续 `RB0` 是【未复权】拼接——实测虚增 1.5–1.7 个百分点

`RB0` 是什么，不能猜，得对出来。拿它和具体合约逐日比：

**最近 40 个交易日**：`RB0` 与 `RB2610` 逐位相同的有 **35 天**，
与 `RB2701` 相同的有 **5 天**——它是**主力连续**，会在合约间切换。
比对同时包含收盘价与持仓量，两个字段都相同才算命中，避免撞价。

**换月点实测**：

| | 2026-08-28 | 2026-08-31 | 涨跌 |
|---|---|---|---|
| `RB0`（主连） | 3112.0（跟 RB2610） | 3197.0（跟 RB2701） | **+2.73%** |
| `RB2610` 真实 | 3112.0 | 3143.0 | +1.00% |
| `RB2701` 真实 | 3158.0 | 3197.0 | +1.23% |

**主连在这一天显示 +2.73%，而无论持有哪一个合约，真实收益都只有 1.0%–1.2%。
凭空多出约 1.5–1.7 个百分点，而且是在一天之内。**

这不是新浪的 bug，是「未复权主力连续」的定义使然：切换那天前后两根来自
不同合约，中间的**基差**被当成了涨跌。螺纹钢一年换月 3–6 次，17 年的 `RB0`
上有上百个这样的接缝，**每一个都是凭空的收益或亏损**。

而它**完全静默**：`RB0` 的序列看上去连续、平滑、没有任何缺口标记。

**这条直接决定本库必须自己做换月拼接**：
以合约级序列为准，自己按明确的规则换月、按明确的方式复权，并把接缝位置
（`RollSchedule`）交出去，让回测能知道哪几天的收益不该算。
新浪的 `RB0` 只作**对账参照**，不作真值。

> 对比：okx-tickflow-go 明确写了「交割合约换月拼接——**不做**」。
> 加密市场的永续合约没有到期日，那个决定是对的。
> 中国期货每个合约都有交割月，**这里不做就等于没做**。

> ⚠️ **本文一度写着「反复续传到 28 MB 仍不到 10%」，那个失败有一半是我自己造的。**
>
> 我先后起了**两个后台续传循环，写同一个输出文件**。两个 `curl -C -` 并发
> seek / 写同一路径，把文件写坏了——坏的形状不是「末尾截断」，是**中间被打乱**：
>
> ```
> 出错位置前: ..."max_limit_ord 0     ← 键名被截断在中间
> 出错位置后: 
  },
  "DCE.pg2101": {...
> ```
>
> 而且文件涨到 43.9 MiB 之后，**解析错误仍卡在 16.36 MiB 那个位置不动**——
> 后面那 27 MiB 全是接在一处损坏之后的垃圾。
>
> **服务端没有问题**：它遵守 Range（206 + 正确的 `Content-Range`），
> 单个 Range 请求实测正常。**并发写同一文件是我的错，不是这个端点的属性。**
>
> 差一点就把它记成「这个端点的续传不可靠」——那正是「**报出一个失败时，
> 先问它是谁造成的；归错源头，缓解措施就会错**」的又一例。
> 若照那个错的归因写，缓解措施会变成「别用 `-C -`」，而真正该写的是
> 「**别让两个下载写同一个文件**」，以及「**用 Range 取片段，不整包下载**」。

> **本文这一节自己错过两次，两次都是同一个动作造成的**：
>
> | 我写过的 | 实际 |
> |---|---|
> | 「约 12.5 MB」 | **334 MiB**——差 **27 倍** |
> | 「服务端会**忽略** Range」 | 服务端**遵守** Range（`206 Partial Content` + 正确的 `Content-Range`） |
>
> 第一条是从**一份没拉完的文件**上量的（`ls -la` 量的是我下了多少，不是它有多大）；
> 第二条我没验就写了，而**它恰好让第一条无法被发现**——如果我当时相信 Range 可用，
> 随手一个 `curl -r 0-100` 就会把 `Content-Range` 里的总大小打出来。
>
> **两个错互相掩护：一个让我量错了大小，另一个让我不去用那个能量准的方法。**

**正确的做法**：**用 Range 取需要的片段，不要整包下载**。
要判断端点是否可用、结构是否还在、总量多大，一个 256 KB 的 Range 请求就够，
`Content-Range` 直接给出权威总大小。探针 `tq-trading-time` 就是这么做的。

**真要落地全量参考数据，334 MiB / 13 小时是个必须先摆到台面上的成本**，
不能像原文那样按「12.5 MB，慢一点而已」来规划。

下游把风险描述成「截断落在两条记录之间时 JSON 解析不会报错」。
**我验了，这个机制不对**——标准解析器对截断输入是会报错的：

```
截断在两条记录之间 → json.loads 报 JSONDecodeError   （不会静默）
【修补后】再解析     → 成功，静默少了 N 条            ← 危险在这
```

**真正的静默丢发生在「自作聪明的修补」上，不在解析器上。** 结论他们是对的，
机制要说准，因为**缓解措施不同**：不是「加一道解析校验」，是**不要修补**。

**而我自己就干了这件事。** 分析这份目录时我写过：

```python
i = s.rindex('\n  },')          # 切到最后一个完整条目
d = json.loads(s[:i+4] + '\n}') # 自己补上闭合括号
```

| | 本文记的 | 实际含义 |

同一份文件里，每个条目都有 `class` 也都有 `exchange_id`，两个合计**必然相等**。

**同一份文件里两个合计永远相等**——这正是「截断」解释不了 2003 的原因。）

> **`refdata/shinnyref` 落盘前必须校验完整性**（能**不加补全**地完整解析），

### 6.1 鉴权：客户端不是公开的

第一轮探测（无凭证）只能确认端点存在。拿到账户后逐个试 client_id，
**错误信息本身就是索引**：

| 返回 | 含义 |
|---|---|
| `Client secret not provided in request` | 客户端**存在**，但是机密客户端 |
| `INVALID_CREDENTIALS: Invalid client credentials` | 客户端**不存在** |
| 200 + access_token | 公开客户端 |

`shinny_web` 是公开客户端，能拿到 token——**但那个 token 没有 `futr` 权限**
（`grants.features` 只有 `opt cmb adv cnd`），连 websocket 会被拒。

正确的客户端是 `shinny_tq` + 一个 client_secret，**硬编码在开源的 tqsdk 包里**
（`tqsdk/auth.py` 的 `_request_token`，PyPI 上人人可下）。用它拿到的 token：

```
grants.features = [adv, cmb, lmt_idx, opt, tq_trading_status,
                   tq_bt, tq_rank, futr, tq_lc_rk, tq_ma]
```

有 **`futr`**（期货行情），这才是关键的那一位。token 有效期 **63072000 秒（两年）**。

#### 这个值不进本仓——以及一次照实记录的历史重写

`client_secret` **不写死在本仓**：探针从 `SHINNY_CLIENT_SECRET`（环境变量或
仓库根 `.env`）读，缺失则 SKIP。理由不是「保密」——它公开印在 PyPI 的 tqsdk 包里
（`tqsdk/auth.py` 的 `_request_token`），谁都能 `pip download tqsdk` 读到——
而是 contract.md 的缓解措施写着「**不设默认值，必须显式提供，让这成为明确的一步**」，
而探针也是本仓的一部分：clone 下来直接跑就用上那个身份，缓解措施就被本仓自己的
工具绕过了。**「可被发现」不等于「可被转发」。**

**但它一度确实进了本仓的公开历史。** 2026-09-07 评审指出：我当时的 `grep -rn`
查的是**工作树**，不是历史；值仍在已推送的两个 commit 里。处置：

- 对分支做了历史重写（`git filter-branch` 把该值替换成占位符）并 `force-push`；
- 重写后 `git rev-list` 全链 grep **零命中**，HEAD 树与重写前**逐字节一致**。

**照实记一条**：GitHub 对被弃置的 commit 对象会**保留一段时间**——重写后立即验，
旧 SHA 经 API 仍返回 **HTTP 200**。所以这是「**大幅降低**」而不是「**彻底消除**」。
写成后者是不诚实的。

> 评审 F4 的原话值得留着：「**不能选一条又写另一条**」——
> 要么重写历史，要么照实写「历史里还在」。这里两件都做了：重写了，
> 也照实写了它没能做到的那一半。

> **这是一处明确的脆弱点**：client_secret 是从对方 SDK 里读出来的，
> 不是给我们的。它随时可以轮换，轮换了本库当天就连不上。
> design.md 把它记成「推定」并要求实现层把它做成**可配置**而不是编译期常量。

### 6.2 行情地址来自名称服务，不是硬编码

之前一直在猜域名（试过 `openmd` / `api` / `free-api` / `u`），全错。
tqsdk 的做法是问名称服务：

```
GET https://api.shinnytech.com/ns?stock=false&backtest=false
    Authorization: Bearer <token>
→ {"mdurl": "wss://free-openmd.shinnytech.com/t/md/front/mobile"}
```

真正的地址是 **`free-openmd`**——恰好是没试过的那个。`backtest=true` 返回同一个。

**所以实现层必须走名称服务**，不能把域名写死：对方按账户/负载返回不同地址，
写死就等于给自己埋一个「换了账户就连不上」的雷。

### 6.3 gorilla/websocket 连不上这个服务——依赖选型被推翻

裸连 `free-openmd` 一直是 **400 Bad Request**，加不加 token 都一样。
响应体是 12 字节的 `Bad Request` 且带 `Sec-Websocket-Version: 13` 头——
这是 Go 的 `http.Error(w, http.StatusText(400), 400)` 的特征，
说明**对方也是 Go 服务，且是握手本身被拒**，与鉴权无关。

用 Python 的 `websockets`（tqsdk 用的那个）连**成功**，返回
`{"aid":"rsp_login","session_id":"MDSESSION"}`。于是把两边的握手抓下来对比
（起一个本地 TCP 监听打印原始请求）：

```
gorilla:  GET ... Connection: Upgrade / Sec-WebSocket-Key / Sec-WebSocket-Version: 13 / Upgrade: websocket
python :  同上，外加  Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits
```

**唯一的差别是 `permessage-deflate`。** 服务端**要求**这个扩展。

给 gorilla 开 `EnableCompression: true` 之后握手过了（**101 Switching Protocols**），
但 gorilla 随即报 `websocket: invalid compression negotiation`——因为服务端回的是

```
Sec-Websocket-Extensions: permessage-deflate; server_no_context_takeover
```

而 gorilla 客户端对这个响应头做**精确字符串比较**，只接受
`permessage-deflate; server_no_context_takeover; client_no_context_takeover`
（两个参数都要）。少一个就判定协商失败。

换 `github.com/coder/websocket` + `CompressionMode: CompressionNoContextTakeover`，
**一次就通**。

> **结论：主模块的 websocket 依赖从 `gorilla/websocket` 改为 `github.com/coder/websocket`。**
> 这不是偏好问题——gorilla 在这个服务上**根本连不上**，且失败信息
> （400 Bad Request）完全指不到真正的原因。
>
> 这条也是「先探针后写码」的直接回报：设计文档第一版把依赖写成 gorilla，
> 真动手才发现连不上，那时候 `Source` 层已经照着 gorilla 的 API 写完了。

### 6.4.1 关键的一环：【已到期】合约还供不供分钟线

上面两行**不足以支撑「硬缺口已解决」**，而这一点差点被漏掉。

`KQ.m@SHFE.rb` 那 89 万根是**主力连续**，而 6.5 恰恰证明了它**未复权**——
按 design 第八节的立场，主连只作对账，**真值必须是合约级序列，换月自己做**。
于是要自建 2016 年至今的分钟级主连，需要的是 `rb1605`、`rb1801` …
这一长串**早已到期**的合约的 1m 历史。

**如果免费档只给在市合约，缺口没有被解决，只是从「新浪 1023 根」挪到了
「天勤只给在市合约」——而且更隐蔽，因为表面上有 89 万根。**

实测（`SHFE.rb2701` 是在市的，其余全部早已到期）：

| 合约 | 到期 | 总根数（1m） | 最早 |
|---|---|---|---|
| `SHFE.rb1605` | 2016-05，**十年前退市** | 39,600 | 2016-01-04 09:00 |
| `SHFE.rb1801` | 2018-01 | 84,180 | 2017-01-16 21:00 |
| `SHFE.rb2310` | 2023-10 | 82,770 | 2022-10-17 21:00 |
| `SHFE.rb2410` | 2024-10 | 82,305 | 2023-10-16 21:00 |
| `SHFE.rb2701` | 在市 | 53,337 | 2026-01-15 21:00 |

**四个已到期合约全部供得出完整生命周期的 1m 历史。** 缺口确实解决了，
v0.4 自建主连成立。

`rb1605` 最早那根是 `2016-01-04 09:00`（日盘），其余都是 `21:00`（夜盘）——
因为 2016-01-04 是**地板线本身**，那天是元旦后第一个交易日、**没有夜盘**，
所以它的交易日从 09:00 起算。与坑三之三的停夜盘结论自洽。

> 这一条是评审 D2 逼出来的。原文只有主连与在市合约两条证据，
> 而**「主连不能当真值」正是我自己在 6.5 写下的**——证据链缺的那一环，
> 恰好被两条相邻的结论各自遮住了一半。

**对比新浪的 1023 根硬顶：分钟级深度历史的硬缺口就此解决。**
`from` 给到 2010 也只返回到 2016-01-04，所以 **2016-01-04 是这个免费档的历史地板**
（主连与 `rb1605` 两条独立序列都停在这一天；是否**所有品种**都是这条线，**未验**）。

**顺带确认了一件与本库时间模型直接相关的事**：
`KQ.m@SHFE.rb` 的 1m 最早是 `2016-01-04 21:00`（周一夜盘），
日线最早是 `2016-01-05 00:00`。也就是说

> **天勤的日线按【交易日】标注（午夜零点），新浪按【自然日】标注。**

周一夜盘 21:00 在天勤那里属于 `01-05` 这根日线，在新浪那里挂在 `01-04` 名下。
**两个源的日期口径相反**，混用就会整体错位一天。这条进 contract.md 的风险表。

### 6.5 天勤的主力连续【也是未复权的】，而且符号会反

第四节实测了新浪 `RB0` 未复权。天勤有自己的主连 `KQ.m@SHFE.rb`，
必须单独验——不能假定它已复权。

拿它和两个真实合约的日线逐日比（都取自天勤，避免跨源口径差异）：

它在 **2026-09-02** 换月（新浪 `RB0` 是 **08-31** 换——**两家的换月规则不同**）。

### 6.6 实时，以及**未完结标志位：没有，但有更好的东西**

连上后 `set_chart` 返回的最后一根就是当前正在走的那根（探测时是 `2026-09-07 14:10`，
盘中）。实时通道可用。

**未完结标志位：结构性不存在。** 这是本文未验表里最要紧的一条，已实测（15:59，收盘后）：

```
kline 对象的字段: [close close_oi datetime high low open open_oi volume]
```

最后一根与倒数第二根的**字段集完全相同**——所以这不是「标志位为 false」，
是**根本没有这个字段**。

> 这个区分是下游记账内核提醒的，它踩过同一个坑的另一面：
> 免费行情网关**不下发静态合约字段**（`volume_multiple` / `price_tick` 等全是 `null`），
> 它一度把「字段有值」写进就绪判据，于是行情到齐了却报「未就绪」，
> **提示语还写着「可能非交易时段」——一个把自己的 bug 说成环境问题的判据**。
> 「拿不到」与「值为否」必须分开判，否则会把前者读成后者。

**但序列节点上有更有用的东西**：

```
last_id              = 53339
trading_day_start_id = 52995
trading_day_end_id   = 53339        ← 53339 − 52995 + 1 = 345 根
trading_day_length   = 5190
market_time_length   = 1240
```

**345 = 225（日盘分钟）+ 120（螺纹夜盘分钟）**——正好是 `rb` 一个交易日的分钟数。
**上游直接给出了交易日的 bar-id 边界**，不用本库自己数。

如果 `trading_day_end_id` 是**预知的**（交易日一开始就知道末根 id），
那么「`last_id < trading_day_end_id` ⇒ 最后一根未完结」就是一个比 confirm 标志
更强的判据——它还顺带给出交易日边界。

### ✅ 2026-09-07 21:16 夜盘实测：**是预知的**

```
此刻 2026-09-07 21:16:25（夜盘时段）
KQ.m@SHFE.rb  last_id=890296  最新=2026-09-07 21:16（0.0 天前）    ← 确在盘中
对照 SHFE.rb1605   最新=2016-05-13 14:59（3769.3 天前） 陈旧 ✓
对照 KQ.m@GFEX.si  最新=2026-09-07 14:59（0.3 天前）   陈旧 ✓     ← 夜盘时段，该对照组适用
trading_day_start_id=890280  end_id=890624  跨度=345  已到 17 根
腿① end_id(890624) > last_id(890296)，领先 327 根        ⇒ 预知
腿② rb 跨度=345（实到 17）= 标称；ag 跨度=555（实到 17）= 标称  ⇒ 预知
⇒ 结论：预知
```

**两条腿一致，且各自会因不同原因失败**：腿①比 `end` 与 `last`，
腿②只看跨度、不依赖 `last_id`——夜盘刚开 17 根而跨度已是整日的 345，
这一条单独就足以定论。

所以「`last_id < trading_day_end_id` ⇒ 最后一根未完结」**成立**，
而且上游直接给出了交易日的 bar-id 边界，不用本库自己数。

**探针已从「提问期」转成「守基线期」**（`baselineAnswer = "预知"`）：
测出的结论与基线不符即 `FAIL`。已验它承重——把基线改成「不预知」重跑，
当场 `FAIL` 并打出「基线记的是「不预知」，这次测出「预知」」。

> 转换时机就是拿到定论那一刻，不能拖：提问期的 `PASS` 同时承载
> 「预知」与「不预知」两个相反结论，**退出码分不开它们**。
> 不转，就等于在拿到答案的同时永久丧失了发现答案翻转的能力。

#### 两次独立观测把「单点」变成了「靶子」

评审方 21:22 独立跑了一次（我那次 21:16）：

```
             21:16      21:22
last_id      890296     890302     ← 走了 6 根 = 6 分钟
end_id       890624     890624     ← 【纹丝不动】
```

我那次是「某一刻 `end > last`」——**单点**。两次放在一起，它变成
「**`end` 是一个固定的靶子，当天在朝它走**」。

差别不只是更硬：单点**排除不掉**「`end` 只是恰好被某个已到的东西撑大」，
两点能。**单点比的是两个量的大小，两点比的是它们各自的动静**——
后者才分得出谁是因、谁是果。

而强的那个证据不来自更聪明的方法，来自**同一个方法的第二个采样点**。

#### 它【没有】证明的三件事

1. **只在主连（`KQ.m@`）1m 上、两个品种、一个时刻测过。** 合约级序列、
   其它周期、已到期合约是否同样预知，**未验**。
2. **没有证明那个预知值是【对的】。** 跨度 345 恰好等于**标称**每日分钟数
   （225 日盘 + 120 夜盘），这说明它多半是**照标称模板算出来的**——
   那么**停夜盘那天它会不会仍然预测 345**？若会，就是多预测了 120 分钟，
   于是那天的最后一根永远等不到 `last_id == end_id`，
   「判完结」会在长假前后**永远判不出完结**。**未验，须在停夜盘日复跑。**
3. **没有证明它在盘中会随情况修正。** 上面两条合起来意味着：
   这个字段可能是一个**一开盘就定死的标称预测**，而不是一个跟着实际走的量。

⇒ **判完结仍然以交易日历为准**，`trading_day_end_id` 作为天勤源的
交叉校验与边界提示；第 2 条验掉之前，不把它单独当作完结判据。

#### 第 2 条已焊进探针 `shinny-suspended-night-span`，不靠人记着

原来那条写的是「须在停夜盘日复跑」——**一件靠人记住的事**。
而「记得三周后跑一次」比手验还弱一档：手验至少发生过，
它连发生都取决于有没有人想起来。

判据用 J1 那轮确立的正确形式——**本交易日第一根 `bar[startID]` 的时刻**：

```
21:00 起 → 那天有夜盘 → 本题不适用 → SKIP
09:00 起 → 那天停了夜盘 → 断言跨度
    跨度 == 225 ⇒ 按当日实际算（好）
    跨度 == 345 ⇒ 按标称算 ⇒ 那天永远等不到 last_id == end_id
```

**不用「本自然日有没有凌晨根」**：周五夜盘的凌晨部分落在【周六】的日期上，
那个判据会把每个周一误判成停夜盘日。

**对照组要成对**，因为「一个恒返回 09:00 的读法会让每一天都像停夜盘日」：

| 对照 | 标称 | 期望读出 |
|---|---|---|
| `KQ.m@GFEX.si` | 无夜盘 | `09:00` —— 09:00 那一侧的正例 |
| `KQ.m@SHFE.ag` | 330 分 | 普通日 `21:00` —— 21:00 那一侧的正例 |

2026-09-07 21:34 实跑，两侧正例同时出现（si 读 `09:00`、ag 读 `21:00`），
rb 读 `21:00` ⇒ 今天不是停夜盘日 ⇒ SKIP。

> ⚠️ 第一版这对对照组在【停夜盘那天】会退化：商品夜盘品种实践中一起停，
> 那天 `ag` 也读 `09:00`，「21:00 那一侧的正例」**在恰恰需要它的那一天不存在**。
>
> ⇒ **对照组会不会在你最需要它的那天失效，是设计对照组时的第一问。**
> （我是**做完才问**的；评审给了解法。）
>
> **解法：换一个不会一起退化的**。加 `KQ.m@CFFEX.IF`：
>
> | 对照 | 读出 | 停夜盘那天会不会退化 |
> |---|---|---|
> | `KQ.m@GFEX.si` | `09:00` | **不会**——它本来就没有夜盘 |
> | `KQ.m@CFFEX.IF` | `09:30` | **不会**——同上，且是第三个不同的值 |
> | `KQ.m@SHFE.ag` | `21:00` | 会（仅普通日有效，保留作参考） |
>
> 关键性质：**中金所本来就没有夜盘，所以「夜盘停了」对它的第一根时刻毫无作用**。
> si + IF 合起来，**任何一天**都给出两个不同的已知值，
> 于是「恒返回某个常量」的读法当场露馅——不管那个常量是几点。
>
> 期望值 `09:30` 是**从实测写死**的，**不读 `calendar/embedded`**。
> 这条不是洁癖：写这段时 embedded 的国债那一行正好是错的（`09:15`）——
> **拿本库的表当期望，表错了就把错误抄进了探针。**

在分辨之前，**判完结仍然只能靠交易日历**——即本库时间模型的那条主线不变。

`trading_day_length` / `market_time_length` 的单位与含义**未验**，
不做推测（5190 与 1240 都对不上分钟数或秒数）。

#### 已把它写成探针 `shinny-trading-day-predicted`（v0.1）

判据只在**盘中**成立：

```
trading_day_end_id > last_id  ⇒  预知
```

两条**会因不同原因失败**的腿，所以是两条腿：

| 腿 | 看什么 | 判「预知」的形状 |
|---|---|---|
| ① | `end_id` 与 `last_id` 比 | `end_id > last_id` |
| ② | `end − start + 1` 与**标称**每日分钟数比 | 跨度已是 345，而实到才 ~30 根 |

腿②**不依赖 `last_id` 的取值**。

**怎么证明「此刻真在盘中」——三道，坏法各不相同**：

「收盘时跑出来的 `end==last`」与「盘中跑出来的 `end==last`」**长得一模一样**，
而只有后者是有意义的否定结论。

| # | 检查 | 它挡的是 |
|---|---|---|
| ① | 墙钟落在 `rb` 公布的时段内（21:00–23:00 / 09:00–10:15 / 10:30–11:30 / 13:30–15:00） | **根本没开市**。这一条**不看数据只看钟**，所以新鲜度判据再松也绕不过去 |
| ② | `KQ.m@SHFE.rb` 最新一根距 now ≤ 5 分钟 | 开市了但喂不过来，或今天是节假日（①不认节假日） |
| ③ | 对照组必须**陈旧** | **新鲜度判据自己坏了** |

①的时段是照交易所公布**写死在探针里**的，**刻意不 import 本库的日历**——
探针要断言外部世界长什么样；拿本库的日历去验本库，日历错了两边会一起错，
那就不是两条独立的路。

③ 有**两个**对照组，前提不同、**覆盖面也不同**：

| 对照组 | 何时适用 | 挡得住 | 挡不住 |
|---|---|---|---|
| `SHFE.rb1605`（已退市，序列停在 2016） | **任何时刻** | 判据恒返回「新鲜」 | 阈值从 5 分钟松到几小时——它照样陈旧 |
| `KQ.m@GFEX.si`（无夜盘，6.6 实测） | **仅夜盘时段** | 小时量级的松动 | 日盘时段不适用——**GFEX 有日盘** |

⇒ 覆盖面**不对称**：夜盘时段两个都在（强），日盘时段只有退市那个（弱）。
这一点探针会在输出里明说，而不是含糊过去——
**「得出了结论」和「结论有多硬」是两件事**，把后者含糊掉，
下一个人会按夜盘那一次的强度去信日盘这一次。

任一不成立 ⇒ **SKIP，不出结论**。

> **评审 J1**：第一版只有 `GFEX.si` 一个对照组，**且不分时段**。
> 而 GFEX 有日盘（`09:00-10:15 / 10:30-11:30 / 13:30-15:00`，6.6 实测过），
> 所以白天跑会走进「对照组也新鲜 ⇒ 新鲜度判据坏了」——
> **SKIP 是对的，归因是错的**。而错的归因会把下一个人送去查时区和时钟，
> 那里什么也没有。
>
> 修的时候差点换来另一个洞：只把 GFEX 标成「日盘不适用」的话，
> 判据一旦松到几小时，日盘时段就没有任何东西拦得住了——
> 老版本会（因为错的理由）SKIP，新版本反而会给结论。
> ①那道墙钟检查就是为此补的：**它和数据侧的坏法完全不相干**。

> **这条对照组是被自己验过的**（2026-09-07 19:12，收盘时段）：
> 把新鲜度阈值从 5 分钟放宽到 24 小时（模拟判据坏掉），
> **拆掉对照组**的那一版当场给出
> `[PASS] … 腿① end_id == last_id，而此刻确在盘中 ⇒ 不预知`
> ——一个**自相矛盾却看起来完全正常**的结论（那一刻市场已收盘 4 小时）。
> 装着对照组的那一版则拦在 SKIP。
>
> ⇒ 对照组不是装饰。**「没检测到」与「不存在」长得一样**，
> 这类断言必须自带一个已知为真的负例。
>
> 但**焊了对照组 ≠ 对照组在承重**——得拆一次，看它塌。上面就是拆过的记录。

**拿到定论那一刻要把探针从「提问期」转成「守基线期」。**
提问期的 `PASS` 同时承载「预知」与「不预知」两个**相反**的结论，退出码分不开它们。
于是答案一旦翻转——上游哪天改了这个字段的行为——探针照样 `PASS`，
**而那正是探针存在的理由**。转换点在代码里备好了（`baselineAnswer` 常量，
现为空串＝尚未定论）；填上之后，测出的结论与基线不符即 `FAIL`。
不转，就等于在拿到答案的同时永久丧失了发现答案翻转的能力
——同「一个会红的必过项迟早被加 `|| true`」「一位总亮着的标志等于没有这一位」。

**「不预知」是合法结论，不是 FAIL。** 本探针是去**判定一件未验的事**，
不是守一条已知基线；把真实的否定结论标成 FAIL，等于逼着后来的人改判据迎合期望。
`FAIL` 只留给**讲不通**的状态：两条腿互相矛盾，或 `end_id < last_id`。

**2026-09-07 19:11 收盘时段的实测（仍不可分辨，但有新数）**：

验本库」搞混——那条说的是不能用本库的日历给探针自己当**对照组**
（日历错了两边会一起错）；这里方向相反，是对的。

> **但这个 import 有代价，要说明白。** 在 `template.go` 之前，
> 「探针不 import 本库」是被**模块边界强制**的——写错了编译不过。
> 现在探针模块 `require` 了本库，**那道结构保障没了，只剩一条注释**。
>
> 所以补了 `independence_test.go`：`main.go` / `tradingday.go` 不许 import 本库，
> 且**新加的探针文件必须显式落进白名单或豁免表**——
> 因为这道保障最可能的失效方式不是有人违反它，是有人**绕过了它而不自知**。
>
> ⇒ **一条刚刚失去结构保障的约定，要么补一道机械检查，
> 要么承认它已经不是约定了。**

> ### ⚠️ 这条探针发出过一条【没有依据的指控】（2026-09-07 22:0x，评审抓到）
>
> ```
> KQ.m@SHFE.rb  日盘实测 09:00-10:15 10:30-11:30 13:30-14:56
>               ≠  日盘内置 ... 13:30-15:00
> ```
>
> **内置表是对的，错的是取数。** 而它把这个读数渲染成了「内置时段表与实测不符」。
> 要不是评审那边有第二个客户端去对，结论会是「快改内置表」——
> **而那会把一张对的表改错。**
>
> **根因**：窗口锚在【起点】（`now − 10 天` 往后取 2000 根），
> 末端落在哪取决于品种每天多少根——`ag` 每天 555 根，2000 根只够 3.6 天，
> 末端就断在某个交易日中间。改成**锚在末端**（不给 `focus_datetime`）。
>
> **而这正是我在夜盘那一半守住、日盘这一半没守住的同一条**：
>
> > 找不到就报「取不到」，不返回 0——否则**一次取数失败会伪装成一条结论**。
>
> **两次修法之间的差别更值得记**：第一版判「完整」用「末根 ≥ 14:00」，
> 我修成「末根 ≥ 14:50」——**只是把余量收紧了，没有把判据换成精确的**，
> 于是同一个 bug 换了个幅度又回来了（这次缺到 14:56）。
>
> > **一个探针的正确性如果依赖「恰好够」，那它就是「迟早会错」**（评审语）。
> > 而更糟的是，它错的时候**不是沉默，是发出一条指控**。
>
> 现在的判据是精确的：**窗口里必须还有更晚的自然日**，那证明末端越过了这一天。
> （中间还踩过一次：一根孤零零的实时根让这条判据也被骗过——
> 直到把每个自然日的根数打出来才看见。）
>
> **最后一条改动才是真正对症的**：把「窗口覆盖到哪」**打进输出**：
>
> ```
> KQ.m@CFFEX.T   2026-09-04  日盘实测 09:30-11:30 13:00-15:15   [窗口 2000 根 08-27→09-07]
> ```
>
> 写注释时我是小心的——甚至专门算过「对 rb 恰好够」。
> **但那个量不在输出里，所以它变化时没有人会知道。**
> ⇒ **凡是要求「小心」的地方，先问那里是不是缺了一个可见的中间量。**
>
> **而根因我并没有完全定死，这一点要说清楚。**
> 我证明的是「窗口锚在起点会截断末端」（`ag` 的窗口断在 09-03 10:31，实测可见）；
> 但评审观测到的是**间歇**（22:07/22:08 红，22:09 起连续六次绿），
> **而间歇不是那个机制的形状**。他同一时刻用自己的客户端读到的是完整数据，
> 指向「快照还没收齐就判了」——另一个机制。
>
> 所以除了改锚定，还加了一条**与根因无关**的护栏：**读第二遍，两遍必须一致**，
> 不一致就报 `SKIP` 数据未收齐，**既不 PASS 也不 FAIL**。
>
> ⇒ **根因未定时，先让错误的形态变安全。**
> 一个**间歇的**错误指控比确定性的更糟：自然反应是「再跑一次」，
> 跑一次它就绿了，于是它永远不会被修，只会被**习惯**——
> 那就是 `|| true` 的形状，只不过不用谁去加那三个字符，**它自己会变绿**。
>
> 这一格原本是空的：`si`/`IF` 那对对照组张开的是**读数**维度，
> 而「读到的比实际少」属于**数据完整性**维度——**当时没有任何东西守它**。
>
> FAIL 的措辞也改了：原来写「改表，别改这条断言」——**那是在预设是表错了**。
> 现在先列「① 取数不全？看窗口 ② 表旧了？」，并写明「先排除①再动表」。

> **写这条时它自己出的两个岔子**，都属于「取不到和不存在长得一样」：
>
> 1. 「完整日盘」第一版只查了**末根晚于 14:00**——于是一个只剩 `14:59`
>    一根的截断日也算「完整」，拿它去比会比出一个**假的不符**。
>    否定式的判据（「没走完就跳过」）天然只看得住一头。
> 2. 取数窗口 300 根对 `rb` 恰好够一个完整日盘，对 `ag`（每日 555 根）就不够，
>    于是报「窗口里没有完整的日盘」——那看起来像数据的问题，
>    其实是**取数窗口**的问题。所以窗口被提成了显式参数。

## 八、这轮探测改变了哪些原本的设想

诚实记一下：动手探之前脑子里的几条，被实测推翻了。

| 原本以为 | 实测 | 影响 |
|---|---|---|
| 新浪实时行情能用（教程都这么写） | **冻结两年** | 实时源必须另找；且任何实时源都要加冻结自检 |
| K 线按开盘时刻标注（照搬 crypto 的直觉） | **按收盘时刻** | 内部要同时存开 / 收两个时刻，见 design.md |
| 高周期按时段对齐 | **按交易时间轴计数聚合，会跨休市段** | 聚合器不能用「时钟网格」实现 |
| 15m 能验证聚合规则 | **15m 上两种规则结果相同，验不出来** | 测试必须用 30m / 60m |
| 同交易所同日盘的品种，网格一样 | **AG0 与 CU0 的 60m 网格错开 30 分钟**（夜盘长度不同所致） | 网格必须按整个交易日算，不能只看日盘 |
| 未完结 K 线像 OKX 一样有标志位 | **没有标志，且标签是未来时刻** | 判完结必须先有时段表 → 日历成为一等公民 |
| 交易所官网能直接拉 | **四家里三家被 WAF 挡** | 官方源降级为可选对账 |
| 主力连续可以直接拿来回测 | **未复权，单日虚增 1.7pp** | 换月拼接必须自己做，且是核心功能 |
| 一张交易时段表够用 | **同品种不同合约时段不同（历史调整过）** | 时段表必须带生效区间 |
| 网格按当天实际交易的时段算 | **相位是品种常量，停夜盘日也不变**（坑三之三） | 长假前后会每天错一根，且只错部分品种 |
| websocket 库随便挑，gorilla 就行 | **gorilla 连不上天勤**（permessage-deflate 协商被它拒） | 主模块依赖改为 `coder/websocket` |
| 天勤的主连大概是复权的 | **也未复权，且换月日与新浪不同、符号会反** | 两个主连都不能直接用，也不能互相对照 |
| 两个源的日期口径一致 | **天勤按交易日、新浪按自然日** | 混用会整体错位一天 |

> 八条里有七条会**静默地**把回测结果变好看或变难看，没有一条会报错。
> 这也是为什么先探针、后设计——反过来做的话，上面每一条都会变成
> 「跑了半年才发现结果不对」。

## 九、重跑：`tools/probe/probe.py`

上面每一条的重跑命令都列在各节末尾，但零散地敲 curl 不会有人真去做。
所以做成了一个脚本，把**全部 14 条结论**一次跑完并与本文档记录的基线比对：

```bash
python tools/probe/probe.py                      # 全部
python tools/probe/probe.py --only sina-frozen   # 单条
```

2026-09-07 实测 **14/14 与记录一致**；另有 `tools/probe/shinny/` 的 Go 探针管天勤那一半
（**5** 条：鉴权 / 名称服务 / 深度 / 网格口径 / **GFEX 无夜盘**），见第六节。

其中两条是**专门用来分辨正确实现与错误实现**的，不是覆盖率填充：

- `grid-differs-by-night`：`AG0` 与 `CU0` 的 60m 网格**必须不同**。
  相同就说明退化成了时钟网格。
- `grid-phase-constant`：停夜盘日的网格**必须与普通日相同**。
  不同就说明实现按当天实际时段算了相位（坑三之三）。
  它自己去窗口里找停夜盘日，不写死日期。

**它是探针，不是测试。** 断言的是「外部世界现在是什么样」，不是本库的行为。
因此：

- 它**会**因为上游变化而失败，那正是它存在的理由；
- 失败**不代表本库有 bug**，代表本文档该更新了；
- 所以它**不进 CI 的必过项**——一个会因为别人改接口而红的必过项，
  迟早会被加上 `|| true`，然后就再也没人看了。

退出码：`0` 全部一致 / `1` 有偏离 / `2` 网络或解析失败（无法判断）。
**后两者分开**，因为「连不上」和「结论变了」是完全不同的两件事。

### 写这个脚本时自己踩了一次坑，值得记下来

第一版挑「倒数第二个自然日」来验证网格，结果 `CU0` 那条返回了**空列表**。
原因是：**周五夜盘 21:00 跑到周六 02:30，所以周六也有 K 线**——
按自然日倒数，取到的是一个只有夜盘残段、没有日盘的周六。

改成「最后一个含 `15:00` 标签的自然日」（只有走完整个日盘才有那一根）后正常。

> 这正是本库要解决的问题本身：**自然日与交易日不是一回事。**
> 一个刚把这件事写进设计文档的人，转头在自己的探针脚本里又踩了一遍——
> 说明它不是「知道就能避免」的那类坑，而是**必须由类型和 API 挡住**的那类。
> `TradingDay` 因此是一个独立的类型，而不是一个 `int32` 别名。

## 十、float64 → decimal：价格无损，但金额乘法不无损

下游的记账内核 [futures-position-simulator-go](https://github.com/dream-until-dawn/futures-position-simulator-go)
用 `shopspring/decimal`（钱不能有误差），本库用 float64（指标是热路径）。
边界画在哪，不能拍，要量。

**用中国期货的真实刻度量**（最小变动价位来自天勤 openmd 的 `price_tick`）：

```
float64 → decimal 往返：29/29 逐位无损
  国债 T tick=0.005   100.005 / 101.235 / 99.995 / 108.750
  沪金 au tick=0.02   512.34 / 512.36 / 1024.98 / 899.02
  股指 IF tick=0.2    3856.2 / 3856.4 / 4012.8 / 2999.6
  原油 sc tick=0.1，螺纹 rb tick=1，碳酸锂 lc tick=50，棕榈 p tick=2
  外加 0.1 / 0.2 / 0.3 / 2.675 这类二进制表示不精确的经典值
```

断言两条都成立：`decimal.NewFromFloat(f).InexactFloat64() == f`（**位相等**，不是近似），
且 `decimal.String() == strconv.FormatFloat(f,'f',-1,64)`（**逐位相同**，没多出尾数也没丢位）。

**但金额乘法不是无损的**——这才是要紧的那一半：

| 结算金额 | float64 | decimal |
|---|---|---|
| 螺纹 3166 × 10 吨 × 137 手 | 4337420 | 4337420 |
| **沪金 512.34 × 1000 克 × 8 手** | **4098720.0000000005** | **4098720** |
| 国债 100.005 × 10000 × 3 | 3000150 | 3000150 |
| 股指 3856.2 × 300 × 5 | 5784300 | 5784300 |

差 `5e-10` 元，小得可以忽略——**但它会随手数与天数累积，而且不报错**。

**结论（决定了对接层的形状）**：

- **价格与量用 float64 跨库传是安全的**；
- **金额运算必须在 decimal 那一侧做**。

所以本库**绝不预先算任何金额**，`价格 × 乘数 × 手数` 一律发生在记账内核内部。
见 design.md 第十二节。

**重跑**

```bash

```
