## ⛔ 勘误：v0.4.1 「自查」方法二自本版起失效

**v0.4.1 的 tag 注解里那一句（逐字，`git cat-file -p v0.4.1` 可取，改不了）：**

```
二、或跑一次 `Sync`，看 `rep.Gaps` 里有没有 `GapStoreUnverified`。
    ⚠️ 而它只在 `.meta` 还在时有效：删掉 `.meta` 之后那一段会报成「没拉过」（实测）。
```

🔴 **自本版起它不再管用，而失效的方式是【为真而有害】：照着做的人会得出「这个库没问题」。**

它在 v0.4.1 上管用，靠的恰恰是当时的一个缺陷。

**⇒ 而下面这两行不是推理，是【实测】** —— 同一份构造、两个底座各跑一遍，只有底座不同：

```
底座 2d9fa40（本版之前）  方法二 ⇒ 缺口：存储答不了·未走查  ⇒ 找得到 GapStoreUnverified ⇒ true  ✅ 管用
底座 ff1343b（本版之后）  方法二 ⇒ 缺口：存储答不了·走查没通过 ⇒ 找得到 GapStoreUnverified ⇒ false ⛔ 失效
                          方法一 ⇒ 两个底座上给出【同一句话】（记录的交易日不是非降序）⇒ 不受影响
```

⚠️ 而这两行由**两个人、两种构造**各量过一遍（倒序记录＋一段 · 零值记录＋两段），
结论相同 —— **出发点不同，所以这一致是加固的**。

> ⛔ **上面这两行是【那时】的读数**，里面的 `GapStoreUnverified` 与显示串「存储答不了·未走查」
> 都是**当时那个世界的名字**（本版之后它们已改名，见下面勘误二）。
> **全仓改名不许动它们** —— 动了就等于宣称「我们当时量到的是新名字」，而那不是真的。
> 🔴 一般化：**全仓改名的射程是【标识符】，不是【这个字符串】** ——
> 读数、引文、历史记录里的同一串字，指的是**那一刻的世界**，不属于改名的射程。
> ⇒ 判法一句话：**这一处说的是「现在应该怎样」还是「那时是怎样」？后者不动。**

机制（照着上面那两行读）：

```
v0.4.1 那一侧   损坏库 ＋ 再同步 ⇒ 落盘先失败 ⇒ 本次一段都没走查
                ⇒ 每一段报 GapStoreUnverified ⇒ 照方法二做的人【找得到】它 ⇒ 结论「库坏了」 ✅
本版            走查不再看「本次碰过什么」，而是按 coverage 的每一段走一遍
                ⇒ 坏库的每一段都走查过了、而且没通过
                ⇒ 它们报的是 GapStoreVerifyFailed，【不再是】GapStoreUnverified
                ⇒ 照方法二做的人【找不到】它 ⇒ 结论「库没问题」 ⛔ 而库是坏的
```

**改看这一类：**

```
GapStoreVerifyFailed   这一段走查过了，而它没通过 —— 真因在 rep.VerifyFailed 里（本版起；见勘误三）
```

⚠️ 而在 `rep.Gaps` 里找不到那一类，**不再是**「库没问题」的证据。

## ⛔ 勘误二：标识符 `GapStoreUnverified` 自本版起**不存在了**

```
旧标识符   GapStoreUnverified     （「存储答不了·未走查」）
新标识符   GapStoreVerifyUnrun    （「存储答不了·走查没跑成」）
```

**为什么改名，而不是留着它**：本版之后那一类只剩**一个**产生者 ——
**这一遍走查没能跑起来**（读盘失败一类）。而旧名字「未走查」读起来像一个常规状态，
它**掩盖了处置的分岔**：

```
GapStoreVerifyFailed   走查过了，而它没通过   ⇒ **别再重跑**，去读真因
GapStoreVerifyUnrun    走查**没跑成**         ⇒ **重跑是对的**
```

🔴 **而改名买的东西只有一样：一次响亮的失败。**

```
不改名        旧名字还在、还能编译，而它的意思变了 ⇒ 调用方的代码照常跑，**结论静静地错**
改名不留别名  旧名字没了 ⇒ 调用方的代码**编译不过** ⇒ 他被迫来查，而这条勘误接得住他
改名留别名    编译得过、行为照旧 ⇒ **把那一声响原样退款**
```

⇒ 所以**没有留 deprecated 别名**，那是有意的。而理由是**两条，各挡一半**：

```
不需要别名   旧名字的【指路】由这条勘误承担
             ⇒ **所以这条勘误不是可选项，它是「不需要别名」这条理由的前提**
不该有别名   别名会让调用方编译得过、行为照旧 ⇒ 把上面那一声响原样退款
```

⛔ **别把「旧名字在别处还 grep 得到」当成第一条的替代** ——
改名之后全仓 grep 旧名字会命中好几处（设计文档、测试、发布说明里的引文），而其中最要紧的两处性质完全不同：

```
v0.4.1 的 tag 正文  命中 ⇒ 读到的是【旧世界的说法】
                    ⇒ **死路**：它不知道新名字，也不知道自己已经失效
这条勘误            命中 ⇒ 读到「旧名字没了 · 新名字是什么 · 为什么改 · 要改什么」
                    ⇒ **活路**
```

🔴 **grep 得到 ≠ 被送到该去的地方。把人往前送的是这条勘误，不是那份历史记录。**

**照着做要改什么**：把代码里的 `GapStoreUnverified` 换成 `GapStoreVerifyUnrun`；
判两类时按上面那张处置表 —— **「没跑成」重跑，「没通过」去读真因**。

### ✅ 方法一不受影响 —— 它是仍然可用的那条路（`TestTagV041SelfCheckOneStillWorks` 每次跑测试都重量一遍）

```
一、对 `store.Coverage()` 的每一段跑 `store.Verify(span)`：
    坏掉的段返回「记录的交易日不是非降序」。
```

`Verify(span)` 在本版里**特意保留**（从 `Store` 接口降级成 `*segfile.Store` 的具体方法），
两条理由都不是兼容：**这条注解逐字点名了它**，以及它是新读法（`VerifyCoverage`）的**参照实现**。
⇒ `tag_selfcheck_meta_test.go` 里有三格守卫钉着这一节自查的三句话，其中一格钉的正是**本条勘误在**。

📎 **这条勘误是怎么被逼出来的**：本版计划里有一步「把那条钉住缺陷的守卫翻面」——
而**翻面的那一刻，就是方法二失效的那一刻**。那条守卫的红法二写在测试里，
🔴 **而受害者在 tag 里，他读不到我们的测试。**
⇒ 收：**一颗钉在现状上的钉子，它响的那一刻要连着问
「有没有哪份【不可修的东西】引用了这个现状」。**

## ⛔ 勘误三：走查失败自本版起**不再写进 `TruncatedTails`**（对 v0.4.1 调用方是一次静默变更）

**v0.4.1 里走查失败写在 `TruncatedTails`**（tag `v0.4.1` → commit `cb2a531`）：

```
sync.go:544  rep.TruncatedTails = append(rep.TruncatedTails,
sync.go:545      fmt.Sprintf("走查 %s..%s 失败：%v", sp.From, sp.To, err))
syncer.go:225    out = append(out, "开库时截过残尾："+s)      ← Incidents() 给这一栏的前缀
```

⇒ 于是 v0.4.1 的报告里，**一条走查失败被宣布成「开库时截过残尾：走查 … 失败：…」**。

**本版起**：走查失败写进新栏 **`VerifyFailed`**，`Incidents()` 前缀「走查没通过：」（与缺口类型
`GapStoreVerifyFailed`「存储答不了·走查没通过」逐字对齐）；**`TruncatedTails` 只剩开库截断（C3b）**。

🔴 **为什么这是一次静默变更**：`TruncatedTails` 这个名字还在、类型没变、编译照过 ——
一个在 v0.4.1 上**从 `TruncatedTails` 里找走查失败**的调用方，升级之后那一栏里**静静地找不到了**，
而不会有任何报错。⇒ 所以这条勘误不是可选项。

**照着做要改什么**：

```
v0.4.1 的写法   在 report.TruncatedTails 里找「走查 … 失败」
本版的写法     读 report.VerifyFailed；TruncatedTails 只用来看开库截断
只想知道库好不好  判 report.Complete() —— 两栏都进 Incidents()，任何一栏非空它都为假
```

## ⛔ 勘误四：v0.4.1 注解「处置」一节里的「再跑一次覆盖全区间的 `Sync`」—— 指纹仍然成立，而对照表与「只删 .dat」那一行过期了

**v0.4.1 的 tag 注解（`git cat-file -p v0.4.1`，「—— 处置 ——」那一节，改不了）教了三件事：**

```
甲  指纹：再跑一次覆盖全区间的 Sync，rep.Gaps 报「没拉过」＋ 同一次落盘被拒 ⇒ 顺序拉反了
乙  对照表：「正常重跑（库是好的）」与「顺序拉反了」并排，err / Halt / Complete() 取值一样 ⇒ 都不是判别符
丙  只删 .dat：能不能恢复取决于重拉顺序 —— 从早到晚拉 ⇒ 库修好了（而每条命令自己都报错）
```

本版的「跳过已覆盖的交易日」（上面第五条）改的正是「再跑一遍」这个动作。**逐格重量**
（探针：日历 0805/0806/0807/0810；源四天都给；segfile；每步印 err · Halt · Complete() · Gaps；
**同一份探针在 tag v0.4.1 与 23969cc 上各跑一次**（23969cc 到本 tag 之间没有改过非测试 .go）；源声明 `ClientUseNone`，免得「闸门没被用到」那一条把 Complete() 染成 false；⚠️ 探针没有入仓，照这一行的场景复现）：

### 甲｜指纹 —— **本版仍然成立**

```
先拉 [0807..0810] ⇒ 再拉 [0805..0806] ⇒ 照注解再跑一次 [0805..0810]：
  本版  err「落盘失败…交易日倒退了」· Halt = HaltStoreWrite · Complete() false
        Gaps = [0805..0806 没拉过 · 0808..0809 不是交易日]
        SkippedCovered = 「跳过 2 个已覆盖的交易日（0807..0810 之间），只拉剩下的 2 个」
```
⇒ 「『没拉过』＋ 落盘被拒」这一对照旧出现：早的那两天不在 coverage 里，**不会被跳过**，重拉时照样撞「交易日倒退」。

### 乙｜对照表 —— 「正常重跑」一列**整列过期**，「顺序拉反了」一列 Halt 换了名字

```
通道          正常重跑（库是好的）                    顺序拉反了（照注解再跑全区间）
              v0.4.1 实测        本版实测               v0.4.1 实测        本版实测
err           有                 nil                    有                 有
Halt          预算耗尽           HaltAllCovered         预算耗尽           HaltStoreWrite（见第八条）
Complete()    false              true                   false              false
Gaps          存储答不了·未走查  只有「不是交易日」     没拉过 ＋ 未走查   没拉过（不再带「未走查」）
```
⇒ 注解那句「`err` / `Halt` / `Complete()` 都不是判别符」**本版起在这两格之间不成立**：正常重跑 err = nil。
⚠️ 而**别反过来读成「err 非空 ⇒ 顺序拉反了」**：HaltStoreWrite 也是盘满 / 权限 / 文件被占的出口。
认「顺序拉反了」**仍然要看那一对**（甲）。

### 丙｜「只删 .dat」—— **本版上任何顺序都修不好了**

