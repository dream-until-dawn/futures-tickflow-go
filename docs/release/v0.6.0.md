# v0.6.0

## ⛔ 勘误一：v0.5.0 勘误四丙格「只删 .dat ⇒ 每条命令 err = nil 的死路」自本版起变了

**v0.5.0 的 tag 注解（`git cat-file -p v0.5.0`，勘误四「丙｜只删 .dat」那一格，改不了）写的是：**

```
本版    三种顺序每一条都是：err = nil · Halt = HaltAllCovered · Complete() false
        Gaps「存储答不了·走查没通过」· rep.VerifyFailed「走查数出 0 条，而 .meta 记的是 4 条」
        SkippedCovered「只拉剩下的 0 个」⇒ 一条都不重拉，.dat 一直是空的
⇒ 只删 .dat 在本版上是死路，而且每条命令都 err = nil。
```

**在 v0.5.0 这个 tag 上它仍然为真；自本版起，第一条命令就中止并报错。** 同一份探针
（好库 [0805..0810] 4 条 ⇒ 关库 ⇒ 只删 .dat ⇒ 重开 ⇒ 重拉；早到晚 / 晚到早 / 全区间一次三种顺序）两个底座各跑一次：

```
底座 e553d09（= tag v0.5.0 所指提交）
  每一条  err = nil · Halt = HaltAllCovered · Complete() false · 走查没通过「走查数出 0 条，而 .meta 记的是 4 条」

底座 986863d（本版的实现提交）
  每一条  err = ErrMissingRecords「开库时缺记录——盘上的记录少于 coverage 声称的条数，同步补不回来：少 4 条（coverage 声称 4 条）」
          Halt = 未记录（早退路径的约定，TestEarlyReturnsCarryHaltUnknown 钉着）· Complete() false
          rep.MissingRecords 一条：「…⛔ 别再重跑，也别只删其中一个文件：把这个周期的 .dat 与 .meta 一起删掉，然后按交易日从早到晚重拉」
          Incidents() 两条：Halt 未记录 ＋「开库时缺记录：…」· 没有向源要过数据 · 盘上 .dat 与 .meta 一个字节没动
```
（探针没有入仓；同一组场景在仓里由 `TestMissingRecordsAbortsBeforePlanning` 钉着，另含截成整条、截出半截、请求在 coverage 之外、旧格式 .meta 几格。）

⇒ **照 v0.5.0 注解判断「err = nil 而 Complete() 为假 ⇒ 多半只删了 .dat」的人，本版上看到的是 err 非空、`errors.Is(err, ErrMissingRecords)`。**
⇒ 出路没有变：**把那个周期的 `.dat` 与 `.meta` 一起删掉，按交易日从早到晚重拉**
（底座 986863d 实测：[0805..0806] 再 [0807..0810]，两条都 err = nil · Complete() true · 各 2 条）。

**判据与射程**（`tickflow.OpenState.MissingRecords` 的注释里有同一段）：

```
认      开库时「盘上完整记录条数 < coverage 声称的条数」：整份 .dat 被删、截成整条、截出半截（后者同时报截掉的残尾）
不认    条数够而内容不对（被换成别的记录、乱序、落在段外）⇒ 仍由同步末尾的走查报
不认    多于：崩在落盘与扩 coverage 之间留下的孤儿记录、只删了 .meta、HaltCoverageWrite 那个出口 —— 本库能合法产生的状态
不认    不填这一格的 Store 实现（零值 ＝ 没发现）
少认    旧格式 .meta 里没有条数的段（Bars = 0）⇒ 只会少认，不会误认
中止范围  这个周期的所有请求，包括 coverage 之外的新日子（在缺数据的库上往后追加只会让缺口更难补）
```

**为什么升级不会把好库拦下**：「少于」只能来自本库之外。segfile 的写路径从第一个发布版起就守着
「先落盘（`AppendBars` 里 `dat.Sync()`）、再扩 coverage，盘上条数不够就拒（`errNotDurable`）」——
引入于 bc92565；`v0.3.0` / `v0.4.0` / `v0.4.1` / `v0.5.0` 的 `store/segfile/store.go` 各含 `errNotDurable` 2 处、`s.dat.Sync()` 1 处。
⇒ 任何发布版写出来、没被外部动过的库都满足「不少于」。

## ⛔ 勘误二：v0.5.0 上「显式 To 含当天」在盘中同步，当天被登记成已覆盖，之后永远不再拉

**这是 v0.5.0 已经发布出去的缺陷，不是注解里某一格变了。** 评审方 2026-09-14 离线造输入发现，我复现，读数一致。

**形状**：调用方给了显式 `SyncRequest.To`，而区间里有一个在 `now` 时还没全部收盘的交易日（典型：盘中 `To=今天`）。
源按约定只给已完结的根 ⇒ Syncer 仍把那一天登记进 coverage ⇒ 收盘之后同一请求再跑，挑段跳过已覆盖（v0.5.0 丙片）⇒ **那一天永远不再拉，报告全绿**。
走查也抓不到：`.meta` 记的条数与盘上一致。

同一份探针（sinasource 真实响应 RB2610、末行 2026-09-08 · 手列日历 20260903/04/07/08 · 真 NewSyncer ＋ 真 segfile ·
请求 [20260907, 20260908] · ① now＝09-08 10:00 ② 同一个库、now＝09-08 16:00 再跑一次）各底座一次：

```
底座 e553d09（= tag v0.5.0 所指提交）；cbd90ff（修之前的 main）逐字相同
  ①  err = nil · Bars=1 · Halt=跑完 · Complete() true · Gaps「2026-09-08 拉过确认没有」· coverage [{09-07 09-08 1 1}]
  ②  err = nil · Bars=0 · Halt=区间里的交易日已经全部覆盖过 · Complete() true · Gaps「2026-09-08 拉过确认没有」
      SkippedCovered「跳过 2 个已覆盖的交易日…只拉剩下的 0 个」⇒ 09-08 那一根永远不在库里

底座 f218ae6（= tag v0.4.0）与 cb2a531（= tag v0.4.1）逐字相同
  ①  与 v0.5.0 相同：err = nil · Complete() true · 当天记成「拉过确认没有」
  ②  err「扩 coverage 失败…coverage 有重叠段」· Halt=预算耗尽 · Complete() false —— 吵；而盘上已经多追加了这一批（`HasBars` 报 09-08 有根，coverage 仍记 1 根）

底座 6525957（本版的修复提交）
  ①  err「To=2026-09-08 含一个在 now=2026-09-08 10:00 时还没收盘的交易日 2026-09-08（它最后一段收盘于 2026-09-08 15:00）——…
      要「同步到最后一个已收盘的交易日」请传 To=0，或把 To 设为那一天之前」· Halt=未记录 · coverage 为空 · 一次都没向源要
  ②  err = nil · Bars=2 · Halt=跑完 · Complete() true · coverage [{09-07 09-08 2 2}] · 两天都有根
```
（探针没有入仓；同形在仓里由 `TestDailyExplicitToTodayIsRejectedThenFilledAfterClose`（日线）、
`TestIntradayExplicitToTodayIsNotRegisteredAsAWholeDay`（1m：修之前是「半天 180 根登记成一整天」）、`TestSyncRejectsExplicitToWithUnclosedDay` 钉着。）
⚠️ 射程：`v0.3.0` 没量（那一版 `segfile.Open` 的签名不同，探针编译不过）；`cffexsource` 没单独量（它同是日线源，推论同形）。

**本版起的行为**：显式 `To` 含未收盘交易日 ⇒ `Sync` 报错、什么都不做。**盘中要「同步到最新」，传 `To=0`**（由 `ClipToLastClosed` 裁到最后一个已收盘的交易日）。

**已经受影响的库怎么认、怎么修**：
```
认   在 v0.5.0（或 v0.4.x）上、盘中用显式 To 同步过日线 ⇒ 那几天在 Gaps 里是「拉过确认没有」，而那个合约那天其实在交易
修   把那个周期的 .dat 与 .meta 一起删掉，然后按交易日从早到晚重拉（To=0，或 To 不晚于最后一个已收盘的交易日）
     两个文件一起删掉之后就是空库；空库上收盘后的同一请求，在 6525957 上拉到 09-07、09-08 两根（上面底座 6525957 的 ②：① 被拒，库本来就是空的）
     ⚠️ 没有拿一个【真被 v0.5.0 写坏的库】走一遍这条出路
```

## ⛔ 勘误四：v0.5.0 上 MaxConsecutiveFails ≥ 1 时，一块失败一次就会在 coverage 留洞，之后这个库再也拉不到新交易日

**这是 v0.5.0 已经发布出去的缺陷。** 评审方 2026-09-15 离线造输入发现，我复现，读数逐字相同。

**形状**：`SyncRequest.MaxConsecutiveFails` ≥ 1，同步中某一块向源要数失败一次（一次瞬时网络错误就够）。
Syncer 跳过这一块、照样落盘并登记后面的块 ⇒ coverage 中间留下一个洞。洞补不进去：
下一次同步先去拉洞里那几天，落盘时撞上「交易日倒退了」⇒ 同步停在那里 ⇒ **此后每次同步都在同一处报错，新的交易日永远拉不到。**
错误是吵的，而这个库自己修不好。`MaxConsecutiveFails` 取零值 0 时第一次失败就停、后面不登记，不触发。

同一份构造（日历 0803 0804 0805 0806 0807 0810 0811 · 假源每块 2 个交易日、每天一根 · 块首为 0805 的那一块失败一次 · `MaxConsecutiveFails=1` · 真 NewSyncer ＋ 真 segfile ·
① To=0810 ② 同一个库、To=0811（新交易日）③ 同 ②），即仓里 `TestFailedChunkIsRetriedNotSkipped`，各底座一次：

```
底座 e553d09（= tag v0.5.0 所指提交）；d7f2d9a（修之前的 main）逐字相同
  ①  请求块 [0803..0804] [0805..0806] [0807..0810] · err = nil · Bars=4 · Halt=跑完
      Gaps「2020-08-05..2020-08-06 没拉过」· coverage [{0803 0804 2 2} {0807 0810 2 2}]   ← 洞
  ②  请求块 [0805..0806] · err「落盘失败，停在 2020-08-05: segfile: 交易日倒退了……盘上最后一条是 2020-08-10……」· Halt=落盘失败
      Gaps 里多了「2020-08-11 没拉过」—— 0811 根本没被请求
  ③  与 ② 相同

底座 9031d68（本版的修复提交）
  ①  请求块 [0803..0804] [0805..0806] [0805..0806] [0807..0810] · err = nil · Bars=6 · Halt=跑完 · coverage [{0803 0810 6 6}]
  ②  请求块 [0811..0811] · err = nil · Bars=1 · coverage [{0803 0811 7 7}]
  ③  请求块（无）· err = nil · Halt=区间里的交易日已经全部覆盖过
```
（同形另两格：`TestBudgetExhaustedRegistersNothingAfterAndNextSyncAdvances`、`TestConsecutiveFailsResetAfterARetrySucceeds`。）
⚠️ 射程：`v0.4.x` 没量；真源上的瞬时失败没有端到端复现过（构造用的是假源）。

**本版起的行为**：
```
一块失败而预算还够   ⇒ 重试同一块，不跳过
预算用完             ⇒ HaltBudget，失败那一块及其后一块都不登记；下一次同步从失败那一块起
「连续」数的是同一块  ⇒ 两块各失败一次、中间隔着一次成功，不再算连续两次
```
⚠️ 最后一条是行为变化：v0.5.0 上 `MaxConsecutiveFails=1`、两块各失败一次会预算耗尽而停（上面第三个测试在 e553d09 上的读数：
「连续 2 次失败（上限 1），停在 2020-08-07」）；本版起两块各自重试成功、同步跑完。

**已经受影响的库怎么认、怎么修**：
```
认   Coverage() 有不止一段，两段之间隔着交易日；而且每次同步都报「落盘失败……交易日倒退了」，停在同一个交易日
修   把那个周期的 .dat 与 .meta 一起删掉，然后按交易日从早到晚重拉
     ⚠️ 没有拿一个【真被 v0.5.0 写坏的库】走一遍这条出路
```
