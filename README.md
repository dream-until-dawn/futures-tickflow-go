# futures-tickflow-go

中国期货的行情数据层：拉取、持久化、算指标，并向回测引擎提供可步进的多周期视图。

> **状态：设计阶段。两轮探针已完成，代码尚未开始。**
> 现在能读的是三份文档，见下。

---

## 这个库要解决什么

回测引擎需要一份**可信的**历史行情。中国期货的「可信」比想象中难，
因为这个市场有几件加密货币市场没有的事：

- 一天有 **2–4 个交易时段**，中间休市，夜盘还跨自然日；
- **交易日 ≠ 自然日**——周五夜盘属于下周一，且它跨午夜的部分落在周六那个自然日上；
- 每个合约都有**交割月**，长周期回测必须**换月拼接**，而拼接方式会改变结果；
- K 线有**持仓量**和**结算价**两个必需字段。

而免费数据源的粗糙程度，比这些还要棘手一点。

## 探针先行：四个值得知道的实测结论

动手写代码之前，先打了一轮真实接口。完整记录在 [docs/probe.md](docs/probe.md)，
这里挑四条最要紧的——注意第四条推翻了第二条：

### 一、新浪的期货实时行情已经冻结两年了

`hq.sinajs.cn` 返回 HTTP 200、字段齐全、数值合理。把它和日线序列一对：

| | 实时接口 | 日线 2024-07-17 |
|---|---|---|
| 开 / 高 / 低 / 最新 | 3538 / 3556 / 3484 / 3487 | **3538 / 3556 / 3484 / 3487** |
| 持仓量 / 成交量 | 2186809 / 1578526 | **2186809 / 1578526** |

**六个字段逐位相同。** 它自 2024-07-17 起就没动过，而大量教程和开源库
仍在用它取期货实时价。本库**不接这个源**，并要求任何实时源都带开机自检。

### 二、同样的日盘时段，两个品种的 60 分钟网格可以差 30 分钟

沪银 `AG0` 与沪铜 `CU0` 的日盘时段完全相同，但 60m K 线的标签是：

```
CU0:  10:00  11:15  14:15  15:00      （夜盘 240 分钟，对 60 整除）
AG0:  09:30  10:45  13:45  14:45  15:00   （夜盘 330 分钟，余 30 分）
```

沪银夜盘余下的 `02:00–02:30`，**跨过 6.5 小时的隔夜缺口**，
与次日 `09:00–09:30` 拼成了完整的一根。

所以周期对齐**不是时钟网格**，而是「交易日内累计交易分钟」上的等分。
任何「对齐到整点」的实现在沪银上**每一根都错 30 分钟**，且序列看起来完全正常。

### 三、主力连续是未复权的，换月当天凭空多出 1.5–1.7 个百分点

| 2026-08-28 → 08-31 | 涨跌 |
|---|---|
| `RB0` 主力连续显示 | **+2.73%** |
| 实际持有 `RB2610` | +1.00% |
| 实际持有 `RB2701` | +1.23% |

换月那天前后两根来自不同合约，中间的**基差**被当成了涨跌。
螺纹钢一年换月 3–6 次，17 年的 `RB0` 上有上百个这样的接缝，
而序列看上去连续平滑、毫无标记。

**所以换月拼接必须自己做，并且要把接缝交给下游。**
（天勤的主连 `KQ.m@SHFE.rb` 实测**同样未复权**，换月日还和新浪差两天，
那次甚至把一根阴线变成了阳线——两个主连连互相对照都不行。）

### 四、第一版的时间模型，被它自己的一个预言证伪了

上面第二条推出的规则是「沿当天实际交易的时段累计」。它解释了当时所有观察，
但有个可证伪的预言：**长假前交易所停夜盘，那天沪银没有 30 分钟的余数，
网格就该退化成沪铜那样。**

实测三个停夜盘日 × 三个品种：**日盘网格与普通日一模一样。** 预言错了。

正确的规则是：**网格相位是品种的固定属性（标称夜盘长度 mod 周期），
与当天是否真的开了夜盘无关。**

那个错误一年只在长假前后发作、只影响 `au`/`ag`/`sc` 这类夜盘不整除的品种，
不报错不崩溃，只是把那几天的每一根 K 线都错开 30 分钟。
[design.md](docs/design.md) 里两个版本都留着，连同推翻的经过。

## 自己验一遍

上面四条不用信，一条命令跑完全部 11 条实测结论：

```bash
python tools/probe/probe.py
```

只用标准库，**Python 3.8+** 即可（不依赖 3.12 的 f-string 新语法）。
2026-09-07 实测 **11/11 与记录一致**。
天勤那一半要 websocket，单独一个 Go 探针：`cd tools/probe/shinny && go run .`。
它断言的是**外部世界现在是什么样**，所以会因为上游变化而失败——那正是它存在的理由。

## 数据源现状

| 源 | 状态 |
|---|---|
| 新浪 日线 | ✅ 17 年（2009 至今），含持仓量与结算价，**六个交易所**（含 GFEX / INE） |
| 新浪 分钟线 | ⚠️ 5/15/30/60m，**每周期硬顶 1023 根且无法翻页**（降级为对账用） |
| 新浪 实时 | ❌ **已冻结两年**，不接 |
| 天勤 openmd 参考数据 | ✅ 免费无鉴权，含**按合约的交易时段表** |
| 天勤 深度历史 | ✅ **890,231 根 1m，回溯到 2016-01-04**（免费快期账户） |
| 天勤 实时 | ✅ 已打通（未完结根的标志位待验） |
| 中金所官方 | ✅ 可直连（对账用） |
| 上期 / 大商 / 郑商官方 | ❌ 被 WAF 挡（412） |

原先「唯一的硬缺口」——分钟级深度历史——**已解决**。新浪 1023 根的上限
（5m 只覆盖约 3 周）曾是去接第二个数据源的唯一理由，现在理由兑现了。

## 与姊妹项目的关系

**下游**是回测引擎，它同时消费本库与
[futures-position-simulator-go](https://github.com/dream-until-dawn/futures-position-simulator-go)：

```
futures-tickflow-go ──视图──> 回测引擎 ──成交/结算──> futures-position-simulator-go
      （本库）                                              （记账）
```

两个上游各自独立，但**口径在设计阶段就对齐**，免得回测引擎夹在中间多转一层。
已对出一处真冲突（郑商所三位 vs 四位年月码）、两样本库可以直接供给对方的
（**当日结算价**、**交易日历与时段表**），以及 float64/decimal 的边界该画在哪。
逐条见 [design.md 第十二节](docs/design.md)。

[okx-tickflow-go](https://github.com/dream-until-dawn/okx-tickflow-go)
在加密市场做同一件事。本库**不是它的移植**：指标层与存储层可以共享思路，
但**时间模型是全新的**，而且是本库绝大部分复杂度的来源。
差异逐条对照见 [design.md 的定位一节](docs/design.md)。
