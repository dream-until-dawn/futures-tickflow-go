# 「文档里声明了、但源码里还没有」的白名单。
#
# 格式：标识符  预定版本  说明
#
# ⚠️ 这不是例外表，是【带到期日的欠条】：
#
#   预定版本一旦打过 tag，doccheck 直接 FAIL。
#
# 不靠人自觉去清理，靠时间推着清。否则白名单迟早变成垃圾桶——
# 和「一个会红的必过项迟早被加 || true」是同一个形状。
#
# 加一项之前先问：它是真的排在后面，还是我不想现在处理它？
#
#   ⇒ 2026-09-13 那次改号（14 条：continuous 11 条 v0.6.0→v0.7.0 · AggRule 3 条 v0.5.0→v0.9.0）的答案：
#     **是真的排在后面** —— 用户两次裁决（v0.5.0 给已落地的硬化；天勤源起整体顺延一号），
#     问句与所选项逐字记在 docs/design.md §十五「版本号的两次裁决」。
#
# ---- ⚠️ 白名单的代价：这张表里的类型，它们的【字段】不受守卫 ----
#
# doccheck 的字段比对只在类型【已实现】时才触发（源码里找不到就走白名单分支）。
# 于是白名单里的类型，其字段从不被拿去和源码比——**它们本来也没有源码可比**。
#
# 代价是真实的：v0.3 设计里 `SyncRequest.From/To`、v0.6 的 `RollRule.Pick`、
# `Roll.Day` 三处都曾把 `TradingDay` 写成 `int32`——**和 doccheck 在
# `Bar.TradingDay` 上抓到的是同一族错误**，而它们在这里活了下来，
# 因为守卫够不到还没实现的那一半。
#
# ⚠️ **对表 2026-09-09（双方各自核过）：那三处【现在都是 `TradingDay`】。**
#
#     **在收编【之后】的这棵树上重量**（`docs/*.md`，`grep` 不区分围栏内外）：
#
#         docs/design.md    4 处 / 3 行
#         docs/probe.md     1 处 / 1 行
#         docs/contract.md  **0 处**  ← 那一处正是这一颗自己收编掉的
#         合计              **5 处 / 4 行 / 2 文件**
#
#     无一在 `SyncRequest.From/To` · `RollRule.Pick` · `Roll.Day` 这三个声明里。
#
# ⛔ **这一行上一版写的是「design.md 全库 int32 命中 = 6 处 / 5 行 / 3 文件」，两个错叠在一起**
#    （评审方 2026-09-09 抓的，我在这棵树上复现一致）：
#
#      一、**口径** —— 6/5/3 是 `docs/*.md` 的数，**不是 design.md 的**（design.md 单份 4 处）；
#          而「design.md 全库」这个说法本身就把【一个文件】和【整仓】混成了一句
#      二、**时间** —— 6/5/3 是【收编之前】的读数，而**收编正是这一颗干的事**
#
#    ⇒ **这颗提交作废了它自己写下的那个数。**
#    ⇒ 而它长在哪儿最刺眼：紧跟着的括注写着「单位写全，因为我第一版把 3 文件报成了 3 命中」——
#      **单位这次写全了，而那个数已经不是这棵树上的数了。**
#
# ⇒ 判据（比「数字要带射程」硬一格）：
#    **改动会影响到的那个数，必须在【改完之后】重量一次。**
#    「对表」这类记录尤其 —— **它的读者会照着它重跑**，
#    而重跑得到 5/4/2 的人分不清是文档漂了，还是自己的命令写错了。
#
# ⛔ **而盲区一点没变，这才是留着这个例子的理由**：
#    改回它们的是【人】，不是守卫 —— doccheck 至今一次都没比过这三处，
#    因为它们仍然在这张白名单里。
#    ⇒ **这个例子证明的是「盲区存在」，不是「现在有三处错」。**
#    ⇒ 它此前有【三个载体】（本处、docs/contract.md 的静默风险表、
#      tools/doccheck/main.go 的 render 注释），而三个一起漂了 ——
#      **同一个断言有几个载体，就有几个地方会漂。**
#      现在收成一个：另两处只留一句指针，指向这里。
#
# ⇒ **「还没实现」的那部分文档，是这张表用覆盖面换来的盲区。**
#    实现它的那天，字段比对第一次生效——那时冒出来的分歧不是新引入的，
#    是一直在那里、只是没人看得见。**别把它当成回归。**
#
# ---- 打 tag 那天，这张表【不该】红 ----
#
# 红了就是有一步没做，两种，doccheck 分开报：
#
#   「白名单已过期」    预定版本打了 tag，而源码里还是没有 → 实现没做完
#   「欠条已兑现，没清」 源码里已经有了 → 实现做完了，这一行忘了删
#
# 所以【不要】提前给这个红发通行证。说「打那一档的 tag 那天它们会一起到期、
# 这是设计如此」是错的——一个被预告过会红的检查，和一个被加了 `|| true`
# 的检查，最终下场一样：没人再读它。
#
# ⚠️ 这句话原本写的是一个具体的版本号。2026-09-08 里程碑整体后移一格时把它拿掉了，
#    理由不是「改起来麻烦」，是：**一个写在散文里的版本号，是一份没人守的第二拷贝**。
#    跟着改一次，下一次里程碑变动它会再坏一次；改成指代，它就不用再跟着走。
#
# ---- 打 tag 之前先空跑一次 ----
#
#   git tag v0.X.0 HEAD && go run ./tools/doccheck; git tag -d v0.X.0
#
# 它会当场告诉你这张表清干净了没有。
# 通则：**一个「条件成立时才失败」的检查，要在条件成立之前先模拟一次条件**——
# 否则暴露时刻就是你已经没得选的那一刻（v0.0.0 那次「批的 commit ≠ 打 tag 的
# commit」就是在打完之后才暴露的）。
